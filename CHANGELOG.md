# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/), and this project adheres to [Semantic Versioning](https://semver.org/).

## [Unreleased]

### Added

- **`spt verify --rmi-registry-port`** — `spt verify` now takes `--rmi-registry-port`, with the default (1099), help text and range check of `spt run`'s flag. Verify's test engine serves its RMI registry on that port, and the port conflict check and bridge port mappings use it. With `--api-port` and `--rmi-registry-port`, a host can be verified beside a running engine that holds ports 1099 and 9999. `spt run` takes the same flag for every engine in a run.
- **`spt replay --rmi-registry-port`** — `spt replay` now takes `--rmi-registry-port`, with the default (1099), help text and range check of `spt run`'s flag. Every engine of the replay serves its RMI registry on that port: the local engine, a lone remote engine, or the entry and every worker of a distributed replay, which the entry reaches on it. A replay that shares hosts with another replay or an `spt run` needs its own `--api-port` and `--rmi-registry-port`, also when it has a local worker. Replay now refuses an `--api-port` equal to `--rmi-registry-port`, as `spt run` does, so it accepts `--api-port 1099` with another registry port. At the default port, every engine command is unchanged.
- **Mongoose versioning flag** — The engine accepts the Mongoose 3.x flag `--storage-net-http-versioning` as a synonym for `storage.object.versioning` with the S3 drivers. **Compatibility:** with `s3` and `s3-rdma`, a command that already passes it now checks the bucket's versioning on first use, enables it on a bucket that has never been versioned, leaves it on, and writes `key~versionId` names; a suspended bucket, or one whose versioning check fails, is left alone with a warning (see **Bucket versioning at first use** under Changed). With `s3-aws` it only splits `key~versionId` input names. With `s3-tables` it has no effect. See the [S3 driver's versioning guide](engine/extensions/storage-drivers/implementations/s3/README.md#434-mongoose-versioning-flag).
- **DELETE from a saved items file** — `spt run delete --items-file` also accepts the `items.csv` saved by an S3 `spt run write --save-items`, as it is. A file whose first record is not the `bucket,key,size,version_id` header is read as one: each row `/<bucket>/<key>,<offset>,<size>,<layer>/<mask>` becomes the current-key manifest row `<bucket>,<key>,<size>,` (bucket = the first path segment, key = the rest, verbatim), and the canonical selection, de-duplication, `--bucket` assertion, multi-bucket rule, `--object-count` cap and recorded counts and SHA-256 apply as for a manifest; it stages to the same bytes as the equivalent manifest. After staging the run prints `DELETE Source: saved S3 items file (write --save-items)` with the rows converted and the buckets, quoted and cut to 64 bytes. It deletes current keys only, so a versioned bucket keeps its data versions and gets delete markers; exact versions need a canonical manifest. A file with any row that can't be mapped safely to one object (for example a name without a leading `/`, which includes a canonical file without its header, a `~` anywhere in the key, since a versioned write names `key~versionId` and the version ID can hold `/`, a `%` anywhere in the name, since a write can store a `%XX` escape decoded, a `+` anywhere in the name, since a write sends it raw, which a target can read as a space, while DELETE encodes it, a comma in the key, an empty bucket or key, a line over 1 MiB, or a blank line) is refused before any request, with exit 1 and the line number, also for the first line, and the error now names both accepted formats instead of only the header; a file refused for `~`, `%` or `+` must be converted by hand to a canonical manifest of the stored keys. Refusals of a saved file give line numbers, never a bucket or key: a `--bucket` mismatch names its line, and one object given two sizes names both lines. A saved file given the header is still refused, and the error now says that removing the header line works for `delete`. `--bucket` must be the first path segment of the saved names. The CLI can't see whether a row names a real object: use `--validate-inventory`, which checks every selected key before the timed phase, since `--verify` counts a 404 for a selected key as verified absent. Canonical manifests are unchanged, and `read-verify --items-file` still takes canonical manifests only.
- **S3 error code of a refused request in `errors.log`** — When a target refuses a request, the `s3` and `s3-rdma` drivers now log, after the existing status line, one more `errors.log` line with the S3 error code and message from the response body, for example `CREATE,<item>,/bucket/,: S3 error code EntityTooSmall, message: Your proposed upload is smaller than the minimum allowed object size.` It covers object PUTs and GETs, multipart parts, and multipart initiations, completions and aborts; multi-object DELETE and LIST responses, and single-range reads (`--range-size`), log no such line. A read split by `--part-size` is covered. Only the first 1 KiB of the body is read, the message is cut to 256 characters, and control, line separator and Unicode format characters in either are replaced, so the line cannot break the log; a code or message not found is logged as `(missing)`, and a refusal with an empty body logs no extra line. Operation status and counts are unchanged, and successful responses are not read. The multipart notes of `SPT_SYNTAX.md` and the `item-data-ranges-threshold` configuration row now say that Amazon S3 requires every part but the last to be at least 5 MiB.
- **Split-read failure mark for extensions** — The new final class `PartialDataOperationFailureMark`, in the package of `PartialDataOperationImpl`, has two public static methods, `markFailureRecorded(part)` and `failureRecorded(part)`, which take a `PartialDataOperationImpl`. A driver built on `CoopStorageDriverBase` marks a range out of retries, an upload part out of retries, and a range it settles unsent after a queue timeout, once the failure is recorded on its read or upload, under the read's monitor, and a split read ends only when each of its failed ranges is marked (see **Split-read counts**). The mark is never cleared, and `result()` does not copy it: a retried or recycled read makes new ranges. `PartialDataOperationImpl` and its supertypes gain no method of either name, so a subclass built against 5.17.0 loads, runs and recompiles as before, also one with its own `failureRecorded()` or with methods of these names from an interface of its own. The driver marks and reads only ranges that are `PartialDataOperationImpl`s: an extension's own `PartialOperation` type is judged as in 5.17.0, so its failed range out of retries, by its `retryCount()`, lets the read end once a range failure is recorded. The `PartialOperation` interface is unchanged. `CoopStorageDriverBase` also has a new protected method, `finishCompositeRead(read)`, called at most once per attempt, when a split read's last range ends (a read whose finalization is queued after a queue timeout skips it): a driver whose finalization of a read sends no request overrides it to end the read on that thread, as `s3`, `s3-rdma` and `s3-aws` do. By default it returns `false`, and the read's finalization is queued, as in 5.17.0.
- **Summary names a failure-limit stop** — When the engine ends an `spt run` phase early at its failure limit (`load.op.limit.fail.count`, default 100,000, or `load.op.limit.fail.rate`), the summary now says so in its warnings, with the failed count and how far into its time limit or request count the phase got, for example `Create: stopped at its failure limit after 28 failed requests (load.op.limit.fail.count 20), 694ms into its 12s time limit`. Before, it showed only the short duration and the failed count. The CLI reads the limits from the step's fetched `config.yaml` and warns only when the failures pass the count limit, or the rate limit is on and the phase had failures, and the phase also ended more than 1 second before its time limit or short of its request count; with the rate limit the warning is hedged, because the engine's comparison isn't in the results. A distributed phase gets no such warning, since the entry's `config.yaml` holds one engine's share of the count limits, not the fleet's. A run that `--auto-terminate-seconds`, Ctrl-C or a failed step ended gets no such warning, nor does a DELETE phase (standalone or `--cleanup`), a `list` run, a seed phase, a step bounded by `load.step.limit.size`, or a weighted or pipeline step. The exit code is unchanged: 0, unless the phase had no successes.

### Changed

- **RMI object range no longer published or checked** — `spt run`, `spt replay` and `spt verify` no longer publish or port-check the RMI object range: the engine never used it, since it serves its RMI services on the registry port. `--rmi-port-start` and `--rmi-port-count` are still accepted and recorded in `spt_run_params.json`, and have no effect. A port in use in 40000-40009 no longer fails a run's preflight, and a local worker or a bridge-mode verify container publishes only the API and RMI registry ports.
- **Partial-read performance wording** — The partial-read docs now describe the release performance check instead of a pending qualification: ordinary READ and WRITE runs showed no regression in the v5.15.2 check against v5.14.2, the last release before partial reads. No partial-read performance figures are published.
- **Known issue: default S3 auth version** — A direct-engine run (`java -jar`, `run.sh` or the image run by hand) with the `s3`, `s3-rdma` or `s3-tables` driver that passes no `--storage-auth-version` signs with V2 or V4 depending on the order in which the host lists the engine's `ext/` directory, so the same command can sign differently on two hosts. Pass `--storage-auth-version` explicitly: `4` for SigV4, or `2` for a legacy target that rejects SigV4. `spt run` always passes a version and is not affected. A later release makes V4 the single default.
- **Engine that never becomes ready** — When an engine never becomes ready, `spt run` and `spt verify` now show, after the wait failure and for each host whose engine API never answered, its container state (running, exited with its exit code, or missing) and its last 20 log lines, stdout and stderr together: in `spt run`'s API readiness failures, under the start failure of a remote worker or entry, and under `spt verify`'s `Ports Accessible` check. A local single-host `spt run` adds the container state to its startup diagnostics, which it already showed with the container's last 120 log lines, and now prints the failure line once, ahead of them. In those log lines, the values of `S3_ACCESS_KEY` and `S3_SECRET_KEY`, and each endpoint's host and host:port from `S3_ENDPOINT` and `S3_ENDPOINTS` (in any letter case), are masked as `***` wherever they appear as a whole token, as are credentials passed as key=value or flag arguments. A state or log that cannot be read is reported as such. Exit codes and the output of a successful wait are unchanged.
- **`spt run --rmi-registry-port`** — `spt run --rmi-registry-port` now works for remote and distributed runs; it previously applied only to local single-host runs. Every engine in the run serves its RMI registry on that port: a lone remote engine, and the entry and every worker of a distributed run. The entry reaches each worker on it, and the port conflict check covers it on every host. Because every engine serves both ports, `spt run`, `spt verify` and `spt replay` now refuse an `--api-port` equal to the registry port.
- **SSH keepalives** — Every SSH command and copy SPT runs now gives up about 60 seconds after its host stops answering, even where the SSH config sets a longer `ServerAliveInterval`, unless it runs over a shared connection opened outside SPT. A network gap longer than that, such as a VPN renegotiation, now ends the command instead of waiting for the connection to recover.
- **RMI handshake timeout in the launchers** — The SPT image, `run.sh` and `run.bat` now also start the engine with `-Dsun.rmi.transport.tcp.handshakeTimeout=10000`, beside the existing `-Dsun.rmi.transport.tcp.responseTimeout=10000`. It bounds the wait for the RMI handshake on each new connection between engines to 10 s; the JDK's default is 60 s. When a worker of a distributed run stops answering but its host still accepts connections (a frozen or stopped process), each call the entry makes after the first failure opens a new connection and waited the whole 60 s, so the entry failed about 8 minutes after the worker stopped. In a loopback test of a 30 s step with the worker stopped 10 s in, the entry now exits about 90 to 100 s after the stop instead of about 491 s (four runs: 91.0, 100.9, 90.9 and 90.9 s; on JDK 21), with the same exit status and error. Runs whose engines answer are unchanged. To override it, add the option with another value: `SPT_JAVA_OPTS` adds options after the defaults, and the JVM uses the later one, for example `SPT_JAVA_OPTS="-Dsun.rmi.transport.tcp.handshakeTimeout=60000"` for the JDK's default. `java -jar spt.jar` started without a launcher is unchanged.
- **`SPT_JAVA_OPTS` with the bundle launchers** — `SPT_JAVA_OPTS` now adds to the bundle launchers' default JVM options, as it does in the SPT image, instead of replacing them. Results of `run.sh` and `run.bat` runs that set `SPT_JAVA_OPTS` can differ from 5.17.0. **Compatibility:** to pick another garbage collector, turn ZGC off first: `SPT_JAVA_OPTS="-XX:-UseZGC -XX:+UseG1GC"`; G1 tuning options without `-XX:+UseG1GC` are accepted and do nothing under ZGC. A maximum heap below 1 GiB needs a matching `-Xms`, because the default `-Xms1g` stays: `SPT_JAVA_OPTS="-Xms512m -Xmx512m"`. `-XX:MaxRAMPercentage` has no effect while the default `-Xmx4g` is on the line; give `-Xmx` instead. To run without the defaults, call `java <options> -jar spt.jar` directly.
- **Bucket in op traces of manifest-driven steps** — The `ItemPath` column of `op.trace.csv` now holds `/<bucket>/<key>` for steps that take their objects from a `bucket,key,size,version_id` manifest, as other steps' rows do: write-verify's verify and `--cleanup` steps, `read-verify`, `read --items-file` with a manifest, and a `mixed` DELETE from a manifest `--delete-items-file`. The path is the one the `s3` driver requests, with one slash between the bucket and the key whatever slashes the manifest's bucket and key carry. A CREATE that takes its objects from a manifest names its destination, the output path, not the manifest's bucket. These rows held the key alone, so a run over several buckets couldn't tell which bucket each object was in. Traces are off by default (engine `output.metrics.trace.persist`), and other outputs are unchanged.
- **Bucket versioning at first use** — With `storage.object.versioning` or `storage.net.http.versioning` on, the `s3` and `s3-rdma` drivers now report what they found at a bucket's first use: versioning already enabled, enabled by this run, or could not be enabled. A bucket whose versioning is suspended is now left alone with a warning, and the run goes on un-versioned; before, SPT re-enabled it. When SPT can't read the bucket's versioning state, it now sends no request to enable it and warns, and the run goes on un-versioned. Each engine writes the notice that versioning is already enabled to the step's `messages.log`, and its warnings to `errors.log`; that this run enabled versioning is a warning, so it shows whatever the log level up to WARN. Each engine also writes them to a new per-step `bucket.versioning.log`, which carries them to the entry engine and is not a result file. On a distributed run the entry engine copies each worker's notices into its own two logs when the step stops, before it publishes the step's total metrics, so the run's results show them. It waits at most 10 seconds for this at each of the step's start, stop and close, and warns about a worker it left out because it didn't answer in time or an earlier read of it hasn't returned; that worker's notices are then only in its own `bucket.versioning.log`. **Recorded exception to the patch-stable rule (owner, 2026-11-14):** with `storage.object.versioning` or its synonym `storage.net.http.versioning` on, on the `s3` and `s3-rdma` drivers, a workload on a Suspended bucket (including Suspended with MFA delete enabled) now runs un-versioned with a warning instead of having versioning re-enabled, and a workload whose `GET ?versioning` fails now sends no `PUT ?versioning` and runs un-versioned with a warning. **Recorded with it (owner, 2026-11-15):** so does a workload on a bucket whose `Status` is neither `Enabled` nor `Suspended`, and one whose successful `GET ?versioning` returns a body that isn't a `VersioningConfiguration` SPT can read (an empty or non-XML body, for example). 5.17.0 sent the PUT in both cases unless the response body contained the text `Enabled` anywhere, so a `Status` such as `NotEnabled` got no PUT there either. A Suspended bucket with MFA delete enabled was misread as enabled before, so it already ran un-versioned, without a warning; it now gets the warning.
- **`spt run --output-dir` deprecated** — `spt run --output-dir` (`-O`) never had an effect: results have always gone under `--results-dir` (default `./results`). It is now deprecated, hidden from help, and warns when used; pass `--results-dir` instead. `spt replay -O` is unchanged.
- **`spt run` `--object-size` and `--duration` check** — `spt run` refuses an `--object-size` or `--duration` that the engine cannot parse before it starts anything, with exit 1 and `--object-size must be a size such as 4KiB, 1MB or 1KB-1MB, got <value>` or `--duration must be a time such as 30s, 5m or 1h, got <value>`; `--generate-only` now checks them as well. Such a value used to start the engines, and the step failed with the reason only in the engine log. Every value the engine accepts is still accepted, and each flag stays unchecked where the run never uses it: `--object-size` for `list`, `tables`, and DELETE with `--items-file` or `--delete-existing`, and `--duration` for `tables --test-vector compaction`.
- **Port held by an SPT engine, without a terminal** — A local `spt run` or `spt replay` with no terminal and no `--force` whose API port is held by an SPT engine now exits 1 at once and leaves that engine and its run alone: `port <N> is held by an SPT engine (run <id>, state <state>); it was left running. Use --force to stop it and free the port, or --api-port with --rmi-registry-port to run alongside it`. It used to try to stop the run, fail with `Failed to stop Spt test: stop command failed with status 400` and exit 1. End of input at the conflict prompt, as with stdin from `/dev/null`, now ends the same way, whatever holds the port, instead of `failed to read user input: EOF`. The conflict report now shows the engine's run ID and state, which were always empty, and shows a worker engine of a distributed run with the run it carries, although its status reads idle. A container that only looks like SPT by its name, image or labels is no longer reported as an engine with a running run.
- **Freeing a port held by an SPT engine** — `spt run --force`, `spt replay --force` and the `g` answer at the conflict prompt now stop the engine's active run, shut the engine down, wait for the API port to be free and then start the command's run. They used to fail with status 400. The wait polls for up to 60 seconds (a probe that starts near the end can take a little longer). The RMI registry port is not checked then, so the start can still fail on it. This ends another user's live run on the port if there is one; that run's CLI reports it as stopped and exits 0. The CLI acts only on the engine, run and container that detection identified and showed. Right before each request that changes something (the run's stop, the engine's shutdown, Docker's stop of a container and its removal), it checks again, and when it sees something else, or can't tell, it changes nothing more. The force choice, `--force` or the prompt's `f` answer, has two exceptions, set out below: a run that detection saw active with no start time is stopped by its ID, and a container whose port gives no answer at all is removed:
  - **One address.** Every HTTP request after the first connection, detection's and the actions', goes to the IP address that accepted that connection, not to the host name, which may name another address too. No redirect is followed: an SPT engine sends none, so a redirect is a service that is not the engine's, or not the one shown. Any 3xx answer counts as a redirect, whatever its `Location` says, and a redirect of a read that guards a write (`HEAD /run` or `/status`) refuses that write as a redirected write does, rather than counting as a read that failed; the message names the status code, not the `Location`. The port check's API client and the run tracker no longer follow redirects either: a redirected stop or shutdown made through them fails with a message naming the status code, and a redirected tracking poll counts as an answer that could not be read. Detection's own `/status` read is unchanged: a redirect or other failure there counts as a status that could not be read.
  - **Which run.** `g` is offered only when the SPT API answers on the port. `g`, `--force` and `f` act only on the run detection saw active (through `HEAD /run`), and shut the engine down only when that run, or none, is active. A run ID that `/status` names while no run is active belongs to a run that has ended: the prompt shows it, but a run active later with that ID is not the run shown, and is left alone. Run IDs can be reused, so a later run with the same ID is told apart only by the start time `/status` reports for a running run on the engine that started it. Once a run's start time was seen, a `/status` that shows another start time, or a running run with none, or cannot be read, leaves the run alone, and the engine is shut down only while `/status` shows that start time or the stopped run ending. A stop that finds no run and then sees the same ID active has found a later run, which is left alone. `g` also refuses a run that has ended and is still cleaning up (try again shortly), and a run whose `/status` cannot be read when it acts. Only when detection saw the run active but had no start time for it, as for a worker engine or a `/status` that could not be read at detection, does `--force` stop it by ID with `/status` unreadable; such a run is not shut down while still active.
  - **Which container, before an API request.** When detection showed a container, the run's stop and the engine's shutdown are sent only while that container, by its full ID, is still the one container that publishes the address; otherwise nothing more is sent, as when another engine took over the endpoint while the prompt was open. That check before the shutdown follows the stop, so the stop has then been sent. When no container publishes the address after the stop and the port can be bound, the engine has closed by itself, and the stop ends as a success. A Docker daemon reached over TCP or SSH may list another host's containers, so none of its containers is shown at the prompt or named in a message. When an SPT API answered at detection, the listing that looks for its container, and the listing before each API request, are each bounded to 5 seconds: at detection a listing that does not answer in time shows no container, and before a request it refuses.
  - **Workers.** A worker engine of a distributed run reports no start time, and the prompt says a later run reusing the ID cannot be told apart from it; such a run is matched by ID. An engine whose `/status` does not name the run it reports active may be a worker, whose stop only asks (the run goes on from its entry engine), or an entry engine whose status a refused `POST /run` overwrote; the CLI says `Asked the engine to stop run <id>; its status does not name that run, so this node may be a worker of it`, for both. It says `Stopped SPT run <id>` only when, after the stop, the engine no longer reports the run active or `/status` shows it ended.
  - **Which container is removed.** `--force` and the `f` answer remove a container only when all of these hold: the Docker daemon is reached through a local socket (`unix://`, or a named pipe on this machine, `npipe:////./pipe/...`, with the scheme in lower case as the Docker client requires); the address that accepts a connection to the port is the one that answered when the conflict was detected; exactly one running container publishes the port on a binding that covers that address (that address itself, or `0.0.0.0` for IPv4 and `::` for IPv6); it is the container detection showed; and, when an SPT engine answers there, it is an SPT engine node container (labels `spt.managed=true` and `spt.role=node`). Otherwise no container is stopped or removed; the message says why and names any candidate to remove by hand: a host-network engine, the containers that all cover the address, a publisher without SPT labels, or containers that publish the port number on another address, the other family or no address (as Podman's default publish does). When the containers could not be listed at detection, the message says so. A bridge container that uses the port number only inside its own network is never a candidate.
  - **The checks before a removal.** Right before Docker's stop of that container, the CLI sends `HEAD /run` (and reads `/status` when a run is active) to the same address. It goes on when no answer at all comes back (not one byte: the connection is refused, or it breaks, ends or times out before any byte; a service that is not an engine and sends something before it reads the request and then resets the connection can count as no answer too, but an engine reads the request first), when `HEAD /run` answers 204, as an engine with no active run does, or, for the force choice, when the active run is the run shown (its ID, and its start time when detection saw one; a start time that cannot be read then refuses). An engine too loaded to answer within 5 seconds counts as not answering, and its container is removed. Another run, a later run with the ID, an HTTP error status such as 503, a redirect, part of an answer (a status line and then a closed connection, say), an answer that is not HTTP, or any other answer leaves the container running, with no Docker change, and the message says why. A service that answers HTTP but not as an SPT engine is left running too: the CLI can't tell whether it is safe to remove, and the message names the container to remove by hand (`docker rm -f <name>`). A service that isn't SPT but answers `HEAD /run` with 204 is removed. Docker's stop can fail, or the container can restart after it and take a run, so once the stop returns or fails the same check is made again before the removal, and the address must have no publisher but that container; otherwise the container is not removed.
  - **When `--force` goes on to remove the engine's container.** After the graceful step, only when the port is still held and the checks before the removal allow it: the engine stopped the run and accepted the shutdown request, but the port is still held at the end of the wait (for example because of a longer `api.linger.sec`); the shutdown request itself failed; the stop request failed with an error status or got no answer; or the engine's active run could not be read when the stop began. A completed stop and shutdown is reported apart from a shutdown request that failed. When the graceful step refuses because the run or the container cannot be identified, or because a request was redirected, `--force` ends there with exit 1 and no Docker change (detection may still have listed the containers), and says to stop the run yourself, naming the engine's container to remove by name when it was shown.
  - **Limit.** A run that starts after the last check and before the request it guards is not seen: the engine's shutdown takes no run ID, and Docker's stop and removal know nothing of runs.
  - **Ctrl-C and SIGTERM** end the check, the prompt, the API requests, the waits and the checks after them with exit 1, reported as an interruption, and nothing further is sent; a stop or removal already sent is not undone. A probe cut short counts neither as a free port nor as a reason to go on, and the CLI's own time limits are reported as such.
  - **Compatibility.** In 5.17.0, `--force` first tried a graceful stop of an SPT service it identified, which always failed with status 400, and `f` went straight to Docker; both then removed the container they found using the port number, if any, and HTTP requests followed redirects. Against 5.17.0, `--force` and `f` now remove no container through a Docker daemon reached over TCP or SSH (`DOCKER_HOST`) or with an upper-case scheme such as `UNIX://`; that publishes the port only on another address, only on the other IP family, or without an address; when two or more containers' bindings cover the address that answered; that is not the container shown, that appeared after detection showed none, or when the container shown no longer publishes the address; when the address answering the port changed since detection; that does not carry SPT engine labels while an SPT engine answers there; when a check before the stop or the removal finds another run, a later run with the same ID, an HTTP error status, a redirect, part of an answer or an answer it can't parse, including from a service that isn't SPT and answers HTTP; or, under `--force`, whose engine's run could not be identified at the stop or before the shutdown. Neither 5.17.0 nor this version removes an engine on host networking, which publishes no port; this version names it, to remove with `docker rm -f <name>`. `g` refuses, with nothing sent, a run that is not the one detection saw active, a run whose start time was shown and whose `/status` cannot be read, gives no start time or gives another, a run that has ended and is still cleaning up, a run shown as a worker's (with no start time) that now has one, and an engine whose container is not the one shown before the stop. Stop such a run or container by hand.
- **Known issue: rate limit in a mixed step** — A `MixedLoad` step (CLI `mixed` workload, or a scenario's `MixedLoad`) does not apply `load.op.limit.rate` (`--load-op-limit-rate`): it accepts the limit but runs its operations without a rate limit, locally and distributed, on every driver, as it has since mixed steps were added. Such a step now logs a warning once at its start, on each engine, in the step's `errors.log`: `<step id>: a mixed step does not apply load.op.limit.rate; the rate limit of <rate> operations per second is ignored, and the step runs its operations without a rate limit`. The rate is the one the step runs with: from its last appended context when it has several, and each engine's share in a distributed step. A step that fails its start logs no such warning. The step's load and results are unchanged.

### Fixed

- **Cooperative driver dispatch task failure** — A cooperative storage driver whose dispatch task stops on an unexpected error or exception now fails the step and logs the cause once. Before, the step stopped sending without a message, then ended at its time limit as a success or ran on with only a count limit. Since 5.4.0.
- **`fs` driver at high concurrency** — The `fs` driver no longer stops serving (zero successes, the engine idle, operations still counted active until the stop gives up on them about 30 s after the time limit, and the run exiting 0) when its concurrency is above the engine's virtual-thread carrier count, for example 32 or more on a 32-CPU host, or 8 on a 6-CPU host. A READ, copy or CREATE step now runs to its limit and stops on time, and a later step in the same engine runs normally. The driver now opens its files and makes its output directory without holding a lock of its open-files maps, so a slow file open no longer holds up operations on the other I/O workers. Since 5.7.0.
- **Live metrics rows of mixed, weighted and pipeline steps** — Each live `/metrics/json` row of a step with several operation contexts, each `/metrics/fleet/json` and `/metrics/cluster/json` row of such a distributed step, and the step's overall completion, could show another context's success, failure and byte counts and latency and duration means, so the CLI's per-type rows, Total and failure chart overstated progress and showed failures that did not happen. Each row now reports its own context, and its latency and duration means stay within the range it shows. Result files and the summary were not affected. With `?verbose=1`, `diag_cached_progress` now marks only a row that used a cached value, where it marked every live row of a step with cached progress. For extension authors: `MetricsManager` adds the default method `getLastProgressSnapshot(MetricsContext<?>)`, a context's own progress, which falls back to the step lookups; `MetricsManagerImpl`'s `getLastProgressSnapshot(String)` and `getLastProgressSnapshot(String, boolean)` now return an entry only for a step with one context of that scope, and empty for a step with several. A call of the one-argument lookup with a bare `null` argument no longer compiles; cast it to `String`.
- **Verified read of a short body** — A verified READ (`item.data.verify`) on the `s3`, `s3-rdma`, Atmos and Swift drivers now fails as corrupt when the response body is shorter or longer than the item or the requested ranges. Before, a truncated or empty body passed, and so did valid data running past the end of an updated item. An RDMA transfer keeps its own length check, and a `read-metadata-only` (HEAD) read is not checked. Since 5.0.1.
- **Summary names a short seed** — When the seed phase of `spt run read` or `spt run mixed` wrote fewer objects than asked, because PUTs failed or the engine stopped it at its failure limit, the summary said nothing, though the later phases ran on those objects only. It now says how many objects the seed wrote and, when the failure limit stopped it, names the limit, for example `Seed: wrote 27 of 2500 objects (28 failed, 2445 not attempted) and stopped at its failure limit (load.op.limit.fail.count 20); later phases used only the objects written (operation.lifecycle.csv)`. The counts come from the seed's `operation.lifecycle.csv` and the limits from its `config.yaml`; in a distributed run each engine is checked against its own share of the failure limit, and the limit is named per node. With the failure-rate limit on (`load.op.limit.fail.rate`) the cause is hedged, and it is left out of a run that Ctrl-C or `--auto-terminate-seconds` ended or whose end is unknown. A multipart seed (`--part-size`) gets no such warning, because its lifecycle file counts every request of an upload, not objects; nor do results without a lifecycle file (engines before v5.15.0). The exit code and every other line are unchanged.
- **Split-read counts** — A read split into ranges (`--part-size`, or engine `item.data.ranges.threshold`) on `s3`, the drivers built on it (`s3-rdma` and the multi-NIC route) and `s3-aws` is now counted when its last range ends, so split-read operation counts and rates rise to their true values: `CountSucc`, `TP*`, the steady rows, `tps` in `result.xml`, and `Success` and IOPS in the CLI summary. The read used to wait in the driver's queue behind the work already queued ahead of it, so a run reported as little as a third of the objects the target had served on `s3`, and far fewer on `s3-aws` with thousands of input objects, with no failure shown; at a time limit, a read whose ranges had all run could end `unresolved`. The bytes counted for the ranges a run completes do not change; the duration statistics of split reads do. Because the read now ends on the thread that completed its last range, a run whose result output is saturated can complete a different number of ranges per second. A read with a range still unsent at the time limit stays `unresolved`, and the bytes of its finished ranges still count. A split read whose ranges ran out of retries now always ends with the failure of the last of them to be recorded: when two ranges failed in different ways at nearly the same time, the read could end with the other range's failure, so `load.op.retry` could count a read as failed that it would have retried, or the reverse.
- **HTTPS seed step that hangs on a worker** — A distributed HTTPS step, such as the seed of a read run, no longer hangs with a worker that generates no operations after a `LinkageError` (`attempted duplicate class definition`) for a Bouncy Castle class in its engine log ([#486](https://github.com/dell/storage-performance-tool/issues/486)). Extensions' classes are now loaded once when several threads ask for the same class at once, so concurrent TLS handshakes no longer hit this error. When an operation of a batch fails to start after earlier operations of that batch were queued, the queued operations are no longer lost, and none runs twice; before, the step could stop dispatching and wait for ever. After an ordinary exception, the failure is logged as a warning in `errors.log` and the failed operation is offered again; after a Java error or a failure that ends the run, the step fails (see below), and a queued operation that has not started is counted as unattempted. **Behavior change:** an unexpected Java error (a `java.lang.Error`, such as a `LinkageError` or an `OutOfMemoryError`) that reaches a step's load generator, including a failed internal consistency check of the generator, now fails the step with `Load generator stopped on an unexpected <error class>`, where it was logged and retried. A `MixedLoad` step whose generator stops on such an error, or on any unexpected exception other than an end of input, now fails with `Mixed load generator stopped on an unexpected <class>`; before, it could end with no failure reported.
- **Recycled multipart CREATE** — A recycled multipart CREATE (`load.op.recycle.mode` with `item.data.ranges.threshold`) now starts a new upload on each circulation. It used to fail its second circulation (on `s3`, after sending a completion with no upload ID) and then leave the circulation.
- **Duration DELETE stop that a cleanup retry completes** — A duration-mode standalone DELETE (`spt run delete` with `--duration`) whose stop does not complete at first (a transient failure closing admission, recovering, draining, stopping or shutting down a worker's slice, or a stop request during the slice stop) now ends with one outcome everywhere. Its results are written once, when the run's cleanup retry settles: `# Results`, the terminal metrics JSON, `metrics.total.csv`, `metrics.steady.total.csv`, `result.xml` and the exit code all follow that retry, with the DELETE counts captured after the drain. If every retry fails, the step ends `failed` and exits 1. Before, `# Results` said `failed`, and the metrics kept pre-drain counts marked unreconciled, which `spt` refused to read, while a successful retry turned the terminal outcome into `completed_cleanly` and the exit code into 0; and a worker slice whose stop failed on every retry left every record saying `completed cleanly` while the run exited 1 (since 5.15.0). A step stopped or closed outside its run, as by a script's own `close()` or at engine exit, writes `failed` at a stop that does not complete, now also when a worker slice's stop fails (before, it wrote `completed cleanly`); that outcome is now final, and a later close that completes the cleanup keeps it and closes the step, also when the inventory ran out before the duration (a run in that case still exits 1). A stop request during a cleanup retry still releases the worker slices and ends the step's stop threads, and a run whose retries end without closing the step stops collecting the workers' metrics. For extension authors: `LoadStepBase` adds the protected final method `runClosesAgain()` and the protected methods `writeOutputLeftToTheRunsClose()` and `failureKeptByClose()`, which `LoadStepClientBase` implements as final methods.
- **A NIC set's silent NIC no longer takes a new upload part for the whole timeout** — With a NIC set, a NIC whose attempt ends with no response (for example under a firewall drop) now has its idle connections closed, and, while another NIC of the set works, it is tried again only on a connection opened after that failure, which a background connect opens without holding an operation. Before, its trial took the next operation onto a pooled connection that still looked alive, so under a silent drop a multipart upload held its slot for twice `storage.net.timeoutMilliSec` again and again, the surviving NICs ran about 10% below their rate, and a time-limited step could overrun its limit by up to `load.op.wait.limit`. Uploads already sending on the NIC when it went silent still wait for their timeout. A NIC that comes back still takes its full share again once an attempt on it gets a response.
- **Every document of a weighted step's fetched `config.yaml`** — A weighted step's fetched `<step>.config.yaml` (from `spt replay` of a `WeightedLoad.append(...)` script) now keeps every YAML document the engine wrote: the base config, then one per sub-load, each with its credentials masked. Before, the CLI's masking kept only the first document, so each sub-load's weight, operation, count, size and item paths were lost. A weighted step with one sub-load no longer gets a failure-limit warning in the summary from the base config's limits (as steps with two or more sub-loads already did not). Single-document config files are unchanged. A script that reads the fetched weighted file with a single-document parser (for example PyYAML `yaml.safe_load`) now needs the all-documents form (`yaml.safe_load_all`), as the engine's own copy already did.
- **A step whose slice fails to shut down** — When a step slice's shutdown throws a runtime exception (for example a load step context whose drain or storage driver shutdown fails), the step still closes: its other slices are stopped and closed, and the step still writes `result.xml`, `metrics.total.csv` and `metrics.steady.total.csv` when an earlier part of its stop fails. Before, the step's close was skipped: the run could end with exit 0, result files missing and an empty saved-items file. On a CREATE, READ or integrity-mode step, an operation lifecycle file that stays missing, such as the failed slice's own, now fails the run with exit 1 through the engine's missing-artifact check; other steps still end with exit 0, with the failed slice's own files missing. On a distributed run the other slices' saved items, event-loop files and `operation.lifecycle.node-NNN.csv` files are collected (see **Per-node result files after a missing one**).
- **Per-node result files after a missing one** — When one node's `operation.lifecycle.csv`, `range.read.csv`, integrity log or standalone DELETE evidence is missing at a distributed step's end, the entry still collects every other node's copy, and logs a warning naming the node and the file for each copy it could not collect (for a lost node's DELETE evidence, one warning for the node on each close attempt). Before, it stopped at the first missing node and the files of the nodes after it were lost. The merged file or DELETE evidence is still not published, and the run still exits 1. For `operation.lifecycle.csv`, `range.read.csv` and the integrity logs, the failure now names every missing node (`failed to aggregate operation.lifecycle.csv: not published, missing node-001; collected the other 2 of 3`), a partly fetched file is no longer left as that node's copy, and a later step that reuses the `load.step.id` is now also refused when such a step left only other nodes' copies. A standalone DELETE's failure stays `failed to collect and publish DELETE evidence`, with the first file it could not collect as its cause and the others suppressed, and a later step that reuses its `load.step.id` is not refused for it. When the entry has lost a worker's step slice, the lost-slice failure (`engine N of M: the entry lost this node's step slice …`) stays the step's failure, as before, and only the warning names the node.
- **`SPT_RDMA` left set without the RDMA driver** — With `SPT_RDMA` set in the environment or `.env`, `spt run` with `--use-rdma=false` (also with `--s3-driver aws` or `default`), with a value such as `yes` that `--use-rdma` does not read, or with the `mock` or `tables` workload, and every `spt replay`, no longer start their engine containers with the RDMA device, `IPC_LOCK` and an unlimited memlock limit. A `mock` or `tables` run also no longer turns on RDMA passthrough or prints "RDMA mode enabled" when given the RDMA driver, which those workloads do not use. On a host without `/dev/infiniband` the container failed to start.
- **RDMA on a single remote engine** — An `spt run` on one remote host with `SPT_RDMA` enabled (for example `--use-rdma` with the `s3-rdma` driver) now starts that engine with the RDMA device, the `IPC_LOCK` capability and an unlimited memlock limit, as remote workers and entry nodes already had, so the engine can open the device.
- **Op trace collection on distributed steps** — With `output.metrics.trace.persist` on, a distributed step built with `append()` logged a false `Unexpected I/O exception` error and a delete warning for each appended context on each worker, and any distributed step did so when a worker traced nothing. A weighted step whose contexts set their own step ids also left every context's worker trace except the last on the worker. Each worker trace is now collected once per step id, and a worker with no trace file is skipped without a warning. With `output.metrics.timing.persist` on, the worker timing metrics file is also fetched once per step id, instead of once per context with transfer warnings; a distributed `MixedLoad` step still logs one transfer warning and one delete warning per worker, as its engines name their timing metrics file differently. For extension authors: `LoadStepClientBase` adds the protected method `contextOutputStepId(int)`, the step's id by default, which names the step id under which the entry collects a context's operation traces and timing metrics from the engines; a step type whose contexts write those under their own ids returns the context's id.
- **Op trace rows in another step's file** — With `output.metrics.trace.persist` on and two or more workers, or across runs on a persistent API engine (`--run-node=true`), a step's worker trace rows could be written into an earlier step's `op.trace.csv`, and the step's own file came out short, with exit 0 and no warning; an untraced earlier step could get an `op.trace.csv` of rows from a later one. The entry now copies each step's worker traces, and logs the errors and warnings of the copy, under that step's id. The worker trace files are now copied one after another instead of in parallel, so collecting large traces at the end of a step takes longer.
- **Partial-read step with one object ending early** — A partial-read (`--range-size`) step with one object left to read (one object in the run, or one in every node's share of a distributed run) no longer ends before its time or count limit. Many such steps stopped early with exit 0, no warning and consistent-looking result files, because the step's completion check could pass while the object's next read was already with the storage driver. Steps with two or more objects to read were not seen to end early; the fix covers them too.
- **Stopping a range READ with retries** — A partial READ (`--range-size`) with `load.op.retry` on, stopped while range retries were waiting, now stops at once. It used to wait `load.op.wait.limit` (30 s by default), which added that wait to the step's total duration and lowered its average IOPS and bandwidth, and dropped the op-trace rows of those retries; with `load.op.wait.finish=false` it did not wait but reported the delivery error at once. A scenario `stop()` of such a step also failed the run with exit 1 and "Range result delivery exceeded the step drain bound" (since 5.15.0). With `load.op.wait.finish=false` (retries on or off), a range GET whose response had arrived when the stop began is now output, with its op-trace row, while the stop waits for it up to `load.op.wait.limit` (normally a few milliseconds); the stop used to fail with that error. With retries off too, a failed range GET whose response arrived as the drain bound expired is now published instead of failing the stop with that error. Steady-state figures and operation counts are unchanged.
- **An `fs` or `s3-aws` I/O worker that does not stop** — When an I/O worker of the `fs` or `s3-aws` driver does not stop within 1 s at the end of a step (for example a file open that blocks, or a full pipeline handoff), the driver now logs a warning and the step closes normally, with the late operations counted as unresolved in `operation.lifecycle.csv`. The run used to end with `operation.lifecycle.csv`, `operation.lifecycle.node-000.csv` and `event.loops.json` missing, an empty saved-items file, and the `s3-aws` clients left open. Since 5.15.0. A late `fs` CREATE that resumes after the close also closes its file.
- **Port conflict prompt without a terminal** — A local `spt run` or `spt replay` whose API port is held now asks at the conflict prompt only when stdin is a terminal and the command is not headless (`--headless`, or no `/dev/tty`). With stdin from `/dev/null` or a closed stdin it used to print the conflict menu and fail with `failed to read user input: EOF`, and a headless run on a terminal (`--headless`, or a native Windows build, which has no `/dev/tty`) showed a working menu; each now prints no menu and exits 1 with the message that names what holds the port and how to run alongside it, as an end of input at the prompt does, and leaves the holder alone. This holds whatever holds the port: a port held by a service that is not SPT, with stdin a pipe or a file, used to end with `Graceful stop only works for Spt services`, and now ends with that message too. `--force` is unchanged. `spt update` without `--yes` and with stdin from `/dev/null` now says `non-interactive update requires --yes` instead of prompting and cancelling.
- **Scenario stopped by a signal during a step** — A SIGTERM or SIGINT while a scenario waits on `step.await()` or runs `.run()` no longer logs `ConcurrentModificationException` or `No step slices are available`, and the exit no longer occasionally abandons the step's close and loses result files such as `result.xml` or `operation.lifecycle.csv`. `await()` on a step the exit has already closed now ends as a stop (`InterruptedException`) instead of failing with `IllegalStateException`.
- **`fs` random-range updates** — An UPDATE with `item.data.ranges.random` on the `fs` driver no longer writes wrong data into a range that crosses the end of the data ring (`item.data.input.layer.size`, 4 MiB by default). A later verified read reported such items as corrupt. An item of 4 MiB or more almost always has such a range, and was written wrongly whenever the update chose it.
- **Fixed-range appends on the Netty HTTP drivers** — A fixed-range UPDATE (`item.data.ranges.fixed`) on the `s3`, `s3-rdma`, Atmos and Swift drivers whose ranges hold an append (`-N-`) together with other ranges now records the item's size correctly, sends each append at its own offset (an append that other ranges follow is sent as a closed range, for example `bytes=1024-1535,0-99`) and counts the bytes it sends. With `load.op.retry` on, a retried append now starts from the object's size before the first attempt, so it no longer leaves a hole that a later verified READ reports as corrupt. On those four drivers a lone append and overwrite-only ranges are unchanged. A fixed-range or whole-object UPDATE on `netty-mock` now records the item's size as the real drivers do. Before, it grew the recorded size by the bytes updated, so a whole-object UPDATE of a 1 KiB item recorded 2048, a recycled one grew it on each pass, and `0-99,200-299` recorded 1224; now 1024. An append grows it by the append only (`0-99,-512-`: 1536, was 1636). Since 5.0.1.
- **Retried random-range UPDATE on the Netty HTTP drivers** — With `load.op.retry` on, a random-range UPDATE (`item.data.ranges.random`) on the `s3`, `s3-rdma`, Atmos and Swift drivers no longer records the ranges of a failed attempt as updated: the ranges are recorded only when the UPDATE succeeds, and the retry re-sends the same ranges, so a later verified READ no longer reports the item as corrupt. Since 5.0.1. A retried random-range UPDATE on the `fs` driver, which already recorded the ranges only on success, now also re-writes the failed attempt's ranges instead of drawing new ones.
- **`fs` append across the data ring end** — An `fs` UPDATE with a fixed-range append (`item.data.ranges.fixed` such as `-1MB-`) whose new bytes crossed the end of the data ring (`item.data.input.layer.size`, 4 MiB by default) left a run of zero bytes in the file and recorded the item too large, so a verified READ reported it corrupt. A fixed-range list holding an append and another range also recorded a wrong size, and two appends left a gap. The UPDATE's operation and byte counts are unchanged, except for a list that holds an append and an open-ended `N-` range, whose byte count followed the wrong size. Since 5.0.1.
- **`fs` fixed-range UPDATE counts and retries** — An `fs` UPDATE whose `item.data.ranges.fixed` list had a from-offset range (`N-`) before an append (`-N-`) counted more bytes than it wrote. A list with a from-offset range at or past the item's end wrote none of its ranges, or failed: on a 1 KiB item `0-99,2000-` and `2000-,-512-` wrote nothing, and `1024-,-512-` failed. Such lists now write their other ranges, and a from-offset range past the end writes nothing. With `load.op.retry`, a multi-range append that failed after one of its ranges was written grew the item again on the retry. The item's size now changes once, when the UPDATE succeeds, and its byte count is the bytes written. Since 5.0.1.
- **Path with a trailing slash** — The `s3-aws` driver no longer adds a slash to the object key when the bucket or path ends with one (for example `--bucket foo/`). It wrote bucket `foo` key `/name` where the `s3` driver writes `name`, so a later verify or another driver could not find the objects. Objects written that way by earlier runs keep their leading-slash keys: the same run repeated with the fixed driver addresses `name`, not `/name`, while a listing of the bucket still finds and addresses them. Separately, the `s3` and `s3-rdma` drivers' standalone DELETE (`delete --items-file`) of one object at a time, and its verification HEAD, now address the key under a manifest bucket written with a trailing slash (`bucket/`): they addressed key `/k1` instead of `k1`, so the step could report success with the listed objects left and objects named `/k1` removed. A batch DELETE already sent the right keys; its request now goes to `/bucket?delete` instead of `/bucket/?delete`. The `s3-aws` standalone DELETE and HEAD still send such a bucket name unchanged.
- **Count-limited recycle steps** — A step with recycle mode and a count limit, such as `spt run read -n N` with fewer seeded objects than N, no longer issues more than N operations. It used to issue and count up to one batch more. Now at most N operations are issued and counted, successes and failures together; a step whose operations fail until nothing is left to recycle still ends below N. A retry (`load.op.retry`) is part of the operation it retries and does not count again. `operation.lifecycle.csv` counts requests, not operations: its `accepted` holds successes only, and its `terminal_results` include each retry and, for a read split by `--part-size`, each part request, so they need not equal N. A count-limited LIST step now requests at most N pages: each page request is one operation toward N, but LIST success counts are the objects those pages return, so its totals and steady count can exceed N. Affected runs send fewer requests: their totals, bytes, steady count and steady-window end can change, and outside LIST the steady count no longer exceeds N.
- **Saved items file under the manifest header** — `spt run` now refuses a saved items file (`--save-items` output) that was given the `bucket,key,size,version_id` header, and says it is a different format, instead of running with wrong object paths. Such a row was read as bucket = object path, key = hex offset and version ID = layer/mask, so a run could send requests for objects that don't exist, and on some targets exit 0 with the listed objects left in place. `delete --items-file` and `read-verify --items-file` check every row; `read --items-file`, `mixed --read-items-file` and `mixed --delete-items-file` check the first data row of a local regular file. Both split rows as the engine's CSV parser does, so a quote inside an object path or a bare-CR line end, alone, mixed with LF, after earlier bare-CR rows or ending the file, does not hide a saved row. Not judged: a size in non-ASCII digits; a key, size or version ID over 1 MiB (an object path cut at 1 MiB is still judged); and, on `delete` and `read-verify`, a saved row whose end the CLI does not see within 1 MiB after it stops reading a row it cannot parse, or, on a named pipe or other stream, one whose line end is not yet in the CLI's buffer. `delete` and `read-verify` then stop with exit 1 and the CLI's own error for the file; the three other flags run. The run stops with exit 1 before any engine starts, and the refusal comes before the multi-bucket one. `read-verify` also adds the explanation to its header error when a saved items file has no header; `delete` reads such a file as a saved items file (see **DELETE from a saved items file** under Added), and the three other flags still take it. A row counts as saved when its `key` is a hexadecimal offset that fits a signed 64-bit integer and its `version_id` is `<layer>/<mask>`, with a hexadecimal layer that fits a signed 32-bit integer and a mask of hexadecimal digits or none (so `0/` counts). A real object with such a key and version ID would be refused too; no S3 server tried issues such a version ID. Other manifests are unchanged.
- **`s3-aws` byte counts** — On `s3-aws`, a multipart CREATE now counts each successful part once and nothing for its parent, and DELETE, STAT and NOOP data operations (mixed steps, `--cleanup` steps, scenario steps) count 0 bytes, as on `s3`. **Compatibility:** in this patch release, `s3-aws` Size and bandwidth change for the same workload. A fully successful multipart CREATE step, including a copy step above the part size, which `s3-aws` runs as a multipart upload, reports half the total of 5.17.0; its steady totals and rates lose the object sizes the parents added, so they fall by about half. An upload that fails keeps the bytes of its successful parts. The op trace's rows for a multipart upload's parent show 0 instead of the object size, and `s3-aws` DELETE, STAT and NOOP Size and bandwidth drop to 0. `load.step.limit.size` follows these counts: a size-limited multipart CREATE step writes about twice as many objects before it stops, and the limit no longer stops `s3-aws` DELETE, STAT or NOOP steps, as on `s3`. Such a step runs until another limit or the end of its items, so a DELETE step that relied on the size limit can delete every listed object. The old values were wrong since 5.9.0 (multipart) and 5.6.0 (DELETE, STAT and NOOP).
- **`s3-aws` multipart upload timing** — On `s3-aws`, a multipart upload's own `Duration` and `Latency` sample is now its completion request, including any retries and back-off the AWS client makes for it, as on `s3`, instead of the whole upload from its initiation to its completion, which overlapped its parts' samples. A completion that fails still adds no sample, and counts, bytes and rates are unchanged. **Compatibility:** in this patch release, `s3-aws` multipart CREATE `Duration*` and `Latency*` change for the same workload, steady rows included: the mean, `DurationSum[s]` and the upper quantiles fall, the median and the minimum may fall too, and the per-bucket statistics rows change the same way. Before, `DurationSum[s]` could exceed the step's time multiplied by its concurrency. The op trace's row for an upload's parent and the per-item timing output now cover the completion (for a failed upload, its completion and the abort sent after it, or the abort alone after part failures); the whole upload's time is still the op trace's initiation row's start to its parent row's end. The old values were wrong since 5.9.0.
- **Ranges threshold on drivers without multipart support** — The `fs`, `atmos` and `s3-tables` drivers have no multipart (composite) handling, and now refuse an `item-data-ranges-threshold` (`--part-size`) above 0 for a CREATE or a READ at step start, whatever the object sizes: the step fails with exit code 1 and `The storage driver type "fs" does not support composite (multipart) operations, but item.data.ranges.threshold=<bytes> would make composite CREATE operations; set item.data.ranges.threshold to 0 for this driver` (or `READ`). The entry engine checks every context of the step that runs operations (in a `pipeline` or `weighted` step, each appended context) before it reads any item input, so a READ from `item-input-path` sends no listing request, and when every engine runs the same driver no operation is sent. When a worker runs a driver that refuses and the entry engine's driver does not, as with an engine of another build, only the worker refuses, as its slice starts: by then the entry has read the items and started its own slice, which can send operations. A threshold that is not a size, such as `bogus`, is read only for a CREATE or a READ on a refusing driver, and fails the step as it did before, when the step slice reads it; a LIST or any other step that never used it runs as before. The run API's `/status` gives the same text, with `configuration` as its category, instead of `see the engine log`. Linear, pipeline, weighted and `mixed` steps are refused alike, and a refused step closes the drivers it opened, which a long-lived engine serving `POST /run` used to keep open for each refused linear, pipeline or weighted run. The entry engine's item input driver is now closed on every failure of its setup, also for a threshold that is not a size, which kept its threads and descriptors open on each such run. On `fs` such a step used to write empty files and count them as successes, with twice the object bytes (since 5.0.1); an upload whose part failed could leave the upload uncounted and hold its upload slot; a split read failed every range as corrupt with `item.data.verify`, and counted every byte twice without it. On `atmos` each part was sent as a new object, and each part of a read asked for the whole object. On `s3-tables` such an operation, each of its parts and its end each ran the configured opMode's request instead of a multipart one, and the operation counted once: in `tableWrite` mode, a table write for the operation, one for each part and one more at its end. With the threshold at 0, or for any other operation type, these drivers are unchanged. Every other driver accepts the threshold as before, among them `s3`, `s3-aws`, `s3-rdma`, `swift` and `dummy-mock`. For driver authors: a driver without composite handling names the new marker interface `CompositeOperationsUnsupported`, which has no methods, in its own `implements` clause; `StorageDriver` itself is unchanged, so a driver built outside the engine keeps its behaviour whatever methods it declares. Only the driver's own class counts: a subclass of `atmos` or `s3-tables` built outside the engine, and a driver that wraps a refusing one, run as before unless their own class names the marker too. `LoadStepClientBase` gains no method, so a load-step client built outside the engine compiles and runs as before.
- **Steady window with retry** — With `load.op.retry=true`, a finite item input without recycle and no count limit at or below its size, a step that reads the end of its input after handing over its last operation now ends the steady window when dispatch is seen to have finished, as it does without retry, rather than after the drain. The steady rows of these steps change, most where the last operations were slow or failed, and a window can now report `short` where it reported `valid`. Results that arrive after the window closes count in the total row only. A step whose last operations were still waiting to be handed over at the end of its input already ended the window this way and does not change. Affected since 5.17.0.
- **Worker shutdown and `DELETE /run`** — A worker node now closes every step service on `POST /shutdown` and exits, also after a step whose entry died was followed by another step on the same node; it used to keep the abandoned step running with no API left. `DELETE /run` on a worker now stops that node's share of the matching run and logs a warning, instead of answering 200 and stopping nothing. The step stays open for its entry, and a run is still stopped on its entry.
- **Worker step whose entry has gone** — A worker node now stops and closes a step whose entry has made no call for 120 s, with a warning, instead of generating load until the worker is stopped. The entry now fails the step when it loses a worker's step slice: the run exits non-zero, and the entry's log has one error line naming the worker node and the step. The entry loses a slice when its `await` call to the slice fails in RMI, or when its stop or close of the slice fails in RMI or finds the slice already released by the worker (`NoSuchObjectException`), as after that worker's 120 s. Such a run used to finish as a success, although its totals can leave out all of that worker's operations. This changes two behaviours of otherwise working runs. A failure at a slice's stop or close, such as a refused or reset connection, now fails the run, where it used to be logged and ignored. One failed `await` call now fails the run too, and the slice stays lost when contact comes back: the entry then stops the whole step at once (see **Distributed step that lost a worker**). A stop or `await` call that gets no response within the RMI response timeout (`sun.rmi.transport.tcp.responseTimeout`, 10 s in the image and the `run.sh` and `run.bat` launchers) is not a loss: it is the worker still finishing its operations in flight inside the call, for up to `load.op.wait.limit`, as a stop does, and as a `pipeline` stage that ends at a size limit does inside the await. The exit status does not change, as in 5.17.0. A slow stop logs `failed to stop the step slice` at WARN; a slow await logs `did not answer its await within the RMI response timeout` at WARN (5.17.0 logged nothing), and the entry then no longer awaits that slice and goes on to its normal stop and close of it, where a dead worker is still lost. After a slow stop, that worker's operations that end after the timeout are still missing from the totals, and after a slow await the entry stops that worker when the other engines finish, so a worker that lags can have its later pipeline stages cut short, with only the WARN to show for it (both known issues, as in 5.17.0). Only a read of the response that timed out counts, which RMI reports as an `UnmarshalException` caused by a `SocketTimeoutException`; a connect that timed out or was refused, a reset connection and a worker process that exited during the call still lose the slice. A worker host that powers off, a network cut or a hung worker during the call first gives the same read timeout, so its slice is lost later, at a failed metrics fetch from it during the step (see **Distributed step that lost a worker**), or when its next call or its close fails to connect. A close of the slice that times out the same way keeps the warning when that slice's latest stop timed out too, because the worker's close waits for that stop; a close that times out after a stop that answered loses the slice. A run whose close timed out behind a slow stop can still exit 1 when the entry collects that worker's files before the worker has written them (`failed to aggregate operation.lifecycle.csv`), as in 5.17.0. For extension authors: `AsyncRunnableBase` gains a protected no-op method, `afterCloseTransition()`, which the close that closed the object calls once, outside its lock. `LoadStepClientBase` overrides it as `final`, so a load-step client built outside the engine that declares a method with that signature must rename it.
- **Distributed step that lost a worker** — A distributed step whose worker engine stops, dies or fails in RMI during the step now fails at once, with exit code 1 and `engine N of M: the entry lost this node's step slice, so the step's totals can leave out all of its operations; see the entry's log` as the step's failure, instead of running on with the entry engine alone until the step's limit, or forever with no limit, and then failing with `failed to aggregate operation.lifecycle.csv`. The entry's log line for the loss now says the same, `the step's totals can leave out all of that node's operations, so the step fails`, where it said only that node's operations since its last metrics report were missing: once the entry loses a slice, by any of its calls to it, it fetches no more metrics from it, so `metrics.total.csv` counts only the other engines' operations, while its `NodeCount` still counts every engine. When the entry loses a worker's slice during the step's await, it stops every other slice of the step at once, in parallel, its own and the other workers', and logs `lost a step slice, so the entry stops the other N remote step slices now` at INFO (`the other remote step slice` with one other worker, and no line with none). It waits for no engine's await or stop to answer first, as a worker's await answers only once that worker's stop has drained. The step ends once every stop has answered: a `pipeline` stage of the entry's own that ends at a size limit drains its operations in flight, for up to `load.op.wait.limit`, and a worker whose stop answers only after its own drain holds up the step's end, but no engine starts new operations meanwhile, with two exceptions: a `pipeline` slice stops its stages one after another, so a later stage can go on starting operations while an earlier one drains, as at any stop of a pipeline step and as in 5.17.0 (a known issue); and a slice whose stop could not be sent at first, because a call to it got no response within the RMI response timeout, gets its second stop only once every other stop has answered. Each of those slices gets that one stop, and a second one only when the first failed before it was sent, so a worker whose stop gets no response within the RMI response timeout logs one warning, the stop's, and none for its await. A standalone DELETE stops its slices after the await, as before. A failure of the step's close that follows, such as that worker's missing files, no longer replaces the lost engine's failure. The entry now also finds a worker whose own slice has ended, as a worker stopped with SIGTERM ends it, and a worker that no await poll has reached yet in a step with more engines than the entry's CPUs: in every distributed step but a standalone DELETE in duration mode, which keeps its own loss handling, the entry's metrics fetch from each worker, at each aggregation period, loses that worker's slice at its first failure in RMI, from the step's start until its stop, also a fetch that gets no response within the RMI response timeout, unlike the await: a healthy worker answers the fetch while its slice drains, inside its stop or inside its await, so a fetch that gets no answer is a worker that has stopped answering. Such a fetch times out only when the worker stalls while that fetch is waiting for its answer, though: a later fetch first pings its pooled connection, and RMI takes a ping that times out for a dead connection and opens a new one, whose handshake waits up to RMI's handshake timeout. So a worker that stalls and then goes on within about 70 s (about 20 s with a 10 s `sun.rmi.transport.tcp.handshakeTimeout`) is usually not lost, and can still let a count-limited step end short with exit code 0, with only the await's WARN to show for it (a known issue). A fetch that fails once the step stops, as its slices close, is no loss. A worker that stays frozen, such as one stopped with SIGSTOP, fails the fetch only when RMI opens a new connection to it and that connection's handshake times out (`ConnectIOException`), about 70 s after the freeze with the 10 s response timeout and RMI's default 60 s handshake timeout (`sun.rmi.transport.tcp.handshakeTimeout`): a step with no limit then fails with exit code 1, where it ran on, and a time-limited step that reaches its limit first finds the loss at its stop, as before. Without a response timeout, as in a plain `java -jar` launch, no call to a frozen worker ends, and such a step still does not end (a known issue). Once the entry has lost a slice, by any of its calls to it, it makes no further call to it but one close, sent at once from a thread of its own: a lost worker that is still alive stops and closes its slice on it. The entry waits for that close for up to the RMI response timeout, or 10 s when none is set, and a worker that does not get it stops and closes the slice itself 120 s after the entry's last call. The entry no longer stops, shuts down or polls a lost slice, asks it for its step id, fetches its terminal or bucket metrics, or reads or deletes its node's files: the entry collects none of that node's files and logs one warning saying so for the node, `the entry collects none of the files of node …, whose step slice it lost`. The item output file then leaves out that node's items, as do the timing metrics file and the operation traces, and an artifact that needs every node's file is not published at all: `operation.lifecycle.csv` (each other node's rows stay in its `operation.lifecycle.node-NNN.csv`), the integrity manifest and, for a standalone DELETE, its DELETE evidence. Their failure names the lost slice (`… was not collected, as the entry lost its node's step slice`) instead of an empty or missing file, and the entry logs a warning for each NIC file it did not get from that node. A frozen worker therefore costs no further wait of the entry's after its loss, where each of those calls used to wait about 60 s; a fetch or a stop that was already waiting when the slice was lost still runs to its end. A standalone DELETE keeps its own coordination of its slices' stops and closes, so a lost slice still gets its stop and close, but the entry collects none of that node's files either, where it used to collect a live worker's DELETE evidence. A working run's output does not change. The INFO line `Failed to fetch the metrics snapshots from …` now comes at most once per worker and step, for the first failed fetch that does not lose the slice, instead of at each of the step's metrics reports (about 90 lines a second for a dead worker); every later failed fetch from that worker logs at DEBUG, also after fetches from it have succeeded again, and a fetch that loses the slice logs the lost-slice error line instead. For extension authors: `MetricsAggregatorImpl` gains a public constructor that takes the entry's record of its lost slices, the new public interface `MetricsAggregatorImpl.SliceLoss`; the existing constructors of `MetricsAggregatorImpl` and `MetricsSnapshotsSupplierTaskImpl` keep their behaviour, apart from the INFO line above.
- **`/run` on a former worker** — A `--run-node` engine that has served a step slice for an entry now answers `HEAD /run` 204 and accepts `POST /run` once that slice has ended. It used to report the old slice's run as in progress and refuse every later run, standalone or as an entry, until the process restarted. `GET /run` with the id of a slice that has ended and closed now answers 204, and `DELETE /run` with it 204 or 404; both answered 200. A slice counts as busy from the end of its start, so a run posted to a worker while an entry is starting a slice there is accepted.
- **Refused `POST /run`** — A `POST /run` that a busy engine refuses with 409 no longer changes the run in progress: its `/status`, and the configuration, run id and step id of its later steps, including the HTTP headers and URI arguments they send. Two requests arriving together can no longer run one request's scenario with the other's configuration. A busy engine now answers 409 before it configures anything, so a request it would reject while configuring gets 409, not 400. After `DELETE /run`, `POST /run` answers 409 and `HEAD /run` 200 until the stopped run has finished its cleanup; `GET /run` and a repeated `DELETE /run` treat that run as the active one meanwhile. Wait for `HEAD /run` 204 or a terminal `/status` before posting again.
- **`/shutdown` after `DELETE /run`** — `POST /shutdown` sent after `DELETE /run` now waits, as `POST /shutdown` alone does, up to 10 seconds for the stopped run to finish its cleanup and publish `STOPPED` in `/status`. It used to close the engine's services at once, so a cleanup longer than the `api.linger.sec` window was cut short when the process exited, `/status` kept reading `RUNNING`, and the count of an operation still in flight was lost. `spt run --force`, `spt replay --force` and the `g` answer at the conflict prompt send this sequence.
- **Run interrupted without a stop** — When a node's run is interrupted by something other than a stop (`DELETE /run`, `POST /shutdown` or the end of the process), for example by a thread an earlier scenario left running, `/status` now reports it `FAILED` with a category and message instead of `COMPLETED`, and the node keeps running later runs. The node used to lose its run thread: the next `POST /run` answered 202 and never ran, and later ones answered 409 until a `DELETE /run`. A node whose API server stops with a run still active and no `POST /shutdown` now also reports that run `FAILED`.
- **Map settings no longer carry over between runs on a node** — A header, URI argument, object tag or `nodeInterfaces` entry set by one `POST /run`, in its scenario or its defaults part, no longer stays in the node's configuration for later runs. A node restart was the workaround. Each run copies a list setting held in an `ArrayList`, `LinkedList`, `Vector`, `CopyOnWriteArrayList` or `Arrays.asList` list, such as a list set from text. It also copies a `List.of`, `List.copyOf`, `Stream.toList` or `Collections.singletonList` list, or a `Collections.unmodifiableList` view, that holds a map or a list that is copied in turn, and shares one that doesn't. A view whose backing list can't be read is shared, with a warning. A copy keeps the list's class. A copied `Arrays.asList` list holds only text when every element is text or empty, as a list set from text does, and takes any value otherwise. Any other list, such as one of an extension's own list classes or a `synchronizedList` or `checkedList` view, is shared with the node as before, along with any map or list it holds. Within one scenario, a value set on one step still reaches later steps (a known issue, fixed in 5.18).
- **Weighted step stall** — A `WeightedLoad` step no longer hangs, or stops driving load until its time limit, when one of its sub-loads finishes first because its count was reached or, for a sub-load that does not recycle, its input ran out. The other sub-loads carry on to their own limits and share the cycle by their weights. A time-limited step that used to stall this way now reports higher totals and different steady rows. A recycling or path-listing sub-load with nothing left to issue before its count limit still holds the others back.
- **Weighted steps with small weights** — When the positive weights of a `WeightedLoad` step sum to between 1 and 99, including the default weight of 1, the step now multiplies them at its start by the smallest integer that brings the sum to at least 100, keeping their ratio, and logs the weights it uses. While every sub-load is still running, such a step behaves as if those larger weights were written: a generator refused by a short weight cycle waits before it asks again, which held a step at 1/1 to a few tens of thousands of operations per second on a fast target, and that limit is gone. A fast context beside a slower one whose input queue has filled slows down far less than before, but still waits: with `load.batch.size=1` it waits for the slower context to use its scaled share, one operation per pass (50 passes at 1/1), before each new cycle. The remaining weights are not scaled again when a sub-load finishes, so a step whose surviving weights sum below 100 can be limited again from then on. With every context fast, the weights keep their ratio but no longer force an exact split over short intervals. Such steps now build their input backlog faster at start-up, as steps with larger weights already do, so on a CPU-bound client the totals of a short run can be lower than before. Steps whose positive weights sum to 100 or more do not change. Affected: 5.15.0 and later, and releases before 5.8.0.
- **Weighted steps without a step id** — Two `WeightedLoad` steps with no `load.step.id` in one scenario, or one such scenario sent twice to a node, now work. Compatibility: results that such a step, or a context of a `WeightedLoad` step that sets no id of its own under a step with no configured id, wrote under the engine's start-up id move from `log/none-<ts>/` to `log/weighted_<ts>/`: `metrics*.csv`, `result.xml`, `errors.log`, `messages.log`, the step's `config.yaml`, `event.loops.json`, the lifecycle files and `op.trace.csv`, on each worker of a distributed run too, so a node serves them under `/logs/weighted_<ts>/`. The `load_step_id` metrics label changes the same way. This includes the bundle's `spt-weighted` Compose service. `log/none-<ts>/` still exists, with the start-up files only, and `/status` still reports the `none-<ts>` id. A context that takes a configured `load.step.id` from its step keeps that folder. A context that sets its own `load.step.id` keeps it, so two runs of such a step under different step ids write that context's results to one folder; when it is the last context, its id names the step, as before, and a later step with the same id is handled as before: it is refused (`StepIdInUseException`) when a result file it would write under that id already exists, as for a CREATE after a CREATE, and otherwise runs and can add a second `<result>` to that `result.xml`, as a CREATE after a NOOP does. Set `load.step.id` if a script looks for the folder. For extension authors: `LoadStepClientBase` adds the protected method `marksSetContextStepIds()`, `true` by default, with which `append()` marks a context whose map sets `load.step.id` as having its id set (`load.step.idAutoGenerated` false); a step type that reads that flag from the merge of its contexts returns `false` to keep the merge as before.
- **Copies of a step that has run** — A `config()` or `append()` copy of a step that has already run, with no step id set by the user, now gets its own generated step id and result folder, so `Load.run(); Load.config({...}).run();` works. A `MixedLoad` copy no longer writes its created items into the first step's `put-remaining.csv`, also when the copy sets its own step id, which 5.17.0 appended there; a `config()` or `append()` copy lists them in its own file. Before, such a copy wrote into the first step's folder: from 5.15.0 a CREATE or READ copy then failed when it closed (`stale node source exists`), and an UPDATE, DELETE, NOOP or LIST copy exited 0 with repeated CSV headers and two `<result>` documents in one `result.xml`. A step id set by the user is still copied, and still refused when reused where it was before.
- **Created items of a `MixedLoad` step with `append()`** — A `MixedLoad` step built with `append()` now lists its created items in its own `put-remaining.csv`. It used to leave that file empty, log that it lists 0 of the items the step created, and list them under a second generated `mixed_<ts>` folder, on each worker separately in a distributed step, from 5.8.0; the empty file and the error came with 5.17.0, and a distributed step also logged that it failed to read a worker's item output file. That folder also held the step's per-operation `errors.log` lines, its `messages.log` and its `op.trace.csv`, which are now in the step's folder; a step id given in an appended map no longer names a second folder either, since the base's id, given or generated, names the step. A file given in the last appended map is now the one the step writes and checks, on every node; a file the base gives beside it is no longer created empty and checked instead. A `MixedLoad` `append()` that changes which operations run reported them under the wrong operation type in `metrics.total.csv`, from 5.8.0, and one that changes the concurrency limit or item size reported the base's values; the rows now carry the operations, concurrency and size the step ran. The operations, counts, rates and bytes a step runs do not change, and neither do steps without `append()` or `spt run mixed`.
- **A step object runs once** — A scenario that starts a stopped step again (`stop()` then `start()` or `run()`), or calls `run()` a second time on a step that has run (for example `Load.run(); Load.run();`), now fails with exit 1 and a clear message, and a node reports `FAILED`. A restart used to fail with a step-id error, or to rerun the whole count and time limit and exit 0 with doubled metrics, and a second `run()` ran nothing and reported success. This affects every release so far. **Compatibility:** a scenario that restarts a step and exited 0 before now exits 1; build a new step from a prototype with `config()` instead. The scenario docs no longer promise resume, which no release provided.
- **Result files of a signal-stopped step** — When SIGTERM or SIGINT sent to the engine process stops a step, the step's `metrics.total.csv`, `metrics.steady.total.csv` and `result.xml` files, and its `metrics.bucket.total.csv` and `metrics.bucket.steady.total.csv` files when it writes them, now have one header, every operation's row and one `<result>` element. Before, a signal could repeat the header or silently drop a row. Which files are written is unchanged: the summary files still need `output.metrics.summary.persist`, and the bucket files a step with bucket metrics on several buckets. Runs not stopped by a signal are unchanged.
- **File system listings skip subdirectories** — An `fs` path listing (`--item-input-path`) now yields only the regular files of the listed directory. Subdirectories, which a READ or UPDATE failed, are skipped, and the log notes how many. An entry whose attributes cannot be read, such as a file in a directory the user cannot search or a link to one, is skipped with a warning. A FIFO in the listed directory no longer stalls a READ step. A DELETE step no longer removes empty subdirectories of the listed path.
- **Out-of-date files in a user-set `SPT_HOME`** — The engine no longer starts with an out-of-date defaults file, extension defaults file or default scenario that it could not replace in a user-set `SPT_HOME`, for example a home installed by another build in a directory the engine's user cannot write. It stops with exit 1 and one line naming the file, the directory and the cause, and says to make the directory writable by the engine's user (for a read-only file system, to use a home on a writable one; for another cause, to check the file) or to unset `SPT_HOME`. The same rule covers every file the engine installs there. Before, it logged warnings and ran on the old file's settings with exit 0, or failed on a configuration value that did not name the file. Installing into a shared `SPT_HOME` is now atomic where the file system supports atomic moves, so engines starting together do not read a half-written file. A current home, even a read-only one, and a writable home are unchanged: a writable home's out-of-date or edited file is replaced with one warning. A file the engine cannot replace in a writable home, such as a bind-mounted `defaults.yaml` from another build, now stops the start too. With `SPT_HOME` unset, as for every `spt run`, image and `run.sh` start, nothing changes, unless the engine cannot finish its temporary home, for example when the temporary directory is full: that start now stops with the same one-line message.
- **Object size of items-file reads** — `spt run read --items-file` without `--object-size` no longer reports the CLI's 1 MiB default as the object size. The summary shows the measured average, such as `64.00 KiB avg`, or `—` for a partial READ or a READ with no successes, and its Object size line says `discovered at runtime`; the `--generate-only` parameter listing says `(from items file)`. A size range given with `--object-size`, such as `16KiB-256KiB`, is shown as given instead of `0 B`. `ObjectSize` in `spt_run_params.json` is now empty for these runs, and the live view's `DoneMiB` shows 0 for them. An explicit `--object-size` is still shown as given. The scenario and `result.xml` are unchanged. Affected since 5.6.0.
- **Multipart initiation response without an upload ID** — When a target's multipart initiation response has no upload ID, the `s3` and `s3-rdma` drivers no longer write the whole response body, raw, to `errors.log` and the console for every operation. A refused initiation or abort logs only its status and error code, and a success response without an upload ID is warned about once per step with a short, cleaned excerpt: the operation and the first 256 characters of the body's first 1 KiB after any leading whitespace, with control, line separator and Unicode format characters replaced; later ones are logged at DEBUG. Such an operation still fails as before.
- **Multipart log fetched** — `spt run` now saves the engine's multipart log (`parts.upload.csv`) as `<stepID>.multipart.csv` for a single-engine step. The CLI looked for it under names no engine uses, so it was always recorded as missing. A distributed step still records it as missing until the engine collects every node's log. The documented columns are corrected.
- **A multipart part that could not be queued** — With `s3`, `s3-aws`, `s3-rdma` and `s3-tables`, an upload or composite range read whose part, range, completion or abort could not be queued within `spt.mpu.child.enqueue.timeout.millis` (default 30 s) now ends as one counted failure. An upload's status is the first failure recorded for it, which is `FAIL_TIMEOUT` when the queue timeout came first; a range read's is the last, which is `FAIL_TIMEOUT` unless a range in flight ran out of retries after the timeout. For an upload, the part that timed out and the parts after it are not sent, and the abort is queued at once, while parts already sent may still be in flight; a part queued before the timeout can still be sent ahead of the abort. A range read ends once its ranges in flight end, and its ranges not yet started are not sent. When an upload's abort or completion cannot be queued either, the upload is still counted as a failure, and its abort is sent directly, outside the queue, so the upload no longer stays open on the target. The stop waits for that abort as it waits for the abort after a failed completion. The errors log still says that such an upload may stay open on the target, as it logs that line before the abort is sent. With integrity metadata on, `multipart.lifecycle.csv` records the upload as `failed_aborted`, or as `failed_orphaned` when the abort fails, is still unanswered at close, or comes after the driver began closing. Before, the step lost the operation: it was never counted, and a step limited by count could hang until its time limit. Affected since 5.10.3.
- **`~` in a versioned item's path** — With object versioning on (`storage.object.versioning`), a `~` in an item's path, such as `--item-output-path=/bucket/run~1`, is no longer taken as a version separator, so retried, recycled and copied operations address the right object on `s3` and `s3-rdma`. In v5.17.0 a retried PUT of item `key` sent `PUT /bucket/run~1/bucket/run`, and a retried GET sent `GET /bucket/run~1/bucket/run` with header `x-amz-version-id: 1/key`. Only a `~` in the name's last path segment starts a version; a `~` in the key itself stays ambiguous (see the s3 driver README, section 4.3). A version ID that contains `/` is not recognised as a version in an item name: a retried or recycled operation on an item renamed `key~<id>` with such an ID addresses an object literally named `key~<id>`, and each successful response appends another `~<id>`, so a recycled CREATE or UPDATE writes a longer key each cycle.
- **`push-worker-image.sh` reported success for an image that can't run** — `engine/tools/push-worker-image.sh` now fails when the saved image has no layer content or a worker's loaded image doesn't match the local one, instead of reporting success. Before contacting any host it checks the saved tar's `manifest.json`: the image must list layers, and its config and every layer must be in the tar; otherwise it prints the tar size and the local image size, suggests re-pulling the base image or rebuilding, and exits 1. After each load it compares the worker's `Os`/`Architecture` and `RootFS.Layers` with the local image's, and counts a worker that differs, or whose inspect fails, as failed. The normal log line now shows the tar size beside the local image size. The script now needs `python3` on the host it runs on; its arguments and exit codes are unchanged.
- **Docker diagnostics of remote replays** — With `SPT_JAVA_OPTS` set, `spt replay` on a remote host, on distributed workers or in attach mode now copies the JVM diagnostics of each engine container it starts into `<results-dir>/<label>-<timestamp>/diagnostics/`, with `diagnostics_manifest.json`, as `spt run` does. They used to be deleted on the host without being copied, whether the replay succeeded or failed. A local replay already kept them.
- **Manifest items output** — A step that reads a canonical `bucket,key,size,version_id` manifest now writes each object's path to `item.output.file`, as it does for other items: the manifest's bucket and the key for a read, delete, stat or update, also when the step sets `item.output.path`, and the output path (the configured `item.output.path` or its default, kept relative if it is) and the key for a CREATE, with the key alone when it already starts with that path. A later step that reads the file back now addresses the object the first step did with the `s3`, `s3-rdma` and `fs` drivers, whatever its own `item.input.path`; with `s3-aws` and a CREATE output path that ends in `/`, the first step wrote an extra `/` after that path (key `/dir/k2` under `/dst/`, `pre//dir/k2` under `/dst/pre/`), as it does for other items, and the read back drops it. From v5.14.0 on the step wrote the bare key, which the reading step took from its own `item.input.path`: a flat key worked when that was the manifest's bucket, and a nested key such as `dir/k2` was read as key `k2` in bucket `dir` and not found. Rows of other items are unchanged. Limits of the legacy format: it has no version ID column, so whether a row keeps its version depends on the driver and the versioning mode (with versioning on, `s3` names the item `key~versionId` and the row carries the suffix; `s3-aws` writes the key alone); it cannot hold a key with a comma or a line break; and a key with an empty segment, such as `a//b`, reads back as another path, as a plain item's does. With `fs`, a key starting with `/` under a relative output path it starts with, such as `/dst/k1` under `dst`, reads back as `/dst/k1`, not the `dst/dst/k1` the CREATE made.
- **`result.xml` start date** — `result.xml` and `result-threshold.xml` could show a start date of 1969-12-31 and a 1970 end date when the step closed before the row was written: the row read `StartDate="1969-12-31 23:59:59"`, `StartTimestamp="-1"`, and an `EndTimestamp` of the elapsed time minus 1, from v5.7.1 on. The row now records the step's start time when it is queued, so `StartTimestamp` is the real start and `EndTimestamp` is start plus elapsed time. Counts, rates and latencies were not affected, and rows that were right are unchanged.

It no longer continues with the hosts already connected, reports too few hosts, or shows an SSH failure. The exit code is still 1.
- **Mock driver concurrency no longer negative** — With `dummy-mock` (`spt run mock`), the concurrency columns in the metrics CSVs (`ConcurrencyCurr`, `ConcurrencyMean` in `metrics.csv`, `metrics.total.csv` and `metrics.steady.total.csv`), the step summary and `/metrics` no longer show negative values. The driver read its scheduled and completed counts one after the other, so a sample read low by every operation that completed in between, from v5.0.1 on. It now reads them stably, so the mock's mean concurrency is a small non-negative number instead of slightly negative. Real drivers were not affected.
- **SigV2-signed S3 listings** — With `storage-auth-version: 2`, the listings of the `s3` driver and of `s3-rdma` and `s3-tables`, which inherit it (the item input path listing, the LIST step, the versions listing and the delimiter probe), no longer fail with `403 SignatureDoesNotMatch` on targets that follow the SigV2 specification, such as SeaweedFS. The driver signed the whole query string; it now signs the path plus only the SigV2 sub-resources (such as `versions`, `uploadId` and `partNumber`), sorted by name, with an empty value signed as the bare name and a `versionId` value signed decoded (see **V2 signature of an encoded version ID**). An item whose name holds a query sends that query and now signs only its sub-resources, as a strict target computes them: `k?x=1&versionId=a%2Bb` signs `/<bucket>/k?versionId=a+b`, and with versioning on, `k?x=1` at version `a+b` (sent as `k?x=1?versionId=a%2Bb`) signs `/<bucket>/k`. It used to sign the query as sent. Bucket checks and bucket creation with `storage-net-http-uri-args` now sign the bare bucket path too. The item input path listing had regressed in v5.14.0; the LIST step had always failed this way. Requests that already signed correctly, such as multipart, `versionId`, tagging, delete and versioning requests, sign the same bytes as before, except an empty version ID (an item named `key~`, which targets refuse), whose `?versionId=` now signs as the bare `?versionId`. SigV4 is unchanged.
- **Versioned read selects its version** — A versioned read (`storage.object.versioning` with `key~versionId` items) on the `s3` and `s3-rdma` drivers now reads the named version with `?versionId=`. It used to send an `x-amz-version-id` request header, which S3 ignores, and read the current version. A versioned STAT now checks the named version; it used to send no version. The request header is no longer sent on READ, including a metadata-only READ (`storage.net.http.read-metadata-only`); DELETE and UPDATE requests are unchanged. Read sizes and recorded version IDs can change, and so can success and failure counts: a READ or STAT naming a version that no longer exists (deleted, expired, or from an items file of another bucket) used to succeed on the current version and now fails with 404. Recorded exception to the patch-stable rule (owner, 2026-11-14): the workload that changes is a versioned READ or STAT with `storage.object.versioning` and `key~versionId` items; with versioning off nothing changes. Versioned copy and items above the multipart threshold still select no version; see the [S3 driver's versioning guide](engine/extensions/storage-drivers/implementations/s3/README.md#43-versioning).
- **Retried versioned operation keeps its version** — A retried versioned operation (`storage.object.versioning` with `load.op.retry`) keeps its version. A retried versioned DELETE used to become a plain DELETE, which adds a delete marker, and a retried READ read the current version. The item is no longer renamed while its request is built, so a failed attempt leaves it named `key~versionId`, and a successful one still renames it `key~<returned version>`, without a second suffix. A success whose response has no `x-amz-version-id` header now keeps the name `key~versionId`, where it used to leave `key`; after a CREATE or UPDATE that name is the previous version, not the one the `PUT` made. Recorded exception to the patch-stable rule (owner, 2026-11-14, widened 2026-11-15): the workload that changes is a retried versioned operation with `storage.object.versioning`, `load.op.retry` and `key~versionId` items, and a non-retried versioned operation on a `key~versionId` item that succeeds without an `x-amz-version-id` header or fails, whose result keeps the name `key~versionId`; with versioning off nothing changes. **Compatibility:** with versioning on, a driver extension that overrides `dataUriPath` now receives the item with its whole `key~versionId` name, where it used to receive `key`, and the driver takes `~versionId` off the end of the path it returns. If that path doesn't end with `~versionId`, nothing is sent and the operation fails at once with `FAIL_UNKNOWN`. A driver extension's `httpRequest` can throw the new protected `HttpStorageDriverBase.RejectedRequestException` to fail an operation the same way; see the [S3 driver's versioning guide](engine/extensions/storage-drivers/implementations/s3/README.md#43-versioning).
- **V2 signature of an encoded version ID** — With `storage.auth.version=2` (the default for the engine's `s3` driver; `s3-rdma` and `s3-tables` default to 4, and `spt run` passes 4), a request that selects a version whose ID needs percent-encoding (for example `v+1=:x`) is now signed with the decoded value, as V2 requires, while the URI still carries it encoded. It used to be signed encoded, so a strict target rejected it with 403. This affects a versioned READ, STAT and DELETE on the `s3` and `s3-rdma` drivers, and explicit-version requests (integrity manifest items): DELETE and explicit-version requests already failed this way before this release. Only requests a strict target rejected change; IDs that need no encoding, and V4, are unchanged. **Compatibility:** with versioning off, the only V2 requests this entry changes are those that carry a percent-encoded `versionId` (integrity manifest DELETE, presence and explicit-version requests), and a strict target rejected those before. Multipart and tagging requests sign their URI as sent, as before. Listings and an item whose name holds a query also sign differently, under **SigV2-signed S3 listings**.
- **Long requests on the Netty drivers no longer fail at the net timeout** — On the `s3`, `s3-rdma`, Swift and Atmos drivers, a single PUT, multipart part or GET (whole-object or `--range-size`) that took longer than `storage.net.timeoutMilliSec` (default 30 s) failed with `FAIL_IO` (`FAIL_TIMEOUT` for range reads) and a "Premature channel closure" warning, however steadily its bytes moved, and a request on a pooled connection that had sat idle could fail before the timeout. The timeout is now the inactivity timeout it is documented to be: a transfer that keeps moving never times out, and a request on a reused connection gets the full timeout. A silent response is now reported the timeout after the last request byte is handed to the socket, and an upload the target stops reading within twice the timeout of its last progress, instead of the timeout after the connection's last read. Bytes still in the socket buffers do not count as progress, so a target that takes longer than the timeout to read a body's tail from them is reported as a silent response. On `s3-rdma` the same timer covers the in-band HTTP requests and the RDMA transfers they carry: an RDMA transfer still fails after the timeout, now counted from its own request rather than from the connection's last read, which on a reused connection could come well under the timeout. Workloads whose requests all finish inside the timeout are unchanged, except that a request on a reused connection no longer fails early. `s3-aws` was not affected.
- **`s3-aws` reads split by `--part-size`** — `s3-aws`: reads split by `--part-size` now run as ranged GETs, instead of hanging without a request. A seeded `spt run read --s3-driver aws --part-size <size>` reads each object larger than the part size with one ranged GET per part, in parallel, and counts it once, with the object's size in bytes. As on `s3`, a split read ignores a requested version ID, and the bytes of parts that succeeded also count when the read fails. Since 5.9.0 the driver failed such a read before it sent any request, and the read step hung with no successes or failures. The workaround (`write --part-size <size> --save-items`, then `read --items-file`) is no longer needed. Reads not split by the part size, and every write, are unchanged.
- **V4 signing with `storage-net-http-uri-args`** — With `storage-net-http-uri-args` set, V4-signed object requests from the `s3` and `s3-rdma` drivers are now signed over the query they send, with parameters sorted by name; targets that check SigV4 refused them with 403 before. The README now lists which requests carry the arguments.
- **First-use versioning check** — The `s3` driver's first-use versioning check no longer throws and stalls the step when its `PUT ?versioning` times out; it warns that versioning could not be enabled, and the run goes on. That PUT is now signed with the bucket's own credential and carries the configured headers, and the bucket's versioning status is read by a hardened XML parser, whatever its namespace prefix, declarations or attributes.

A start that failed before the engine identity check (a missing image, or an engine API that never came up) has no results to summarize. It no longer reports `summary generation encountered issues`; it prints `Auto-results: no run was submitted; no results were produced.` and records `lifecycle.summary` as not started. On `spt run write-verify` and `read-verify` such a start still exits 1, and its final error no longer carries the `graceful shutdown: …` and `summary generation: …` clauses. A start the engine identity check rejected, or whose scenario submission the engine refused after the check passed, still writes its run summary, as before. A launch the engine accepted, including one kept only for cleanup, still requests shutdown on every host.

- **Early stop of a duration DELETE** — A duration DELETE stopped by its failed-object budget names the budget as the cause, instead of reporting that its inventory ran out and advising `--seed-objects`. - **Steady-state window warning after a failed start** — A step that fails to start, for example with an unknown storage driver type, also logged, from v5.17.0 on, a steady-state window `IndexOutOfBoundsException` warning (`Steady-state window closed by shutdown could not be measured` and `failed to close the steady-state window`). It no longer does. The start failure's ERROR lines and exit code 1 are unchanged, and the step's steady-state window now closes as not reached with cause `shutdown`. Working runs are unchanged.
- **DELETE verification against a target that drops its `HEAD`s** — `spt run delete --validate-inventory` and DELETE post-verification no longer send a `HEAD` storm when every `HEAD` fails at once, for example when the target closes or refuses the connection. The verifier used to retry such an object every 10 ms for the whole `verificationTimeoutMillis` (default 30 s), each `HEAD` on a new connection: against a loopback target that closes every `HEAD`, more than 1,500 `HEAD`s per object in the 30 s window, now under 40. The first retry pass still follows the complete pass at once; later passes wait 10 ms, doubled per pass up to 1 s. Near the timeout the wait shortens, to no less than 10 ms, so the next pass starts about one pass duration before the timeout and an object that settles late in the window is checked again before it. The timeout keeps its meaning, and a phase that cannot resolve every object fails at it. A typo such as `hots` used to start the engines in bridge mode without a warning. `host`, `bridge` and the default behave as before. `spt verify` still accepts only exactly `host` or `bridge`. **Compatibility:** an explicit empty value and a bad value given with `--generate-only` are now refused; `Bridge`, `BRIDGE` or ` bridge` with `--interfaces` or `--host-interfaces` is now refused, as `bridge` already was, and those spellings now print the bridge warning on remote routes too.
- **Port checker engine detection** — The CLI's port checker now recognises a running engine by its own API responses, not by the Jetty error page (the Docker container lookup is unchanged): its `/metrics/json` probe accepts the current `metrics_schema` payload, and its `/run` probe accepts the engine's "Invalid run ID format" answer. It used to match a current engine only through the "Powered by Jetty" footer (and on Jetty 9.4 the servlet row) of the error page, so an engine on a newer Jetty, or one that hides its Jetty version there, would not have been recognised as SPT. A generic Jetty 400 page on `/run`, and an empty body (`[]`, `[ ]` or `null`) on `/metrics/json` or `/metrics`, no longer count as SPT: no engine sends them, and any other service that did was labelled an SPT service and, without an interactive prompt or with `--force`, sent `DELETE /run`. A JSON body with the fields `successCount`, `failCount`, `bytesCount`, `concurrency`, `opType`, `opsPerSec`, `meanLatencyMicros` or `lastUpdateTimeISO` on either metrics path, or a `200` JSON answer with `runId`, `status`, `startTime` or `startTimeISO` on `GET /run`, no longer counts as SPT either. Every engine from v5.0.1 on is still detected.

It used to run as JavaScript and stop on a JavaScript syntax error.   - A count-based read from an items file with fewer items than engines. It used to hang.

Its dispatch was refused, but nothing settled it. At the head of the driver's dispatch queue, such a part kept the dispatcher busy on one CPU offering it again, and the operations queued behind it did not run, at least while the abort's result was being published and, once the abort had ended, until something else let the part through. On `s3` and `s3-rdma` with a NIC set, a part whose connection arrived while the abort's result was being published, or after the abort had ended, gave back its connection and permit but stayed queued in the step's operation lifecycle until the step stopped. It needs a part still queued when the abort ended, which a full input queue (`driver-limit-queue-input`) makes more likely, with any number of parts against the part window. It was reproduced in unit, stress and loopback tests, not in a step: among them a part that a successful sibling queued just before the abort, and a two-part upload on two NICs.
- **Multipart writes with `load.op.retry=true`** — A multipart write with `load.op.retry=true` no longer stalls after a part fails. A failed upload is now retried as a whole, from a new initiation with all its parts, as documented. The part used to be retried as an extra part of its upload, which then never completed and held the step until its stop. An upload aborted after a part ran out of retries now ends with the status of the first part that did, including in the operation trace, whether the abort is answered, refused or cannot connect, so it is retried only when the part's failure is transient: a part the target refuses for good, for example with 403, fails its upload once. It used to end with `FAIL_UNKNOWN` after an abort the target answered (on `s3`, also one it refused), and otherwise with the abort's own failure, such as `FAIL_IO`. On `s3`, a failed initiation now keeps its own status, so a throttled one (503) is retried too; on a connection's first initiation it used to be reported as `RESP_FAIL_NOT_FOUND`, which is never retried.
- **Stale upload ID on a reused `s3` connection** — On the `s3` driver, a multipart initiation answered without an upload ID no longer takes the previous upload's ID on a reused connection. A successful answer without an ID is now `RESP_FAIL_NOT_FOUND` on every connection, as it already was on a connection's first initiation, instead of sending its parts to the previous upload. A failed initiation keeps its own status and no longer stores the previous upload's ID or writes an `INIT` row with it to the multipart log (`parts.upload.csv`, fetched as `<stepID>.multipart.csv`). Real S3 targets answer each successful initiation with its own ID, so only a target that leaves it out, or a failed initiation on a reused connection, was affected.
- **Credentials in the engine's `cli.args.log`** — The engine's `cli.args.log` now masks as `***` the values of `--storage-auth-uid`, `--storage-auth-secret` and `--storage-auth-token` (and its alias `--atmos-subtenant`), and of the `Authorization`, `Proxy-Authorization`, `Cookie`, `x-amz-security-token` and `X-Auth-Token` headers set with `--storage-net-http-headers-<name>`, matched in any case. The file used to hold every argument as given. A node also serves that file at `GET /logs/<step_id>/Cli`. Argument names, their order and every other value are unchanged, an empty value or an argument without `=` is logged as given, and the run still uses the real values. Values in `storage.net.http.uri.args` are not masked. Only arguments on the engine's own command line reach this file (the jar, `run.sh`, `docker run <image> ...`); `spt run` passes no credentials there. The step `config.yaml` now also masks those five header values under `storage.net.http.headers`, wherever they were set (command line, scenario `config` block, posted defaults or a defaults file) and for every run, `spt run` included; it already masked the credentials.
- **Credentials in a node's `GET /config`** — A node's `GET /config` now shows the storage credentials (`storage.auth.uid`, `.secret` and `.token`) and the values of the `Authorization`, `Proxy-Authorization`, `Cookie`, `x-amz-security-token` and `X-Auth-Token` headers under `storage.net.http.headers` as `***`, in YAML and JSON, as the step `config.yaml` does. It used to return them in clear. An unset or empty value and every other value are unchanged, the node keeps the real values, and `GET /config/schema` is unchanged. SPT itself does not read `GET /config`. A client that posts a `GET /config` response back to `POST /run` as `defaults` now sends `***` as those credentials and headers, so it must set them itself.
- **Completion of multi-host steps with several operation types or differing limits** — On more than one host, the CLI now shows a step with several operation types as completed, and prints "Test COMPLETED", only once every operation type has completed on at least one engine. It used to do so once any one operation type had. Every `spt run` mixed workload on several hosts is such a step. Separately, when the engines of one step report different limit types (for example one engine an operation count and another no limit), the CLI now treats the step as having no limit and waits until every engine has completed it. It used to take the limit of whichever engine it read first, so it could show the step as completed while an engine was still running. Only weighted, pipeline and appended mixed scenarios run straight on the engines can report different limits; the scenarios `spt run` generates never do.
- **Shipped example scenarios** — The example scenarios shipped in the image under `/opt/spt/scenarios/js`: `types/weighted.js`, used by the Compose example's `spt-weighted` service, `rampup.js`, `parameterized/s3-multiuser.js`, `system/circular_append_test.js`, `system/circular_read_limit_by_time_test.js`, `system/read_verification_after_circular_update_test.js`, `system/weighted_load_test.js` and `system/tls_read_using_input_file_test.js` no longer stop on an invalid configuration path or a syntax error. `backward_compatibility.js` no longer stops on an invalid configuration path either: it now uses current configuration names, since the Mongoose 3/4 names it used are not aliased.
- **`s3-aws` UPDATE** — An `s3-aws` UPDATE writes the object again, as before 5.9.0, instead of failing every operation with a copy from a missing object. Each UPDATE of an item named `/<bucket>/<key>`, as an `s3-aws` write's items file records it, or of an object listed from an item input path, was sent as a copy from an object named after the bucket in the driver's own bucket, and failed with not found. It is now one PUT of the whole object with the item's current content, counted as the item's size, which matches the `s3` driver's default UPDATE. Configured ranges (`item.data.ranges.random` or `item.data.ranges.fixed`) are ignored, as they were before 5.9.0. No `spt run` workload runs an UPDATE; an archived `UpdateLoad` in `spt replay`, an engine `--load-op-type=update` or a direct scenario reaches it.
- **Verification steps that ended between two status polls** — When the live status of an `spt run read-verify` or `write-verify` never showed a LIST, CREATE or verification step that the engine reports as completed, but showed another step of the run, the run now fetches that step's files and finalizes the results from them; with `--allow-empty-selection`, a missed verification step was already fetched. The `Auto-results: fetching N step(s)` line now counts and names the steps actually fetched, these included, and is no longer printed when a verification run fetches nothing. Without `--allow-empty-selection`, when the missed step is the verification step, the results directory now holds its files, `index.json` and an Integrity section in the summary, where it used to hold only run metadata. A run in which no step was seen at all is unchanged.
  - A `read-verify` without `--allow-empty-selection` whose step files prove the selection empty now reports "verification selected zero objects", exit 1, where it could report missing runtime evidence or a missing LIST metrics file. With the flag, such a clean empty selection now passes, where a missed LIST step failed it with exit 1.
  - A missed verification step that had objects to verify still exits 1 without `--allow-empty-selection`, and the run now says that the verification step completed but its live corruption count was not observed. With the flag, its reason ("verification READ step could not be identified") and exit codes are unchanged.
  - When the verification step was seen but the LIST or CREATE step was missed, a run that verified every selected object now exits 0, where it failed with exit 1. Corruption still exits 20, now without the secondary finalization error about the missing LIST or CREATE files.
- **Verify runs with unverified objects** — An `spt run read-verify` or `write-verify` that failed to verify some of its selected objects, for example because their GETs were answered 403 or 404, now exits 1, as `S3_INTEGRITY.md` documents; it exited 0. The reason names how many of the selected objects verified and how many remain unverified. An empty selection, `--allow-empty-selection` and the corruption exit 20 are unchanged.
- **Multipart completion answered 200 with an error** — The `s3` and `s3-rdma` drivers now treat a multipart completion answered `200 OK` with an S3 `<Error>` body as failed, abort the upload, and count it as a failure. Only transient error codes (`InternalError`, `ServiceUnavailable`, `SlowDown`, `RequestTimeout`, or a missing, empty or truncated code) are retried under `load.op.retry=true`, as a whole upload. Before, it counted as a written object and the upload was left open, so a later read of it failed. Each step's `errors.log` names each such error code once, for at most 16 codes (once per sub-load in a weighted, mixed or pipeline step); a missing code is logged as `(missing)`, and a code that is not a plain S3 code name of at most 64 characters as `(unreadable)`. These still count as written, as before: a `200` completion with an empty or whitespace-only body, an `<Error>` root more than 4 KiB into the body, and an `<Error>` root after an XML comment or a byte-order mark. The `COMPLETE` row in `parts.upload.csv` is still written for a failed completion.
- **Copy answered 200 with an error** — A copy (a CREATE with `item.input.path`) on the `s3` driver, and one `s3-rdma` sends over HTTP, that the target answers `200 OK` with an S3 `<Error>` body now fails instead of counting as written, and counts no bytes. The error code decides the status as for a multipart completion answered so: a transient code (`InternalError`, `ServiceUnavailable`, `SlowDown`, `RequestTimeout`) or a missing, empty or truncated one gives a service failure (`RESP_FAIL_SVC`), which `load.op.retry=true` retries, and any other code a client failure (`RESP_FAIL_CLIENT`). This holds however the body is framed: chunked, by `Content-Length`, or ended by the connection's close. Each step's `errors.log` names each such copy error code once, for about 16 codes (a few more when copies on several connections fail with new codes at the same moment); a missing code is logged as `(missing)`, and a code that is not a plain S3 code name of at most 64 characters as `(unreadable)`. These still count as written, as before: a `<CopyObjectResult>` body, an empty or whitespace-only body, an `<Error>` root more than 4 KiB into the body, and an `<Error>` root after an XML comment or a byte-order mark. A copy answered with a failed status is unchanged. Since the initial import.
- **Multipart aborts at the end of a step** — On the `s3` drivers, the abort that follows a failed multipart completion near the end of a step is now read to its answer, within its own time bound (5 s from when the abort was sent, so that a worker's stop, with every abort sent before it, stays inside the entry node's 10 s RMI response timeout), before the driver's connections close. Before, an abort answered late was logged as "Response timeout", recorded as failed, and held the step's close for `storage.net.timeoutMilliSec` (30 s by default), or hung the scenario with `storage.net.timeoutMilliSec=0`. A step that ended by its count right after such a completion could also stop its connections before the abort was sent: the upload stayed open on the target and, in an integrity run, was recorded `failed_orphaned`. The wait now falls inside the step: when such an abort is pending, whole-step `StepDuration`, `TPAvg` and `ConcurrencyMean` include it. Steady-state figures do not change. The driver's close no longer waits without bound for such an abort: it waits at most twice `storage.net.timeoutMilliSec` plus 1 s (60 s when the timeout is 0), then records the upload `failed_orphaned` in `multipart.lifecycle.csv` and logs one warning with the count. A multipart completion or abort that fails with `FAIL_UNKNOWN` before it has a connection now settles its upload as a `FAIL_IO` one does: the completion's upload is aborted, and the abort's upload is recorded `failed_orphaned`. On the HTTP drivers (`s3`, `s3-tables`, `swift`, `atmos`), a synchronous control request (the bucket check, versioning check and bucket creation, listings, delete verification, and the aborts above) whose connection closes without a response now ends at once and logs "Connection closed before the response"; before, it waited `storage.net.timeoutMilliSec` and logged "Response timeout".
- **Multipart writes and multi-range reads at a stop** — A step with multipart uploads or multi-range reads, on the default route or with `storage.net.interfaces`, now ends promptly when it stops with such operations in flight: at its time limit, the case most runs hit, or at a count or size limit, a failure threshold or an interrupt. An upload or read whose next part, next range, completion or abort the stop refused used to wait out `load.op.wait.limit` (30 s by default) before it was reported unresolved, which lowered the step's whole-run rate, bandwidth and concurrency in `metrics.total.csv`. Such operations are now reported unresolved at once, and every upload left open is counted as unresolved in `operation.lifecycle.csv`, including one whose initiation completed after the stop, which used to count as unattempted. Steady-state figures do not change. Known issue: a stopped step can leave the multipart uploads it had in flight open on the target. SPT reports them as unresolved but neither completes nor aborts them; remove them with a bucket cleanup. For driver authors: `CoopStorageDriverBase` adds the protected final methods `beginDispatchOrSettle(O)`, `settleRefusedDispatch(O)`, `withDispatchAdmission(BooleanSupplier, O)` and `withDispatchAdmission(BooleanSupplier, DispatchRefusal<O>)`, and the protected interface `DispatchRefusal<O>`. A driver extension that declares a method with one of these signatures no longer compiles; rename that method.
- **Refused reads with `item.data.verify`** — With `item.data.verify` on, a READ the target refuses (for example 403, 404 or 503 with an error body) on the `s3`, `s3-rdma`, `s3-tables`, Swift and Atmos drivers now ends with its HTTP status (`RESP_FAIL_AUTH`, `RESP_FAIL_NOT_FOUND`, `RESP_FAIL_SVC` and so on) instead of `RESP_FAIL_CORRUPT`, so it no longer counts as corrupt. The error body was verified as item data and failed. A refused verified read now counts no bytes; before, it counted the body's bytes up to the first one that failed verification: usually none, and part or all of the body when the item was smaller than it. A 2xx body that fails verification is still `RESP_FAIL_CORRUPT`. Under `load.op.retry` a refused 5xx read is retried again, so a run that failed on a transient 5xx can now succeed and exit 0; a read split into ranges (`item.data.ranges.threshold`) whose range is still refused with a 5xx after its three retries is then retried as a whole, so request counts can grow. Runs with verification off, and verified runs with no refused reads, are unchanged.
- **`--force` at a local port conflict** — `spt run --force` and `spt replay --force` (and the interactive force choice) at a local port conflict no longer remove a container that only exposes the API port, or maps a different host port to it, and no longer send the SPT stop request to a non-SPT service on the port. Only a running or paused container that publishes the host port over TCP is taken as the port's holder; with none, the run reports `No containers found using port N - service may not be containerized` and removes nothing.
- **Run summary totals when a step's metrics are missing** — When a step in the fetched results has no `metrics.total.csv` because it was not fetched, the run summary no longer prints zero, or the sum of the other steps, as the run total. With no phase's totals available, including a run whose expected steps are all absent from the fetched results, the console prints `Totals: unavailable (no phase has metrics)` instead of `Totals: duration 0s, data moved 0 B`, and `Run Totals` in the summary file shows `unavailable` for the duration, data moved and failed requests. With only some phases' totals, the sums carry their coverage before the colon, for example `Totals (2 of 3 phases): duration …, data moved …` and `Run Totals (2 of 3 phases)`, which always shows the failed requests as counted phases only and names the phases not counted. The phase tables now show such a phase as a row of `—` instead of leaving it out. A tool that reads the `Totals: duration` line no longer matches either form. An expected step that is absent from the fetched results while other phases were counted leaves the totals as before, since such a step need not be a missing phase (for example the single pipeline step of `spt run mock --cleanup`, or a cleanup with no work); the summary file still lists it under `Missing steps`. A run with at least one phase counted and no fetched step missing its totals prints exactly what it did before. A totals file that was fetched but cannot be read still stops the summary, as before.
- **`s3-aws` 5xx and error-body failures** — An `s3-aws` request answered 5xx or with a `RequestTimeout` error code (after the AWS client's own retries), or a copy or multipart completion answered `200 OK` with an S3 `<Error>` body, is now recorded as a service failure (`RESP_FAIL_SVC`) or, for a 200 whose error code is not transient, a client failure (`RESP_FAIL_CLIENT`), instead of `FAIL_UNKNOWN`. For 5xx and `RequestTimeout` answers only the failure status changes, in op traces, logs and the `error` column of `multipart.lifecycle.csv`; counts and `load.op.retry` are unchanged, since both statuses are retried. A copy or multipart completion answered 200 with a non-transient error code (for example `AccessDenied`) is no longer retried by `load.op.retry`, as a refused request is not; a transient or missing code is still retried. A 504 now gives a service failure on the transfer client, which cannot tell it from a 500; the ordinary client (standalone DELETE, exact-version requests) still gives a timeout (`FAIL_TIMEOUT`).
- **Retried part of a split read or write** — A read split into ranges (`--part-size`, or engine `item.data.ranges.threshold`) on the `s3` and `s3-rdma` drivers no longer counts the bytes of a failed range attempt when the range is retried. With `item.data.verify` off, a range refused with an error body, or cut off mid-body, then answered, used to add the error body or the partial bytes to the step's bytes and bandwidth. With `item.data.verify` on, a refused range already counted no bytes, but a range cut off mid-body made its read fail as corrupt on every retry; it now succeeds when the retry returns correct data. A retried range also lost its time-to-first-byte sample; it now records one. On the `fs` driver, a part of a split write retried after its failed attempt had written some bytes now writes the whole part; it used to stop short by as many bytes as the failed attempt had written, and report success. Runs with no failed part are unchanged, and so is the accounting of a successful multipart upload on the `s3` drivers; a failed part attempt's trace can now show fewer bytes than before. For driver authors: `DataOperationImpl` adds the public final method `resetAttemptProgress()`. An extension subclass that declares a method with that signature no longer compiles; rename that method.
- **Path item input with foreign keys on the `s3` driver** — A path item input (`item.input.path`) on the `s3` driver, and drivers that inherit its listing such as `s3-rdma`, no longer fails on a listed key that SPT did not generate, such as a folder marker `dir/` or `photo.jpg`: such a key is read, deleted or copied with data offset 0, as on `s3-aws` and `fs`, and each listing logs one warning with the number of such keys and the first one, never a line per key. Since 5.14.0 the step did nothing and exited 0; since 5.17.0 it exited 1 before any object request, or, when the first such key was on a later listing page, exited 0 after acting only on the earlier pages. With `item.data.verify` such a key is still refused, and the message now says that verification needs keys SPT generated. A foreign name made only of id digits, such as `photo`, still parses as an id. On `s3` a listed key is sent as written except for `?`, `#` and a space, which are now percent-encoded (see **`s3` object keys with `?`, `#` or a space**): a key with `%XX` is still sent as written, so a target that decodes the path can read another object, and with `storage.object.versioning` a key with `~` is read as a key and version ID; `s3-aws` encodes keys. Only an `item-input-path` engine override or a direct scenario reaches it.
- **`--skip-image-pull` message and docs** — With `--skip-image-pull` or `SPT_SKIP_IMAGE_PULL=true`, `spt run` and `spt replay` now print `Skipping the engine image pull when the image is present; a missing non-dev engine image is still pulled before the engine starts.` instead of claiming the cached image is used, and the flag help, `cli/README.md` and `cli/docs/SPT_SYNTAX.md` say the same: a missing non-dev engine image is still pulled, and `spt_dev` images are never pulled. The multi-host preflight and `spt verify` now log `Docker image not found locally; pulling despite skip` in `spt.log` when they pull a missing image with the skip set. Pull behaviour is unchanged.
- **Ctrl-C while `spt replay` connects** — Ctrl-C or SIGTERM during the host connection phase of a remote or distributed `spt replay` (ssh, preflight checks, an image pull or `--force` cleanup) now cancels it, as on `spt run`. The replay used to finish connecting before it stopped.
- **Totals of an interrupted distributed run** — A distributed run stopped mid-step by Ctrl-C (which sends the entry engine `/shutdown`) or by `DELETE /run` now keeps its totals: the entry engine writes the stopped step's `metrics.total.csv`, `metrics.steady.total.csv` and `result.xml`, as after an uninterrupted step. The stop left the step's interrupt set, so the entry engine skipped them, and the CLI reported `failed to retrieve required metrics.total.csv for all steps` and a summary of zero. The entry engine's JSON metrics also keep the stopped step's final entry, and its Prometheus series for the step are removed. The stopped step's close does the same cleanup work as an uninterrupted step's close, and still publishes the merged `operation.lifecycle.csv` and the worker's node files. A stop during a step's last moments still ends the run at that step, as before. A single-engine run and an uninterrupted run write the same files as before. An engine killed outright still writes no totals.
- **Headless runs** — A local headless run, passing or failing, no longer ends with a false `Error reading container logs: context canceled` line and a `file already closed` trace error (since 5.14.0).
- **Multipart response bodies bounded** — On the `s3` and `s3-rdma` drivers, a multipart initiation, completion, or abort sent as the operation (after a part ran out of retries) that a target answers with a body over 64 KiB no longer grows client memory without bound: only the first 64 KiB of the body is read, and each engine's driver logs one warning to `errors.log`. The abort SPT sends after a failed completion is not covered. An initiation whose upload ID is not in those 64 KiB fails as not found, as one with no upload ID does, and a completion is still checked for an S3 error in its first 4 KiB. Each chunk of a multipart response no longer allocates a buffer it throws away. Responses up to 64 KiB, which every normal initiation, completion and abort is, are read as before; LIST responses are unchanged.
- **Numeric URI arguments, headers and tags** — A number or boolean given for a URI argument (`storage.net.http.uri.args`), HTTP header (`storage.net.http.headers`) or S3 object tag (`storage.object.tagging.tags`) through `spt run --engine-override` or a `POST /run` defaults document no longer fails the step with `ClassCastException … cannot be cast to class java.lang.String`. URI arguments and headers are sent as typed (`--engine-override storage.net.http.uri.args.tid=0012` sends `tid=0012`), and tags as the text `s3-aws` already sent (`7`, `true`, `1000.0`). With the Netty HTTP drivers (`s3`, `s3-tables`, `s3-rdma`, Atmos, Swift), a list or map URI argument or header, or a header with no value, now fails the step with a message that names it instead of a cast or a `NullPointerException`, and so does a list or map tag with `s3`, `s3-tables` and `s3-rdma`; `s3-aws` and `fs` take these values as before. A number or boolean given either way for `load.step.id`, `run.comment`, `storage.integrity.mode`, `storage.integrity.algorithm`, `storage.integrity.input.provenance` or `storage.integrity.input.expectedProducerId`, which failed every run, is refused with a message that names the setting and says to quote the value; other text settings behave as before. Values that worked before send the same bytes, though a step's `config.yaml` now records a number or boolean given for these three maps as quoted text (`X-Id: "007"`), with every driver; a whole-map override such as `storage.net.http.uri.args={tid: 0012}` keeps its YAML meaning, so quote the values in a map literal.
- **A stopped step ends sooner after its limit** — When a step stops, the engine settles every operation still queued before dispatch as unattempted, and it now does so in fewer passes over the queues: each queued operation is visited once by the storage driver and is not settled again by the step. At the shipped `driver-limit-queue-input` of 1,000,000, a stopped step can hold one to two million queued operations (two million for a multipart write), which took several seconds after the last request. That settling now takes much less time: in a 20 s time-limited write against a loopback S3 target, a stopped multipart step (about two million queued operations) ended about 2.7 s after its limit instead of about 7.2 s, and a single-part step (about one million) about 0.8 s after it instead of about 2.9 s. So the step ends sooner and its whole-step duration and averages include less of this bookkeeping; a stopped multipart write at the default queue limit still spends a second or more on it. Steady-state results and the `operation.lifecycle.csv` counts are unchanged. Since 5.15.0.
- **File system listing** — Reading a listed `fs` path with data verification no longer reports every SPT-written file as corrupt, and an items file written from such a listing now holds each SPT-written file's real offset instead of 0. The offset is now taken from the file name, not the full path; a file SPT did not write still gets offset 0, unless its name after the prefix happens to be a non-negative number in the naming radix (such as `readme` in radix 36). Affected all releases.
- **`--auto-terminate-seconds` stops the run** — With auto-results on (the default), `spt run` and `spt replay` `--auto-terminate-seconds` stop the run again at the deadline, a regression since 5.14.0: the CLI let the step run to its natural end and then exited 1. At the deadline the CLI now stops the run through the engine API (`DELETE /run` with the run's ID), fetches its artifacts, then shuts the engines down if `--shutdown-on-complete` is set; with `--auto-results=false` it ends the run through shutdown and container stop, as before. It exits 0 when the run was healthy up to the deadline and the stop is confirmed, and prints `Auto-terminate: the run was stopped at the N s deadline`. It exits 1, with an error that names auto-terminate, when the stop request fails or the run reports no terminal state after it, since the results may then be partial; with `--shutdown-on-complete` the CLI then tries the shutdown, which can still confirm the stop. A run that had already ended at the deadline, or that ended on its own while the stop was in flight, says so instead of saying it was stopped; one that had already ended takes the normal exit rules. A step that failed before the deadline still exits 1. For `spt run`, a run whose every request failed before the deadline also exits 1, and a DELETE or verification workload stopped at the deadline exits 1, because it did not complete. Ctrl-C keeps its exit code and messages. The TUI waits for the stop attempt, for a bounded time, before it closes. The deadline starts after the CLI has connected to the hosts and covers engine start-up, launch and the run; in headless mode a deadline reached before the workload is submitted now ends the start with an error that names auto-terminate, instead of the start step's own timeout text.
- **Verified split read of an updated item** — With `item.data.verify` on, a read split into ranges by engine `item.data.ranges.threshold` (from the CLI, `--engine-override item.data.ranges.threshold=N`) on the `s3` and `s3-rdma` drivers no longer reports the ranges of an item whose ranges were updated as corrupt (`RESP_FAIL_CORRUPT`) when the target holds the updated data. Each range is now verified as the same bytes of a whole read are, against the updated data where the item's update mask says so; before, it was checked against the item's data before the update, so a range that held stale data for an updated part of the item passed; such a range is now reported corrupt, as a whole read of it always was. Reads of items with no updated ranges, whole reads and unverified reads are unchanged. The defect dates from 5.6.0.
- **`s3-rdma` copies are HTTP server-side copies** — An `s3-rdma` copy (a CREATE with `item.input.path`) is now always an HTTP server-side copy. A copy at or above `storage.rdma.thresholdBytes`, or any copy with the threshold at `0`, used to be sent as one request with both the copy source and an RDMA token, after the driver generated and registered a payload for it, so the target stored generated data, or the copy failed (`RESP_FAIL_SVC` or `RESP_FAIL_CORRUPT`) though it was made, since v5.2.0. A copy now sends no RDMA token and prepares no RDMA buffer. Copies no longer count in the RDMA data path counters, `http_below_threshold` or `http_rdma_unavailable`, and a copy below the threshold no longer logs the below-threshold warning. Plain CREATE and READ routing is unchanged.
- **Last log lines at engine exit** — The engine could exit before writing its last log lines, losing a scenario's or argument's error message and, for an engine run directly (`java -jar spt.jar`, `run.sh` or the image with `--run-scenario`), the `result.xml` row, `metrics.total.csv` and `errors.log` lines and the final console summary. The shutdown hook now drains the engine's log queue. A run that ends with a log backlog, for example with operation tracing on, now waits for it to drain at exit, for at most 10 s after the engine's services have closed; lines still queued after that are lost, and so are lines a reader that has stopped reading the engine's output cannot take. A `docker stop` with its default 10 s grace can end that wait early. Exit statuses are unchanged, the engine prints no new lines at exit, and a run whose log queue is empty at exit exits as fast as before. Affected all releases.
- **Keys with an empty segment kept whole** — A listed or items-file key with an empty segment before its last segment, such as `/k2` or `a//b` in bucket `pp`, is no longer collapsed. The `s3` and `s3-rdma` drivers requested the collapsed key (`GET /pp/k2` for `/pp//k2`), so a path-input DELETE could delete a different object, such as `k2`, and report success (since 5.10.1); items files on every driver wrote the collapsed name, so a later step read back from one could act on another object. Names without such a segment are unchanged. A DELETE on the `fs` driver whose name already holds its path, as on a retry (`load.op.retry`), now deletes that file; it used to address the path twice (`<dir>/<dir>/f`).
- **DELETE verification of large objects** — On the Netty S3 drivers, `--validate-inventory` pre-validation no longer fails for objects of 2 GiB or more, and post-verification no longer reports a surviving object of that size as unresolved instead of still present. A `HEAD` response's size no longer counts against the control-response limit. Affected since 5.15.0.
- **RDMA pool sizing under the image-pull skip** — With `--skip-image-pull` or `SPT_SKIP_IMAGE_PULL`, RDMA pool sizing now pulls a missing non-dev engine image, as the engine launch does, instead of leaving that host unsized at the default direct-memory limit. A dev image is still never pulled, and `spt.log` notes that the pool-sizing probe may pull the image despite the skip. Since 5.17.0.
- **Attach runs no longer pull the image on attached workers** — With `--attach-existing`, `spt run` and `spt replay` no longer check or pull the engine image on attached worker hosts, where they start nothing. A missing image there was pulled (`--skip-image-pull` and `SPT_SKIP_IMAGE_PULL=true` skip only the pull of an image that is present), or, for a dev image, refused with advice to distribute it to that host; a failed pull refused the host, which failed the start unless `--min-hosts` allowed fewer hosts. The engine identity check still compares the build of each attached worker that takes part in the run, and the entry host and every host of a run without `--attach-existing` are checked as before.
- **Control responses** — Bucket checks, item-input listing pages and other control requests on the Netty HTTP drivers (`s3`, `s3-rdma`, `s3-tables`, Atmos and Swift) now refuse a response body over 16 MiB with one warning naming the cap, the method and the URI, instead of buffering up to 2 GiB; the request then fails as one left without a response does. The `s3-tables` read of a table's metadata file takes up to 64 MiB. `HEAD` responses are not capped. Responses under the cap are unchanged.
- **File system copy from a listed path** — On the `fs` driver, a copy from a listed path (`--item-input-path`) now copies the files of the listed directory, and a copy from an `fs` items file with `--item-input-path` copies each item, instead of failing every item. A listing covers the regular files of one directory level and skips subdirectories (see **File system listings skip subdirectories**); nested directories are copied with one step each. A `create` from an `fs` items file without an input path now writes its generated items instead of failing. Each item lands under the output path with the source file's full path, as with `s3`: `/src/dir/f0` is written to `/dst/src/dir/f0`, the name the step's results already recorded, and missing directories are created. A `create` whose output directory is removed during the run now recreates it instead of failing each later item. The copy-mode design notes no longer say that an items file alone enables copy mode: without `--item-input-path`, a `create` writes generated data.
- **`--version` writes nothing** — `--version` and `-v` on the engine, the image and `run.sh` no longer leave an empty `${ctx:home_dir}/log/${ctx:step_id}` directory in the working directory, and no longer print Log4j status lines on stderr. The version output is unchanged. An extension's log lines from class initialization on this route now behave as on `--help`: errors go to stderr, lower levels are dropped.
- **`s3` object keys with `?`, `#` or a space** — The `s3`, `s3-rdma` and `s3-tables` drivers now percent-encode `?`, `#` and a space in object keys (as `%3F`, `%23` and `%20`) and sign the encoded path, under SigV2 and SigV4 where the driver supports them (`s3-tables` signs SigV4 only). A key with `?`, such as one read from an items file, a listing or a `--prefix`, was sent as a query, so a READ or DELETE acted on another object and counted a success: a DELETE of `weird?x=1` removed `weird`, and `spt run write --prefix 'run?x/'` wrote every object to the key `run`. A key with a space failed before it was sent. Every object request sends the encoded key, including multipart, tagging, range and versioned requests, and the `x-amz-copy-source` header of a copy now carries the encoded source key. Every other character is sent as before, so a key with SPT's generated name sends the same request. A `%XX` in a key is still sent as written, not encoded again: a target that decodes the path reads `a%2Bb` as `a+b`, and so another object. A target that checks SigV4 strictly does too, since `%2B` is SigV4's own form of `+`, and answers 403 for an escape SigV4 would not produce, such as `r%41` or a lowercase `a%2bb`. The standalone DELETE and its verification HEAD (`spt run delete`) already encoded keys, `%` included, and are unchanged. Item names, items files, the operation trace and the multipart record keep the key as written. A key with `?` and another reserved character, such as `weird?x=1`, may now fail with 403 on a target that checks the signature strictly, instead of acting on another object. A name such as `key?versionId=abc` now names that key, where it used to select version `abc` of `key`. For driver authors: `HttpStorageDriverBase` adds the protected method `requestPath(String)`, which the object request builders apply to the path before its query; the standalone DELETE, listings, bucket requests and Swift's multipart builders don't. The default returns the path unchanged. An extension driver that already declares `protected String requestPath(String)` now overrides it and changes its request paths. Affected all releases.
- **Copy into its own source path** — A copy-mode step whose item output path equals its item input path now fails at start (exit 1), before any engine starts and before any object is copied, instead of copying every object onto itself and counting each as a success; Copy Mode always listed this layout as unsupported. Leading and trailing slashes don't matter: `/src`, `src` and `/src/` are the same path. An output path under the input path logs one warning at start, because the listing also returns keys already under it, such as an earlier run's copies, and those are copied onto themselves; a first run into an empty prefix under the input path copies correctly, as before. Target-bucket setup still runs first, as before: an S3 step sends one `HEAD` for the output bucket and creates the bucket if it is missing, then is refused. A weighted or pipeline step also lists the input path of each configuration before the one refused (its base, and in a weighted step every earlier context); no object is written. Only a constant output path and a listed `item-input-path` are checked, not an output path expression, an items file, or a pipeline sub-step after the first, which reads the results of the one before. A mixed step is never checked: its listed input is only its GET and STAT pool, and its PUTs name new objects, never a listed one. Only an `item-input-path` engine override or a direct scenario reaches it. This applies to every driver but `fs`, which has its own rule below.
- **File system copy into its own source directory refused at start** — On the `fs` driver, a copy-mode step whose item output path is its listed input directory or one of that directory's parents, such as `--item-input-path=/data/src` with `--item-output-path=/data` or `/data/src/`, now fails at start (exit 1). Such a copy opened each listed source file as its own destination, emptied it, and then never finished. The input path is taken as the listing names its files, with doubled and trailing slashes dropped and a relative input path made absolute against the working directory, so `data//src`, `//data/src` and a relative `data/src` are refused into their parent too. The output path is compared as written, as the driver compares it with each listed name, and `.` and `..` segments are compared as written on both sides: a relative output path never holds a listed name and copies elsewhere, so it is not refused. An output path under the input path is not refused or warned about, because an `fs` listing does not descend into it. An items file, an output path expression, a pipeline sub-step after the first and a mixed step are not checked at start, the same as on other drivers.
- **Unresolved operations in the run summary** — The `spt run` summary now adds a warning for each step that ended with operations unresolved at the stop, counted neither as successful nor as failed, from the step's `operation.lifecycle.csv`. For example: `Read: 1845 operations unresolved at the stop, in neither Success nor Failed; Data Moved can include their bytes (operation.lifecycle.csv)`. Time-limited split reads and multipart writes can show this line, as can requests that outlive `load.op.wait.limit`. Steps that share a phase label are named by step ID as well. DELETE and partial READ steps keep their own counts and get no such line. Tables, `result.xml`, metrics and exit codes are unchanged.
- **Next step after a signal** — A multi-step scenario stopped by a signal (Ctrl-C on a direct engine run, or `docker stop`) no longer starts its next step before the engine exits. It could send that step's first requests to the target, or, in a distributed run, a worker could keep running it after the entry had exited. Affected all releases. A node run ended by a signal now reports `STOPPED` on `/status` once its scenario has ended, or `FAILED` for a step's own terminal failure, never `COMPLETED`, and a worker that refuses a step this way writes no result files for it, and a step stopped this way during its start no longer reports a failed close over the slice files it never wrote. Two cases still fail their close: a step with a NIC set whose slice start the signal cut short, and a distributed standalone DELETE that only some of its slices started, since some objects may already be deleted.
- **Distributed time limit** — A distributed step with a time limit no longer runs a multiple of its limit when its slices (one per node, plus the entry's own) outnumber the threads polling them, which is the entry's CPU count and at least 2 (for example 3 nodes from a 2-CPU entry, or 8 nodes from an 8-CPU entry). Such a step used to run its limit once for each round of polling, so 9 nodes from a 2-CPU entry ran 5× its limit, with that many more operations. An affected step now stops polling at its limit. A slice still waiting for a poller then gets its only poll, so its terminal failure still fails the run. For a node that does not answer, that poll can add an RMI timeout: up to 10 s for a reply on an open connection with the shipped launch settings, or the handshake timeout on a new connection: 10 s with the shipped launch settings (see "RMI handshake timeout in the launchers"), and the JDK's 60 s under a plain `java -jar` (a frozen node held it 60.6 s in a loopback test, and 20.4 s with `-Dsun.rmi.transport.tcp.handshakeTimeout=20000`). The step then stops and drains as any step does, so its `StepDuration` and totals shrink and its `SteadyStatus` can change (for example from `valid` to `short`). A step's poll that reaches its timeout, with or without nodes, also checks each context it did not reach for a terminal failure that is already visible when that context is checked (a standalone DELETE in duration mode polls as before), so a failure in a later context of a weighted or pipeline step fails the run on that poll. It used to wait for the earlier contexts, and was lost when they ran to the step's limit. That check completes a done context only once every context before it is done, so a pipeline stage keeps reading what the stage before it still writes.
- **Retries on a busy distributed entry** — With `load-op-retry`, a distributed run's entry no longer holds back its own slice's retries while the step's await occupies the ForkJoin common pool. Whole-operation retries used to end as unattempted, and their failures were missing from `CountFail`. An affected run's entry slice now retries, so it counts more failures and issues fewer new operations. Range-read retries use the same timer, and each delayed retry logs to the step that scheduled it. Runs with retry off are unchanged. Because every step's delayed retries now share one timer thread, a retry-on run can see its retries run at other times than before, so an affected run can count more failures, or complete a retry successfully. For extension authors: `LoadGenerator.retry` and `retryRange` run on that shared retry timer for a delayed retry (the default `retry` calls `recycle` there) and must not block, since no other step's delayed retry runs while one blocks.
- **`/metrics/json` role on a worker** — A worker's `/metrics/json` node rows now report `"role": "worker"`, live and terminal; they reported `entry` on every `--run-node` engine, workers included, from v5.0.1 on. A row is `entry` when the node accepted that row's run through `POST /run`, and keeps its role from its first appearance until it expires (the node remembers the 16 latest runs it accepted, so a row outlived by 16 later runs reads `worker`), including at the start of each step before the entry's distributed context registers. A node that holds its own step and another entry's slice labels each row by its own part. The idle sample is `entry` while a distributed context is live or a distributed terminal entry is retained, otherwise `worker`. Fleet rows stay `aggregate`; the field's values and `metrics_schema` are unchanged. `/ready` and `/health` are unchanged.
- **`spt status` run id** — `spt status` now prints the run id of a node's run, as `run: state=RUNNING, run=1757500000000`, while the run is active and after it ends. It read a `runId` string while `/status` sends a numeric `run_id`, so it never printed one; a string `runId` is still accepted. A worker's line still shows no run id, because its `/status` stays `IDLE`.
- **In-flight concurrency of a multipart `mixed` step** — A `mixed` step with `item.data.ranges.threshold` set now reports in-flight concurrency and holds the generator's concurrency limit correctly. Each result of a multipart upload or split-range read (its initiation, each part and its completion) released a concurrency permit and counted the operation out, so the step sent more than its concurrency at once and `ConcurrencyCurr` showed an upload as finished while its parts still ran. On the cooperative drivers (`s3`, `s3-aws`, `fs` and the others built on the cooperative base), a multipart operation now holds one permit and counts as one active operation from dispatch until its final result: its completion, a failure, or an abort that reports a failure. This changes the output of such a step: `ConcurrencyCurr`, `ConcurrencyMean`, the start of the steady window and `SteadyTurnovers`. Such a step also dispatches far fewer operations it never sends (`unattempted` in `operation.lifecycle.csv`), and its operation rates can change, because it now runs at most its concurrency of operations at once. One case keeps its permit and count to the end of the step, so the step then runs with one operation fewer at a time for each such upload: on `fs` an upload whose part runs out of retries while other parts are still out, when its abort succeeds; `s3` and `s3-aws` report that abort as a failure and release it.
- **Final active count of a stopped `mixed` step** — The final `ConcurrencyCurr` of a stopped `mixed` step, in `metrics.total.csv` and the final console table, no longer counts operations the step sent to the driver that were never sent on. An operation the driver had accepted but still held unsent when the step stopped (counted as `unattempted` in `operation.lifecycle.csv`) stayed counted as active, so a timed step could end with a nonzero `ConcurrencyCurr` although every sent operation had finished; this showed most on `s3-aws`. This applies on the cooperative drivers; a driver that does not declare how it publishes composite results (`StorageDriver.compositeResults`), such as an extension that wraps another driver, keeps its earlier count, with every result counting an operation out and nothing counted out at the stop. A multipart or split-range operation left unsent now counts out once. Its parts, and the ordinary operations a driver creates and queues through the cooperative base's `enqueueChildOperation` or its child queue, sent or not, never count out or release a concurrency permit, so they no longer lower the count of other operations of their type. Two extension routes still lower it: a driver-created child whose operation class does not track its lifecycle (the `Operation` interface's untracked default) counts out and releases a permit at its result, and a child an extension records with `driverQueued` before it offers it to the child queue counts out if the stop finds it unsent, or at its result, where it also releases a permit. An operation still out at the drain deadline stays counted, and so does a multipart upload or split-range read that the stop cuts short: a timed step with a ranges threshold usually ends with those still counted in its final `ConcurrencyCurr`, one for each upload or split read, while `unresolved` in `operation.lifecycle.csv` counts each of their parts as well, so the two differ. Counts, rates and the requests sent do not change, and nor does steady-window output of a step without a ranges threshold, except that on an `fs` or `s3-aws` step an operation a driver worker gives up unsent while the step still runs now counts out at once.
- **Ctrl-C during a step start** — An engine stopped by a signal (Ctrl-C on a direct run, or `docker stop`) while a step is starting, for example while it retries a distributed node that refuses connections or waits for a silent target, now stops the start and exits, and logs `<step id>: step start stopped, the engine is exiting` once; it used to wait until the start ended, up to about 10 minutes for a node that refuses connections. A distributed step's start stopped this way, or through the node API (`DELETE /run`, `/shutdown`, which `spt run` Ctrl-C sends to a distributed run), no longer goes on to the remaining nodes: it waits only for the node call in progress and starts no further node's slice; it used to start every remaining node, which then sent operations until the stop reached it. The files of the slices that had started (operation lifecycle, integrity performance, item output, traces, timings) are still collected, and each started slice still writes its own `event.loops.json`, but a stopped start writes no metrics or `result.xml` and collects no per-node `event.loops.node-NNN.json`, so those operations are counted only in the started slices' files; a node whose slice was created but not started keeps no result file of it. A start that fails between creating a node's slice and starting it (a NIC-set preparation or metadata run-id check failing on that node) likewise writes no operation lifecycle or event-loop file for that slice; it used to write a lifecycle row of zeros. A start still waits on a call it cannot cut: a node that drops connection packets or never answers the handshake, or one that stopped responding mid-call. With integrity metadata on, a start cut before any slice started no longer logs a terminal integrity failure; its status is unchanged. Once a slice has started, the step still fails closed and the exit logs the failed close. A start stopped through the node API (`DELETE /run`, `/shutdown`) no longer logs a `step failed to start` warning. With traces on, a worker whose trace file name cannot be read no longer stops a distributed step from starting; its traces are left out, with a warning. Affected all releases.
- **File system failure status** — On the `fs` driver, a failure to create or write a file is now reported as a space failure (`RESP_FAIL_SPACE`) only when the file system is out of space or quota. Before, nearly any failure to create a file was reported as one, including 'Too many open files', 'Not a directory' and a read-only file system; these are now `FAIL_IO`, so with `--load-op-retry` they are retried up to the retry limit, permanent ones included (a read-only mount or a path through a regular file goes from one attempt per item to eleven with the default limit). A write that runs out of space is now a space failure instead of `FAIL_IO`, and is no longer retried.
- **No exception at exit after a refused configuration** — A step refused at construction for an invalid configuration (for example `storage.integrity` or standalone DELETE settings) no longer throws a `NullPointerException` from the exit shutdown hook, also after a scenario that handles the refusal. Since 5.14.0.
- **No descriptor or thread leak after a refused driver** — A storage driver refused while it is being built (for example for an unsupported `storage.auth.version`), or dropped because the rest of its step failed to initialize, no longer leaves its event-loop descriptors and I/O threads open on a long-lived engine, nor the worker of an asynchronous expression in `storage.net.http.uri.args`; on `s3-rdma` its payload copier and buffer pool are released too. The exit shutdown hook no longer logs an exception for such a driver. A driver whose `start` fails is handled as before.
- **Worker step slice that fails to stop or close** — A worker engine now releases a step slice whose stop or close fails, for example when it cannot write its operation lifecycle file, also when the slice is closed without an earlier stop: the slice's queued operations, driver thread and periodic metrics output no longer stay on the worker for the rest of its life. This covers a standalone DELETE step whose recovery evidence cannot be written (a read-only or full step folder) or whose post-verification cannot run (a read-only `java.io.tmpdir`) at every attempt: after its stop and close the slice is unexported and its contexts close their storage drivers (a slice closed without an earlier stop is released by a later close), so such runs no longer leave driver threads or storage connections on the worker. The run still fails as before, and the DELETE evidence staged before a failed write stays in the step folder. A standalone DELETE slice in duration mode that runs out of close retries is unexported, stops its metrics output and closes its contexts' storage drivers; if one of its closes is still running on the worker when the run gives up, it also stays exported, as before. Since 5.15.0.
- **Unreachable remote node fails sooner** — A step whose remote node refuses the connection now fails about 2 minutes sooner: the entry no longer sleeps after its last connection try, and that try's log line no longer says it will reconnect.
- **Connection tries to a remote node time out after 10 s** — An entry now gives up on each connection try to a remote node after 10 s. When the network dropped the connection, a try used to take about 2 minutes, and a stop request could not end it; a stop request (`DELETE /run`) now takes effect within about 10 s. A node that is only late is still found.
- **Close failures at engine exit are logged** — A failure to close a step, driver or other engine service while the engine exits is now logged as a warning on the console and in the engine's own `errors.log`, under `log/none-<timestamp>/`, not in the step's `errors.log`; it was printed on stderr in only a few runs and was usually lost. Affected all releases.
- **Close after a failed start** — A step whose start fails before any engine started its part (for example a metadata-mode standalone DELETE without a selection manifest, or a READ whose items file is missing or empty) no longer reports close failures for counts and files it never produced: no `failed to capture terminal metadata-mode operation failure counts`, `entry-node logger artifact is missing`, `entry-node manifest source is missing` or `failed to retain DELETE frozen selection evidence` under the start error, and no `Failed to close the daemon instance` warning at exit. The start error and exit code are unchanged (since 5.14.1; the warning at exit since the change above). When the entry's part wrote its `operation.lifecycle.csv` row before its start failed, as a READ whose items file is missing does, that unmerged file is left under its own name, with no `operation.lifecycle.node-000.csv` copy; the step used to keep it as `operation.lifecycle.node-000.csv` as well, or only there when a worker took part. For extension authors: `LoadStepBase` gains the protected final method `startStepEntered()`, so a load step built outside the engine that declares a method `startStepEntered()` with no arguments must rename it.
- **No exception at a signal during startup** — An engine stopped by a signal (Ctrl-C, SIGTERM or `docker stop`) while it is still building a step, for example while it prepares the step types at the start of a scenario or a `POST /run`, no longer logs `Failed to close the daemon instance …: NullPointerException` with a stack trace for the half-built step. The engine's exit leaves that step alone; a fully built step or driver is still closed as before. The exit code and the result files were and are unaffected. Affected all releases. For extension authors: `DaemonBase` gains the protected constructor `DaemonBase(boolean)`, with which a daemon defers its registration for the exit's close, and the protected final method `registerForCloseAll()`, which such a daemon calls as the last statement of its constructor; `LoadStepBase` gains a 5-argument protected constructor with the same flag. A daemon built outside the engine that declares a method `registerForCloseAll()` must rename it. `DaemonBase.closeAll()` also no longer closes a daemon that is still being built inside `DaemonBase.openConstructionScope()` (new in this release), or whose construction failed there, such as a storage driver that `StorageDriver.instance(...)` or `TargetBucketProvisioning.provision(...)` is building or refused: a failed scope releases it, and a `closeAll()` after the outermost scope succeeded closes it.
- **No false standalone DELETE failure at exit** — A standalone DELETE step client that never started work no longer logs `Standalone DELETE failed … no worker object counters are available`, its close at engine exit no longer fails on that verdict, and it no longer marks a real step with the same step id as failed in its retained metrics (`delete.failure_policy.outcome` in `/metrics/fleet/json`, as a scrape at shutdown reads it). Such clients are the engine's step-type prototypes when `load-op-delete-standalone` is in the base configuration (every exit then logged 16 of these errors), unrun `.config()` copies, and steps refused, stopped or failed before their first slice started; a start that fails keeps its own error. A step that started a slice is judged as before. Exit codes and result files were not affected. Since 5.15.0; the close warnings came with the change above.
- **Size limit on operations without a body** — `load.step.limit.size` stops a step on the bytes it has transferred, so it cannot stop a DELETE, STAT or NOOP step, a standalone DELETE, or a mixed step whose first enabled type (in the order get, put, delete, stat) is DELETE or STAT. Such a load now logs a warning in its `errors.log` at its start, naming the step, the operation type and the limit. It still runs until its count or time limit, or the end of its items. The configuration guide called the limit the size of the data items processed; it now says transferred bytes, and the load steps guide gives the mixed, weighted and pipeline rules. For the `s3-aws` steps that this limit used to stop, see **`s3-aws` byte counts** above.
- **`s3-aws` requests lost at a signal** — When the engine got SIGINT or SIGTERM, the AWS CRT stopped handing results to the driver at once, so the requests in flight were cancelled as `INTERRUPTED` after `storage.crt.stopTimeoutMs`, including ones the target had completed. Their operations and bytes were missing from the totals, `operation.lifecycle.csv` counted them as failed, objects the target had stored were missing from the item output, and the stop took 5 s longer. They now complete as on the `s3` driver. Multipart uploads still in progress at the signal are left open at the target, as before.
- **Recycle steps with output duplicates** — A recycle step with `load.op.output.duplicates=true` no longer ends early with "no load operations to recycle (all failed?)". It now runs to its count or time limit. A step whose operations have all failed still ends at once.
- **Metrics row limits for steps built with `append()`** — A row on `/metrics/fleet/json`, its terminal entry and the Prometheus completion and test-state gauges could carry a count or time limit the step did not run with, so it reported 100% or Completed mid-run. A mixed step's rows took the limits of the context with the same index, weighted and pipeline rows took a context's time limit although the step stops on the base's, and a linear step took its first appended context's limits. A mixed step's own `/metrics/json` rows showed the base count, and with `storage.targetBucket.count` set only in a mixed step's `append()` map, `metrics.bucket.total.csv` and `metrics.bucket.steady.total.csv` held only the READ rows; a linear step with it set only in `append()`, which runs on its base configuration, wrote both files with a header and no rows and logged two incomplete-bucket-metrics warnings, and now writes neither. Every row now carries the limits the step enforces: the count and bucket settings of the configuration its operations run on, and the step's own time limit. For extension authors: a step client can override the new protected `LoadStepClientBase.effectiveConfig(int)` to name the configuration a row's operations run on; the default merges the base with the context of that index, as before, and every row's time limit now comes from the base.
- **Duration of an op-trace row with no start** — In `op.trace.csv`, a row for an attempt that failed before its request was sent (no `ReqTimeStart[us]`), such as a refused connect, now leaves `Duration[us]` empty. It used to hold the attempt's end timestamp (epoch microseconds). The row keeps its node, status and `TransferSize`, and rows with a start are unchanged. Traces are off by default (engine `output.metrics.trace.persist`), and metrics and other outputs are unchanged.

### Added

- **Driver statistics in the metrics JSON** — Rows of `/metrics/json` and `/metrics/fleet/json` gain an optional `driver_stats` object with the counters and gauges a storage driver reports about itself, summed over nodes in fleet rows (metrics schema 5). The `s3-rdma` driver reports its RDMA and HTTP data path counts, buffer registrations and pool levels. See `cli/docs/S3_RDMA.md`.
- **S3-RDMA data path in the run summary** — For each step in which the `s3-rdma` driver sent payload requests, the run summary shows the transfers made over RDMA and those sent over HTTP, and warns when a step moved no payload over RDMA. Each step's final statistics are stored in `spt_run_params.json` under `driverStats`.
- **Driver statistics on the Prometheus endpoint** — `/metrics` on the entry node now exports the fleet totals of each running step's driver statistics, as `spt_driver_<name>_total` counters and `spt_driver_<name>` gauges.
- **Bucket sets** — `spt run --bucket-count N` spreads the objects a run creates over `N` buckets named `<bucket>-0` to `<bucket>-<N-1>`, and `--buckets`, `--buckets-file` or `S3_BUCKETS` names the buckets instead. Bucket sets work with `write`, `write-verify`, seeded `read` and `delete`, and `mixed` on the `s3`, `s3-aws` and `s3-rdma` drivers; other workloads reject a set of more than one bucket. See [Target Buckets](cli/docs/TARGET_BUCKETS.md#bucket-sets).
- **Steady-state metrics** — Each step is now also measured over its steady-state window, from the end of warm-up to just before the drain, in `metrics.steady.total.csv` with the window's start, turnovers, trend, variation and status; existing outputs are unchanged. The run summary shows IOPS Steady and Bandwidth Steady beside the averages, and the JSON metrics API (`metrics_schema` 5) adds a `steady` object. A distributed run needs the same engine version on every node.
- **NIC preview in `spt verify`** — `spt verify --interfaces auto`, or a list of interfaces, addresses or RDMA devices, previews on each host the NICs and Paths a run would use for its S3 endpoints, and fails a host whose plan has a failure. See [`spt verify`](cli/docs/SPT_SYNTAX.md#nics-and-the-nic-plan).
- **NIC list in `spt verify`** — With an SPT 5.17 or later image, each host's verify report now ends with its NICs: state, address, speed, MTU, NUMA node and RDMA device. The image adds `/opt/spt/spt-nic-plan`, which prints a host's NIC inventory and plan as JSON.
- **NIC sets in the engine** — The `s3` driver can now spread its requests over chosen client NICs, set with the engine setting `storage.net.interfaces` (`auto` or a list). Each engine plans the NIC set on its own host, binds its connections to each NIC, splits the concurrency limit across the NICs, and skips a failing NIC while others are working. Control requests, such as bucket checks and multipart aborts, keep the kernel's route.
- **Per-path NIC evidence** — A step whose `s3` driver has a NIC set now writes `nic.paths.csv`, with each NIC and endpoint pair's request attempts, how they ended, and payload bytes. The CLI fetches the files and names them in the run summary. See the engine's [per-path NIC evidence](engine/core/spt-base/README.md#per-path-nic-evidence).
- **NIC sets in `spt run` and `spt replay`** — `spt run --interfaces auto`, or a list of interfaces, addresses or RDMA devices (also `SPT_INTERFACES`), gives every engine of the run a NIC set for the `s3` and `s3-rdma` drivers, and `spt replay --interfaces` does the same. Each step also writes `nic.set.json`, and the run summary shows the interfaces and event loops in use. See [Network Interfaces](cli/docs/NETWORK_INTERFACES.md).
- **Admission barrier for NIC sets** — A step in which any engine has a NIC set now starts operations on every engine at once, after all have prepared, and fails if one engine fails or `load.step.preparation.timeout` (default `10m`) passes. Its duration and rates count from that moment, so they exclude preparation.
- **Host overrides for NIC sets** — `spt run`, `spt replay` and `spt verify` now take `--host-interfaces <host>=<value>` (also `SPT_HOST_INTERFACES`), so hosts with different NICs can each have their own value, or `none` to turn NICs off on one host.
- **NIC sets for the `s3-rdma` driver in the engine** — With `storage.net.interfaces`, the `s3-rdma` driver now opens one RDMA context per NIC on that NIC's device, and each operation keeps its requests on one NIC. Each NIC has its own buffer pool, preparation and copy threads, and by default `max(4, hardware threads / 48)` event loops, so a slow NIC delays only itself. See [S3-RDMA with a NIC set](cli/docs/S3_RDMA.md#nic-sets).
- **RDMA pool check and pre-warm with a NIC set** — A step whose `s3-rdma` driver has a NIC set now checks, before any object operation, that each NIC's buffer pool fits in direct memory, then pre-warms the pools so the load starts warm. The new engine setting `storage.rdma.poolShortfall` decides whether a short pool fails the step (`fail`, the default) or only warns (`warn`).
- **RDMA columns in `nic.paths.csv`** — The per-path CSV moves to schema 2, which adds `rdma_succeeded` and `http_succeeded` columns and per-NIC buffer pool counters for the `s3-rdma` driver. A reader that goes by column name reads both versions.
- **`spt run --interfaces` for the `s3-rdma` driver, and sized direct memory** — `--interfaces` and `--host-interfaces` now work with `--s3-driver rdma`, and `--rdma-pool-shortfall fail|warn` sets the pool check. With a NIC set, the CLI sizes each container's `-XX:MaxDirectMemorySize` from that host's NIC plan when `SPT_JAVA_OPTS` doesn't set it, and `spt verify --use-rdma` previews the sizing. See [S3-RDMA with a NIC set](cli/docs/S3_RDMA.md#nic-sets).
- **Event loops in every run's results** — Every engine now writes `event.loops.json` for each step, with each driver's event loops and what sized them, and the run summary shows an `Event loops` line. See [Event loops](cli/docs/EVENT_LOOPS.md).

### Changed

- **Fewer default event loops on large clients** — With `storage.driver.threads` unset, Netty-based drivers on the default route, including `s3` and `s3-rdma` without a NIC set, now run `max(4, hardware threads / 24)` event loops instead of `max(4, hardware threads / 8)`; clients with fewer than 40 hardware threads keep 4. On a client with 192 hardware threads, 10 KiB GETs carried 16% to 29% more for about half the client CPU per operation. Set `storage.driver.threads` for the earlier count; see [Event loops](cli/docs/EVENT_LOOPS.md#default).
- **Huge pages in the image** — The SPT image now sets `GLIBC_TUNABLES=glibc.malloc.hugetlb=1`, so malloc asks for huge pages where the host's transparent huge pages mode is `madvise`. This roughly halved RDMA pool pre-warm time, with no change measured under load.
- **Driver extension methods** — `NettyStorageDriverBase.releaseTransport(Channel)`, `CoopStorageDriverBase.hasAvailableDispatchCapacity()` and `CoopStorageDriverBase.dispatchAttemptLimit(int)` are now protected. A driver extension that declares a method with one of these signatures now overrides it, or no longer compiles if it declares it with weaker access; rename that method.
- **Dependency updates** — The CLI is built with Go 1.27.4 (previously 1.25.14), which building it from source now needs, and the engine image uses Eclipse Temurin JRE 25.0.5. Updated Netty to 4.1.140, AWS SDK/CRT to 2.57.11/0.50.0, Jackson to 2.22.4, and several Go modules.

### Fixed

- **Spurious ERROR at the end of every `mixed` run** — A `mixed` step that stops normally no longer logs `MixedLoadGenerator error in doWork` with `java.io.EOFException`. It didn't affect results.
- **Outdated libraries inside extension JARs** — The `mixed`, `pipeline` and `weighted` extensions no longer bundle outdated copies of Jackson, SnakeYAML and Log4j that image scanners flagged; they use the engine's. The `s3-tables` extension now bundles Parquet 1.18.1, fixing CVE-2025-30065.
- **`NullPointerException` in every step's errors log** — A step's errors log no longer records a `NullPointerException` from closing the driver that checks target buckets. Present since 5.16.2.
- **`spt run delete --cleanup` with objects left to clean** — A seeded DELETE whose cleanup removed objects now exits by its measured result. It used to exit 1 with "unexpected current-run DELETE step" or "missing authoritative terminal DELETE step".
- **Ordinary runs that failed outright** — A `read`, `write`, `mixed` or `tables` run now exits 1 if every request of a phase failed, instead of 0, and a `list` run that found no objects and had failed requests also exits 1. The summary has a new `Failed` column. Partial failures still exit 0.
- **Steady windows across an outage** — The summary now warns when a `valid` steady window's rate didn't hold (a trend of -50% or lower, or a CV of 0.5 or higher). The window stays `valid`, and the cutoffs are uncalibrated.
- **A `written.csv` manifest as `--read-items-file`** — A `mixed` run reading from a `written.csv` manifest now reads each row's object. Every READ used to fail with 404, because the row's bucket was lost.
- **Bad items input and failed starts** — A blank or invalid line in an items file, an unreadable or empty items file, a listing that fails part-way, or an engine that fails to start now fails the run with exit 1 and a named reason, instead of passing with a wrong count. A scenario run with `--run-scenario` now exits 1 on any terminal failure.
- **`spt replay` exit code** — A replay whose scenario fails after its first step now exits 1 instead of 0.
- **`spt run delete --duration`** — A duration DELETE now runs for its requested duration. It used to stop almost at once and exit 1, with most of its inventory unattempted.
- **`--delete-items-file` in a distributed `mixed` run** — Each engine now deletes its own share of the file's rows. Every engine used to delete every row, which multiplied the reported DELETE count and rate by the number of engines.
- **Large `spt run delete` runs** — A DELETE whose step takes a moment to finish no longer exits 1 with "engine terminal state is RUNNING" after deleting everything. A failed DELETE step's error now leads with the step's own reason.
- **`spt run read-verify` on an empty bucket** — With no `--prefix` and more than one thread, `read-verify` on an empty bucket no longer hangs. It exits 1 with "selected zero objects", or 0 with `--allow-empty-selection`.
- **`spt run delete` across buckets** — A DELETE with `--delete-batch-size=1` over several buckets now works on all of them at once, instead of one bucket after another.
- **`spt run delete --validate-inventory`** — A count-based DELETE with `--validate-inventory` now runs its post-delete verification and finishes, instead of exiting 1 after correct requests.
- **`spt run delete --label`** — A standalone DELETE with `--label` no longer exits 1 with "planned DELETE step identity ... has no stable ordinal" after correct requests.
- **`spt run delete --items-file`** — A DELETE from an items file now exits by its result. It used to exit 1 with "failed to retain DELETE frozen selection evidence" after correct requests.
- **A multipart part that loses its connection before any response** — When a multipart part lost its connection before any response and its retry succeeded, the HTTP-based S3 drivers never completed or aborted the upload, which could stall the step until its time limit. The upload now completes after the retry.
- **A multipart completion or abort that cannot connect** — A multipart upload whose completion request cannot connect is now aborted, instead of staying open on the target with its parts. The operation still fails, and an integrity run's `multipart.lifecycle.csv` now records such uploads.
- **A multi-range read whose range runs out of retries** — When one range of a multi-range read failed on every retry, the read could be counted as a success or not at all, and could stop the driver sending requests. It now finishes its other ranges and counts as failed.
- **Object names that start with the bucket name** — The HTTP-based S3 drivers treated an object name that merely started with the bucket's name as already holding its bucket, so `--bucket abc --prefix abcdef/` wrote into bucket `abcdef` and `--prefix abc/` lost the prefix, with exit 0. A name now holds its bucket only when the match ends at a `/`. **Compatibility:** objects that earlier versions wrote this way stay where they were written, and items files and manifests from those runs still name the old keys.
- **Rate-limited runs start paced** — With `load.op.limit.rate` set, each node sent up to one batch at full speed before pacing began, so short runs reported rates well above the limit. Each node now paces from its first operation.
- **Mixed cleanup on several workers** — `spt run mixed --cleanup` on more than one worker left objects behind, because cleanup read only the entry engine's list. Cleanup now collects every worker's list first, and the run's `put-remaining.csv` covers every worker.
- **Collecting a worker's item list survives a failed read** — A failed read while collecting a worker's item list is now retried up to 3 times. A list that still can't be read is kept on that worker with an error, instead of being deleted.
- **The `dummy-mock` driver stops like the real drivers** — The `dummy-mock` driver now refuses operations once a stopping step closes admission, so no operation completes after the step's outputs have closed.
- **A step's final values come from its own last read** — A metrics read still in progress as a step ended, such as a CLI poll or a Prometheus scrape, could replace the step's final totals with earlier counts. Final values now always come from the step's own last read.
- **Endpoint slicing when the node count does not divide the endpoint count** — With `--slice-endpoints`, when the node count did not divide the endpoint count, the later nodes targeted every endpoint instead of their own group. Each node now targets the group the log lists for it.
- **RDMA readiness in `spt verify` covers every device** — `spt verify --use-rdma` now checks the port of every RDMA device in the container, not just the first, and warns about each inactive one.
- **A JavaScript array in a scenario step's configuration** — A list setting written as a JavaScript array in a scenario's `.config(...)` or `.append(...)` now works like the same comma-separated string, instead of failing with `Scenario syntax error`. Three shipped example scenarios that could not run are corrected.
- **Pipeline steps hand over every item** — In a `PipelineLoad` step, a sub-step after the first could end before processing every result of the sub-step before it, and the handoff could stall the step past its time limit. Each sub-step now waits for and processes every result, so `spt run mock --cleanup` deletes while it creates and its create phase can run about 10% slower.
- **In-flight counts of `mixed` steps** — A `mixed` operation that finished before the step had counted it as sent stayed counted as in flight, so `ConcurrencyCurr` and `ConcurrencyMean` could read too high. Requests, rates and latencies were not affected.

## [5.16.2] - 2026-10-22

### Added

- **Concurrent local runs** — Added `spt run --rmi-registry-port` (default 1099) to set the local engine's RMI registry port, so several `spt run` instances can run on one host at once, each with its own `--api-port` and registry port. Before, a second instance failed to start with `Port already in use: 1099`. Remote and distributed runs keep port 1099 and reject any other value.

### Changed

- **Target-bucket provisioning** — Before each phase of an `s3`, `s3-rdma` or `s3-aws` workload starts, the engine on the entry node now checks the phase's target buckets: the bucket it writes to, the bucket it reads or lists, and every bucket its items file names. It creates a missing bucket only for the phase that writes the run's objects (the write or seed phase), and only after the target answers 404. `spt run --provision-target-bucket=false` (engine `storage.targetBucket.provision`, default `true`) still checks every bucket but never creates one. A bucket that is missing or not accessible ends the run before any object operation, with the phase and the cause in the console and exit code 1. Before, each worker checked and created the bucket on the first object it wrote, distributed workers could race to create it, and a failure only failed operations. Existing buckets are used as they are; SPT never clears, deletes or reconfigures a bucket. See [Target Buckets](cli/docs/TARGET_BUCKETS.md).
- **S3 region** — The `s3-aws` driver now picks its region in the same order as the other S3 drivers: `--region` or `storage.region`, then the region of a standard AWS endpoint (`s3.<region>.amazonaws.com`), then `us-east-1`. Before, it used `eu-west-2` when no region was set. `spt run` now also reads `S3_REGION` when `--region` is not given. A CreateBucket request to a standard AWS endpoint outside `us-east-1` carries the region's location constraint.
- **Bucket names in custom scenarios** — A per-operation expression (`${...}`, `#{...}`) in the bucket segment of `item.output.path` now fails the step at start with a configuration error, because the bucket must be known before the phase starts; keep such expressions after the bucket, as in `/bucket/${...}`. An initialization expression (`%{...}`) in the bucket segment, including the engine's default timestamped output path, is now evaluated once by the entry node, so every node of a distributed run writes to the same bucket instead of one per node.
- **`--create-prefix` deprecated** — The flag never had an effect. It is now hidden, prints a deprecation warning, and will be removed in the next minor release.
- **S3-AWS workers** — With `storage.driver.threads` unset, the `s3-aws` driver now runs one I/O worker per concurrency permit instead of at most one per hardware thread. Every request blocks its worker, so a run with `--threads` above the node's CPU count previously kept only as many requests in flight as the node had CPUs and queued the rest behind busy workers; it now keeps the configured number in flight. A worker blocked in a request no longer takes queued permits with it: new operations go to idle workers first.

### Fixed

- **Bucket checks taken for a missing bucket** — The `s3` and `s3-rdma` drivers treated any failed bucket check, an authorization failure (401, 403) or a server error included, as a missing bucket and tried to create it. Only a 404 now counts as missing; any other answer is reported as the bucket being inaccessible, and no create request is sent. Worker logs no longer print the response body of a failed bucket check.
- **Runs that fail during setup** — A run that fails before any phase slice starts now ends with an engine `FAILED` status that carries the step, the category and the message, and `spt run` exits 1 for every workload. The console shows that cause rather than a missing-metrics error, and a distributed run ends instead of waiting for metrics that never come.
- **S3-AWS lost requests** — A request the AWS client lost with no connection (so that `storage.crt.socketTimeoutMs` could not see it) stayed in flight for the rest of the run and, through the worker it blocked, stalled every permit queued behind it. The driver now puts a deadline on each request with `storage.crt.requestTimeoutMs` (default 300000, `0` for no bound), from the moment it makes it until the response has been read in full, a GET's body included: a request that outlives it is cancelled and fails as a timeout, counted and logged like any other.
- **S3-AWS stop with a lost request** — A step that stopped with such a request in flight waited for the whole of `load.op.wait.limit`, could not be stopped within the engine's budget, and ended with the operation still active. Once the step has closed admission, the driver now gives the requests in flight `storage.crt.stopTimeoutMs` (default 5000, half of the engine's budget for stopping a run; `0` to turn off) and then cancels them, a GET still reading its body and a request made after the grace included, so they end as `INTERRUPTED` and the stop completes within the budget. A driver stopped and started again gets a fresh grace for each stop.

## [5.16.1] - 2026-10-19

### Fixed

- **S3-AWS stalled requests** — The `s3-aws` driver now applies `storage.crt.connectionTimeoutMs` (default 5000) and `storage.crt.socketTimeoutMs` (default 30000) to all of its S3 clients. Before, a request that stopped making progress stayed in flight indefinitely and could keep the step from stopping. Now such a request fails as a timeout once its connection has moved no data for `socketTimeoutMs`, possibly after the AWS client retries it. `0` turns this off; any other value must be at least 2000. ## [5.16.0] - 2026-10-13

### Added

- **S3 region selection** — Added `spt run --region` and engine YAML `storage.region` support to explicitly select the AWS region for S3 requests. Omitting the setting preserves each driver’s existing region selection.
- **S3-RDMA data-path summary** — The `s3-rdma` driver now logs one end-of-step summary in `messages.log` showing how many data operations actually moved over RDMA, were declined by the server, failed, or used HTTP (RDMA unavailable, below threshold, oversize, ineligible, or preparation fallback).
- **Automatic RDMA local address** — When `--rdma-local-ip` is not set and `--rdma-device` is `auto`, each worker now selects the local address it routes toward the first S3 endpoint for RoCE GID selection, so distributed runs no longer need one shared address. Leave the flag unset for multi-host runs; a named `--rdma-device` keeps device selection authoritative.
- **S3-RDMA payload copy threads** — Added `spt run --rdma-copy-threads` (env `RDMA_COPY_THREADS`, engine `storage.rdma.copyThreads`) to copy each RDMA PUT payload of 2 MiB or more into its buffer on several threads instead of on the driver's dispatcher thread alone. The default of 1 keeps the previous behavior.
- **Legacy RDMA byte-count option** — Added `spt run --rdma-allow-missing-bytes-header` (env `RDMA_ALLOW_MISSING_BYTES_HEADER`, engine `storage.rdma.allowMissingBytesHeader`) for servers that report RDMA GET success without `x-amz-rdma-bytes-transferred`; it counts the requested size instead of failing the read.
- **S3 endpoint selection** — Added opt-in `--endpoint-selection` for the Netty S3 driver to choose the connect destination of every request attempt: `round-robin` over the `--endpoints` addresses, or `per-request-dns`, a fresh DNS lookup of the endpoint hostname. The default mode is unchanged; see `cli/docs/ENDPOINT_SELECTION.md`.

### Changed

- **S3-RDMA buffer reuse** — The `s3-rdma` driver now keeps registered buffers and reuses them across operations instead of allocating, zero-filling, and registering a new buffer for every PUT and GET, which limited RDMA throughput. A buffer is reused only after the server's final response to its request, and a buffer used by an integrity-verified GET only after that GET verified; buffers of requests that time out, lose their connection, or fail are deregistered. Pooled buffers stay within half of the JVM's direct-memory limit and are released when a per-operation buffer would otherwise not fit; transfers above 1 GiB are not pooled. `spt run --rdma-buffer-pool=false` (env `RDMA_BUFFER_POOL`, engine `storage.rdma.bufferPool`) restores per-operation buffers. The RDMA data-path summary in `messages.log` adds pool counters.
- **Remote entry-node log relay** — Entry-node output now arrives over one `docker logs --follow` SSH session instead of a new SSH session twice a second, reducing CPU load on the entry host. The console still shows only the engine's stdout; its stderr (such as JVM and logging warnings) is kept only in the CLI log, and only with `--log-level debug`.
- **Dependency updates** — The CLI is now built with Go 1.25.14 (previously 1.25.10). Updated Netty to 4.1.139 (netty-tcnative 2.0.84), AWS SDK/CRT to 2.55.14/0.48.5, Log4j to 2.26.1, Jackson to 2.22.3, Jetty to 9.4.58, Commons Codec to 1.23.0, Commons Lang to 3.21.0, Guava to 33.7.2, Avro to 1.11.5, Disruptor to 3.4.4, SLF4J to 1.7.36, Bouncy Castle TLS to 1.86.2, and Docker Go connections to 0.8.2.

### Fixed

- **S3-RDMA reply validation** — RDMA PUT and GET now honor the server's `x-amz-rdma-reply` and `x-amz-rdma-bytes-transferred` headers. A server that declines RDMA (HTTP 200 with reply 501, or no reply) previously produced "successful" writes counted at full object size although nothing was stored; declined PUTs now fail. Declined GETs are counted once over HTTP when `--rdma-fallback` is enabled and fail otherwise. GET bytes come from the server's reported transfer size, and a success without that header, a byte-count mismatch, or any HTTP body (including chunked bodies) on an RDMA success fails as corrupt.
- **S3-RDMA multipart uploads** — The multipart initiate request no longer allocates, copies, and registers the entire object; only upload parts use RDMA, each with a part-sized buffer. Parts that fail RDMA preparation or time out now settle their upload's part accounting exactly once, so retries and abort proceed.
- **S3-RDMA ranged reads** — Reads with fixed or random byte ranges now use HTTP instead of an RDMA buffer sized for the whole object, which previously miscounted or failed valid range responses.
- **S3-RDMA memory exhaustion** — An RDMA buffer allocation that runs out of JVM direct memory, or a PUT payload copy that runs out of memory, now fails the operation, or sends it over HTTP with `--rdma-fallback`, instead of escaping the driver and stopping its dispatch of further operations.
- **S3-RDMA fallback setting** — With `--rdma-fallback` disabled, RDMA buffer-registration or token failures now fail the operation instead of silently sending it over HTTP.
- **S3-RDMA fallback payload** — With `--rdma-fallback`, a PUT whose RDMA preparation failed after its payload was copied (for example, when no RDMA token could be generated) was sent over HTTP without its body and failed. The fallback request now carries the whole payload, and the same failure with `--rdma-fallback` disabled no longer reports the object's bytes as written.
- **Partial-read retries at stop** — A partial read whose retry had not yet sent its request when a run stopped now delivers its earlier failure exactly once. Previously, the failure was counted but its result was never delivered, and the run ended with “Range result delivery failed.”
- **DELETE failure-budget reporting** — Duration-based DELETE runs now propagate a failure-budget exception consistently when the budget is exceeded during worker startup, matching failures detected during active waiting.
- **Composite expression evaluation** — Give each expression segment its own evaluation context to prevent intermittent method-resolution failures when synchronous and asynchronous segments run together.

- **Write prefixes and saved manifests** — `spt run write` now honors `--prefix` before any shard directories, preserving complete object keys in saved manifests for subsequent reads and cleanup. Combining `--save-items` with `--cleanup` retains the manifest after object deletion. Workloads that do not support `--prefix` now reject it explicitly instead of silently ignoring it.
- **Run labels on result artifacts** — `spt run --label` now applies the same sanitized label to generated step IDs and their result filenames as to the results directory. Runs without a label retain the `mt` prefix.
- **Distributed launch messages** — Ordinary distributed workloads now report “distributed run” instead of the misleading “distributed replay.”
- **Verification service startup** — `spt verify` now polls the required service ports for up to 30 seconds instead of checking once after a fixed ten-second sleep. Healthy engines that start more slowly can pass, already-ready engines proceed immediately, and unavailable ports still cause a bounded failure followed by container cleanup.
- **False metrics-schema warning at run start** — The TUI no longer reports “Incompatible metrics JSON … requires metrics_schema >= 2” while engines are reachable but have not yet published metrics for the current run, such as during the pre-step stabilization pause. Genuinely incompatible metrics payloads still produce the warning, including when they first appear after startup.
- **Credentials in step config logs** — The engine now masks storage credentials in each step's logged `config.yaml`, which single-host runs keep under `.node-home` in the results folder.
