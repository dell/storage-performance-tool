# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/), and this project adheres to [Semantic Versioning](https://semver.org/).

## [Unreleased]

### Added

- **`spt verify --rmi-registry-port`** — `spt verify` now takes `--rmi-registry-port`, with the default (1099), help text and range check of `spt run`'s flag. Verify's test engine serves its RMI registry on that port, and the port conflict check and bridge port mappings use it. With `--api-port` and `--rmi-registry-port`, a host can be verified beside a running engine that holds ports 1099 and 9999. `spt run` takes the same flag for every engine in a run.
- **`spt replay --rmi-registry-port`** — `spt replay` now takes `--rmi-registry-port`, with the default (1099), help text and range check of `spt run`'s flag. Every engine of the replay serves its RMI registry on that port: the local engine, a lone remote engine, or the entry and every worker of a distributed replay, which the entry reaches on it. A replay that shares hosts with another replay or an `spt run` needs its own `--api-port` and `--rmi-registry-port`, also when it has a local worker. Replay now refuses an `--api-port` equal to `--rmi-registry-port`, as `spt run` does, so it accepts `--api-port 1099` with another registry port. At the default port, every engine command is unchanged.
- **Mongoose versioning flag** — The engine accepts the Mongoose 3.x flag `--storage-net-http-versioning` as a synonym for `storage.object.versioning` with the S3 drivers. **Compatibility:** with `s3` and `s3-rdma`, a command that already passes it now checks the bucket's versioning on first use, enables it on a bucket that has never been versioned, leaves it on, and writes `key~versionId` names; a suspended bucket, or one whose versioning check fails, is left alone with a warning (see **Bucket versioning at first use** under Changed). With `s3-aws` it only splits `key~versionId` input names. With `s3-tables` it has no effect. See the [S3 driver's versioning guide](engine/extensions/storage-drivers/implementations/s3/README.md#434-mongoose-versioning-flag).
- **S3 error code of a refused request in `errors.log`** — When a target refuses a request, the `s3` and `s3-rdma` drivers now log, after the existing status line, one more `errors.log` line with the S3 error code and message from the response body, for example `CREATE,<item>,/bucket/,: S3 error code EntityTooSmall, message: Your proposed upload is smaller than the minimum allowed object size.` It covers object PUTs and GETs, multipart parts, and multipart initiations, completions and aborts; multi-object DELETE and LIST responses, and single-range reads (`--range-size`), log no such line. A read split by `--part-size` is covered. Only the first 1 KiB of the body is read, the message is cut to 256 characters, and control, line separator and Unicode format characters in either are replaced, so the line cannot break the log; a code or message not found is logged as `(missing)`, and a refusal with an empty body logs no extra line. Operation status and counts are unchanged, and successful responses are not read. The multipart notes of `SPT_SYNTAX.md` and the `item-data-ranges-threshold` configuration row now say that Amazon S3 requires every part but the last to be at least 5 MiB.

### Changed

- **RMI object range no longer published or checked** — `spt run`, `spt replay` and `spt verify` no longer publish or port-check the RMI object range: the engine never used it, since it serves its RMI services on the registry port. `--rmi-port-start` and `--rmi-port-count` are still accepted and recorded in `spt_run_params.json`, and have no effect. A port in use in 40000-40009 no longer fails a run's preflight, and a local worker or a bridge-mode verify container publishes only the API and RMI registry ports.
- **Partial-read performance wording** — The partial-read docs now describe the release performance check instead of a pending qualification: ordinary READ and WRITE runs showed no regression in the v5.15.2 check against v5.14.2, the last release before partial reads. No partial-read performance figures are published.
- **Known issue: default S3 auth version** — A direct-engine run (`java -jar`, `run.sh` or the image run by hand) with the `s3`, `s3-rdma` or `s3-tables` driver that passes no `--storage-auth-version` signs with V2 or V4 depending on the order in which the host lists the engine's `ext/` directory, so the same command can sign differently on two hosts. Pass `--storage-auth-version` explicitly: `4` for SigV4, or `2` for a legacy target that rejects SigV4. `spt run` always passes a version and is not affected. A later release makes V4 the single default.
- **Engine that never becomes ready** — When an engine never becomes ready, `spt run` and `spt verify` now show, after the wait failure and for each host whose engine API never answered, its container state (running, exited with its exit code, or missing) and its last 20 log lines, stdout and stderr together: in `spt run`'s API readiness failures, under the start failure of a remote worker or entry, and under `spt verify`'s `Ports Accessible` check. A local single-host `spt run` adds the container state to its startup diagnostics, which it already showed with the container's last 120 log lines, and now prints the failure line once, ahead of them. In those log lines, the values of `S3_ACCESS_KEY` and `S3_SECRET_KEY`, and each endpoint's host and host:port from `S3_ENDPOINT` and `S3_ENDPOINTS` (in any letter case), are masked as `***` wherever they appear as a whole token, as are credentials passed as key=value or flag arguments. A state or log that cannot be read is reported as such. Exit codes and the output of a successful wait are unchanged.
- **`spt run --rmi-registry-port`** — `spt run --rmi-registry-port` now works for remote and distributed runs; it previously applied only to local single-host runs. Every engine in the run serves its RMI registry on that port: a lone remote engine, and the entry and every worker of a distributed run. The entry reaches each worker on it, and the port conflict check covers it on every host. Because every engine serves both ports, `spt run`, `spt verify` and `spt replay` now refuse an `--api-port` equal to the registry port.
- **SSH keepalives** — Every SSH command and copy SPT runs now gives up about 60 seconds after its host stops answering, even where the SSH config sets a longer `ServerAliveInterval`, unless it runs over a shared connection opened outside SPT. A network gap longer than that, such as a VPN renegotiation, now ends the command instead of waiting for the connection to recover.
- **`SPT_JAVA_OPTS` with the bundle launchers** — `SPT_JAVA_OPTS` now adds to the bundle launchers' default JVM options, as it does in the SPT image, instead of replacing them. Results of `run.sh` and `run.bat` runs that set `SPT_JAVA_OPTS` can differ from 5.17.0. **Compatibility:** to pick another garbage collector, turn ZGC off first: `SPT_JAVA_OPTS="-XX:-UseZGC -XX:+UseG1GC"`; G1 tuning options without `-XX:+UseG1GC` are accepted and do nothing under ZGC. A maximum heap below 1 GiB needs a matching `-Xms`, because the default `-Xms1g` stays: `SPT_JAVA_OPTS="-Xms512m -Xmx512m"`. `-XX:MaxRAMPercentage` has no effect while the default `-Xmx4g` is on the line; give `-Xmx` instead. To run without the defaults, call `java <options> -jar spt.jar` directly.
- **Bucket in op traces of manifest-driven steps** — The `ItemPath` column of `op.trace.csv` now holds `/<bucket>/<key>` for steps that take their objects from a `bucket,key,size,version_id` manifest, as other steps' rows do: write-verify's verify and `--cleanup` steps, `read-verify`, `read --items-file` with a manifest, and a `mixed` DELETE from a manifest `--delete-items-file`. The path is the one the `s3` driver requests, with one slash between the bucket and the key whatever slashes the manifest's bucket and key carry. A CREATE that takes its objects from a manifest names its destination, the output path, not the manifest's bucket. These rows held the key alone, so a run over several buckets couldn't tell which bucket each object was in. Traces are off by default (engine `output.metrics.trace.persist`), and other outputs are unchanged.
- **Bucket versioning at first use** — With `storage.object.versioning` or `storage.net.http.versioning` on, the `s3` and `s3-rdma` drivers now report what they found at a bucket's first use: versioning already enabled, enabled by this run, or could not be enabled. A bucket whose versioning is suspended is now left alone with a warning, and the run goes on un-versioned; before, SPT re-enabled it. When SPT can't read the bucket's versioning state, it now sends no request to enable it and warns, and the run goes on un-versioned. Each engine writes the notice that versioning is already enabled to the step's `messages.log`, and its warnings to `errors.log`; that this run enabled versioning is a warning, so it shows whatever the log level up to WARN. Each engine also writes them to a new per-step `bucket.versioning.log`, which carries them to the entry engine and is not a result file. On a distributed run the entry engine copies each worker's notices into its own two logs when the step stops, before it publishes the step's total metrics, so the run's results show them. It waits at most 10 seconds for this at each of the step's start, stop and close, and warns about a worker it left out because it didn't answer in time or an earlier read of it hasn't returned; that worker's notices are then only in its own `bucket.versioning.log`. **Recorded exception to the patch-stable rule (owner, 2026-11-14):** with `storage.object.versioning` or its synonym `storage.net.http.versioning` on, on the `s3` and `s3-rdma` drivers, a workload on a Suspended bucket (including Suspended with MFA delete enabled) now runs un-versioned with a warning instead of having versioning re-enabled, and a workload whose `GET ?versioning` fails now sends no `PUT ?versioning` and runs un-versioned with a warning. **Recorded with it (owner, 2026-11-15):** so does a workload on a bucket whose `Status` is neither `Enabled` nor `Suspended`, and one whose successful `GET ?versioning` returns a body that isn't a `VersioningConfiguration` SPT can read (an empty or non-XML body, for example). 5.17.0 sent the PUT in both cases unless the response body contained the text `Enabled` anywhere, so a `Status` such as `NotEnabled` got no PUT there either. A Suspended bucket with MFA delete enabled was misread as enabled before, so it already ran un-versioned, without a warning; it now gets the warning.
- **`spt run --output-dir` deprecated** — `spt run --output-dir` (`-O`) never had an effect: results have always gone under `--results-dir` (default `./results`). It is now deprecated, hidden from help, and warns when used; pass `--results-dir` instead. `spt replay -O` is unchanged.
- **`spt run` `--object-size` and `--duration` check** — `spt run` refuses an `--object-size` or `--duration` that the engine cannot parse before it starts anything, with exit 1 and `--object-size must be a size such as 4KiB, 1MB or 1KB-1MB, got <value>` or `--duration must be a time such as 30s, 5m or 1h, got <value>`; `--generate-only` now checks them as well. Such a value used to start the engines, and the step failed with the reason only in the engine log. Every value the engine accepts is still accepted, and each flag stays unchecked where the run never uses it: `--object-size` for `list`, `tables`, and DELETE with `--items-file` or `--delete-existing`, and `--duration` for `tables --test-vector compaction`.

### Fixed

- **Multipart initiation response without an upload ID** — When a target's multipart initiation response has no upload ID, the `s3` and `s3-rdma` drivers no longer write the whole response body, raw, to `errors.log` and the console for every operation. A refused initiation or abort logs only its status and error code, and a success response without an upload ID is warned about once per step with a short, cleaned excerpt: the operation and the first 256 characters of the body's first 1 KiB after any leading whitespace, with control, line separator and Unicode format characters replaced; later ones are logged at DEBUG. Such an operation still fails as before.
- **Multipart log fetched** — `spt run` now saves the engine's multipart log (`parts.upload.csv`) as `<stepID>.multipart.csv` for a single-engine step. The CLI looked for it under names no engine uses, so it was always recorded as missing. A distributed step still records it as missing until the engine collects every node's log. The documented columns are corrected.
- **`result.xml` start date** — `result.xml` and `result-threshold.xml` could show a start date of 1969-12-31 and a 1970 end date when the step closed before the row was written: the row read `StartDate="1969-12-31 23:59:59"`, `StartTimestamp="-1"`, and an `EndTimestamp` of the elapsed time minus 1, from v5.7.1 on. The row now records the step's start time when it is queued, so `StartTimestamp` is the real start and `EndTimestamp` is start plus elapsed time. Counts, rates and latencies were not affected, and rows that were right are unchanged.
- **Ctrl-C while connecting to hosts** — Ctrl-C or SIGTERM while `spt run` or `spt replay` connects to its hosts now reports a cancellation, such as `spt run`'s `failed to connect to required hosts: host connection cancelled: interrupt signal received`. It no longer continues with the hosts already connected, reports too few hosts, or shows an SSH failure. The exit code is still 1.
- **Mock driver concurrency no longer negative** — With `dummy-mock` (`spt run mock`), the concurrency columns in the metrics CSVs (`ConcurrencyCurr`, `ConcurrencyMean` in `metrics.csv`, `metrics.total.csv` and `metrics.steady.total.csv`), the step summary and `/metrics` no longer show negative values. The driver read its scheduled and completed counts one after the other, so a sample read low by every operation that completed in between, from v5.0.1 on. It now reads them stably, so the mock's mean concurrency is a small non-negative number instead of slightly negative. Real drivers were not affected.
- **SigV2-signed S3 listings** — With `storage-auth-version: 2`, the listings of the `s3` driver and of `s3-rdma` and `s3-tables`, which inherit it (the item input path listing, the LIST step, the versions listing and the delimiter probe), no longer fail with `403 SignatureDoesNotMatch` on targets that follow the SigV2 specification, such as SeaweedFS. The driver signed the whole query string; it now signs the path plus only the SigV2 sub-resources (such as `versions`, `uploadId` and `partNumber`), sorted by name, with an empty value signed as the bare name and a `versionId` value signed decoded (see **V2 signature of an encoded version ID**). An item whose name holds a query sends that query and now signs only its sub-resources, as a strict target computes them: `k?x=1&versionId=a%2Bb` signs `/<bucket>/k?versionId=a+b`, and with versioning on, `k?x=1` at version `a+b` (sent as `k?x=1?versionId=a%2Bb`) signs `/<bucket>/k`. It used to sign the query as sent. Bucket checks and bucket creation with `storage-net-http-uri-args` now sign the bare bucket path too. The item input path listing had regressed in v5.14.0; the LIST step had always failed this way. Requests that already signed correctly, such as multipart, `versionId`, tagging, delete and versioning requests, sign the same bytes as before, except an empty version ID (an item named `key~`, which targets refuse), whose `?versionId=` now signs as the bare `?versionId`. SigV4 is unchanged.
- **Versioned read selects its version** — A versioned read (`storage.object.versioning` with `key~versionId` items) on the `s3` and `s3-rdma` drivers now reads the named version with `?versionId=`. It used to send an `x-amz-version-id` request header, which S3 ignores, and read the current version. A versioned STAT now checks the named version; it used to send no version. The request header is no longer sent on READ, including a metadata-only READ (`storage.net.http.read-metadata-only`); DELETE and UPDATE requests are unchanged. Read sizes and recorded version IDs can change, and so can success and failure counts: a READ or STAT naming a version that no longer exists (deleted, expired, or from an items file of another bucket) used to succeed on the current version and now fails with 404. Recorded exception to the patch-stable rule (owner, 2026-11-14): the workload that changes is a versioned READ or STAT with `storage.object.versioning` and `key~versionId` items; with versioning off nothing changes. Versioned copy and items above the multipart threshold still select no version; see the [S3 driver's versioning guide](engine/extensions/storage-drivers/implementations/s3/README.md#43-versioning).
- **Retried versioned operation keeps its version** — A retried versioned operation (`storage.object.versioning` with `load.op.retry`) keeps its version. A retried versioned DELETE used to become a plain DELETE, which adds a delete marker, and a retried READ read the current version. The item is no longer renamed while its request is built, so a failed attempt leaves it named `key~versionId`, and a successful one still renames it `key~<returned version>`, without a second suffix. A success whose response has no `x-amz-version-id` header now keeps the name `key~versionId`, where it used to leave `key`; after a CREATE or UPDATE that name is the previous version, not the one the `PUT` made. Recorded exception to the patch-stable rule (owner, 2026-11-14, widened 2026-11-15): the workload that changes is a retried versioned operation with `storage.object.versioning`, `load.op.retry` and `key~versionId` items, and a non-retried versioned operation on a `key~versionId` item that succeeds without an `x-amz-version-id` header or fails, whose result keeps the name `key~versionId`; with versioning off nothing changes. **Compatibility:** with versioning on, a driver extension that overrides `dataUriPath` now receives the item with its whole `key~versionId` name, where it used to receive `key`, and the driver takes `~versionId` off the end of the path it returns. If that path doesn't end with `~versionId`, nothing is sent and the operation fails at once with `FAIL_UNKNOWN`. A driver extension's `httpRequest` can throw the new protected `HttpStorageDriverBase.RejectedRequestException` to fail an operation the same way; see the [S3 driver's versioning guide](engine/extensions/storage-drivers/implementations/s3/README.md#43-versioning).
- **V2 signature of an encoded version ID** — With `storage.auth.version=2` (the default for the engine's `s3` driver; `s3-rdma` and `s3-tables` default to 4, and `spt run` passes 4), a request that selects a version whose ID needs percent-encoding (for example `v+1=:x`) is now signed with the decoded value, as V2 requires, while the URI still carries it encoded. It used to be signed encoded, so a strict target rejected it with 403. This affects a versioned READ, STAT and DELETE on the `s3` and `s3-rdma` drivers, and explicit-version requests (integrity manifest items): DELETE and explicit-version requests already failed this way before this release. Only requests a strict target rejected change; IDs that need no encoding, and V4, are unchanged. **Compatibility:** with versioning off, the only V2 requests this entry changes are those that carry a percent-encoded `versionId` (integrity manifest DELETE, presence and explicit-version requests), and a strict target rejected those before. Multipart and tagging requests sign their URI as sent, as before. Listings and an item whose name holds a query also sign differently, under **SigV2-signed S3 listings**.
- **Long requests on the Netty drivers no longer fail at the net timeout** — On the `s3`, `s3-rdma`, Swift and Atmos drivers, a single PUT, multipart part or GET (whole-object or `--range-size`) that took longer than `storage.net.timeoutMilliSec` (default 30 s) failed with `FAIL_IO` (`FAIL_TIMEOUT` for range reads) and a "Premature channel closure" warning, however steadily its bytes moved, and a request on a pooled connection that had sat idle could fail before the timeout. The timeout is now the inactivity timeout it is documented to be: a transfer that keeps moving never times out, and a request on a reused connection gets the full timeout. A silent response is now reported the timeout after the last request byte is handed to the socket, and an upload the target stops reading within twice the timeout of its last progress, instead of the timeout after the connection's last read. Bytes still in the socket buffers do not count as progress, so a target that takes longer than the timeout to read a body's tail from them is reported as a silent response. On `s3-rdma` the same timer covers the in-band HTTP requests and the RDMA transfers they carry: an RDMA transfer still fails after the timeout, now counted from its own request rather than from the connection's last read, which on a reused connection could come well under the timeout. Workloads whose requests all finish inside the timeout are unchanged, except that a request on a reused connection no longer fails early. `s3-aws` was not affected.
- **`s3-aws` reads split by `--part-size`** — `s3-aws`: reads split by `--part-size` now run as ranged GETs, instead of hanging without a request. A seeded `spt run read --s3-driver aws --part-size <size>` reads each object larger than the part size with one ranged GET per part, in parallel, and counts it once, with the object's size in bytes. As on `s3`, a split read ignores a requested version ID, and the bytes of parts that succeeded also count when the read fails. Since 5.9.0 the driver failed such a read before it sent any request, and the read step hung with no successes or failures. The workaround (`write --part-size <size> --save-items`, then `read --items-file`) is no longer needed. Reads not split by the part size, and every write, are unchanged.
- **V4 signing with `storage-net-http-uri-args`** — With `storage-net-http-uri-args` set, V4-signed object requests from the `s3` and `s3-rdma` drivers are now signed over the query they send, with parameters sorted by name; targets that check SigV4 refused them with 403 before. The README now lists which requests carry the arguments.
- **First-use versioning check** — The `s3` driver's first-use versioning check no longer throws and stalls the step when its `PUT ?versioning` times out; it warns that versioning could not be enabled, and the run goes on. That PUT is now signed with the bucket's own credential and carries the configured headers, and the bucket's versioning status is read by a hardened XML parser, whatever its namespace prefix, declarations or attributes.
- **Shutdown after a start failure** — After a start failure in which no run was submitted, `spt run` and `spt replay` no longer request shutdown on any host or report `Shutdown completed with warnings`. With `--attach-existing`, such a failure no longer shuts down the prestarted workers. With `--shutdown-on-complete` on (the default), they print `Auto-results: no run was submitted; nothing to shut down.` instead, and `spt_run_params.json` records `lifecycle.shutdown` as not started, with no error. A start that failed before the engine identity check (a missing image, or an engine API that never came up) has no results to summarize. It no longer reports `summary generation encountered issues`; it prints `Auto-results: no run was submitted; no results were produced.` and records `lifecycle.summary` as not started. On `spt run write-verify` and `read-verify` such a start still exits 1, and its final error no longer carries the `graceful shutdown: …` and `summary generation: …` clauses. A start the engine identity check rejected, or whose scenario submission the engine refused after the check passed, still writes its run summary, as before. A launch the engine accepted, including one kept only for cleanup, still requests shutdown on every host.
- **Shutdown after a start failure** — After a start failure in which no run was submitted, `spt run` and `spt replay` no longer request shutdown on any host or report `Shutdown completed with warnings`. With `--attach-existing`, such a failure no longer shuts down the prestarted workers. With `--shutdown-on-complete` on (the default), they print `Auto-results: no run was submitted; nothing to shut down.` instead, and `spt_run_params.json` records `lifecycle.shutdown` as not started, with no error. A start that failed before the engine identity check (a missing image, or an engine API that never came up) has no results to summarize. It no longer reports `summary generation encountered issues`; it prints `Auto-results: no run was submitted; no results were produced.` and records `lifecycle.summary` as not started. On `spt run write-verify` and `read-verify` such a start still exits 1, and its final error no longer carries the `graceful shutdown: …` and `summary generation: …` clauses. A start the engine identity check rejected, or whose scenario submission the engine refused after the check passed, still writes its run summary, as before. A launch the engine accepted, including one kept only for cleanup, still requests shutdown on every host, or with `--attach-existing` on the entry node only.
- **Attach runs leave their workers running** — A default `spt run --attach-existing` or `spt replay --attach-existing` no longer stops its prestarted workers: at the end of a run, normal or interrupted, `--shutdown-on-complete` now sends `/shutdown` to the entry node only, which ends its run, so the next run can attach to the same workers again. This includes a launch kept only for cleanup. Whoever started a worker stops it; there is no flag to have `spt` stop attached workers. An attach run with `--items-file` or another item file no longer copies it to the attached workers, which never used it, so it no longer leaves a `/tmp/spt-items-<nanos>/` directory on each of them. The progress line `Auto-results: requesting shutdown on all hosts...` now reads `Auto-results: requesting shutdown...` for every run. Runs without `--attach-existing` are otherwise unchanged.
- **Early stop of a duration DELETE** — A duration DELETE stopped by its failed-object budget names the budget as the cause, instead of reporting that its inventory ran out and advising `--seed-objects`. A duration DELETE whose engine or step is stopped under it before the deadline now reports that it was stopped before the requested duration, not that its inventory ran out. Both kinds of stopped run still fail. A run that truly runs out of inventory before the deadline still fails with the exhaustion message and the `--seed-objects` advice.
- **DELETE verification against a target that drops its `HEAD`s** — `spt run delete --validate-inventory` and DELETE post-verification no longer send a `HEAD` storm when every `HEAD` fails at once, for example when the target closes or refuses the connection. The verifier used to retry such an object every 10 ms for the whole `verificationTimeoutMillis` (default 30 s), each `HEAD` on a new connection: against a loopback target that closes every `HEAD`, more than 1,500 `HEAD`s per object in the 30 s window, now under 40. The first retry pass still follows the complete pass at once; later passes wait 10 ms, doubled per pass up to 1 s. Near the timeout the wait shortens, to no less than 10 ms, so the next pass starts about one pass duration before the timeout and an object that settles late in the window is checked again before it. The timeout keeps its meaning, and a phase that cannot resolve every object fails at it. A phase that ends with unresolved objects now logs one WARN with their count and the cause reported for one of them, given only as a category, such as `HTTP 503`, `no HEAD response (the connection closed or the response timed out)` or `connection failure (ConnectException)`, never as the exception text, URL or reason phrase; per-request details stay at DEBUG. For driver authors: verification calls `DeleteVerificationProbe.observe`, whose default calls `presence` once, so a driver that overrides `presence` keeps working as before; it can report a cause from `presence` with `DeleteVerificationCause.report`.
- **Local workers and bridge-mode verify with an advertised hostname** — A local worker of a distributed run with a remote entry, and a remote `spt verify --network-mode bridge`, can now start their engines. A bridge-mode engine whose `java.rmi.server.hostname` is the host's own address bound its RMI services through that address, which from inside the container comes back from the bridge gateway, and the registry refused it (`Registry.rebind disallowed; origin /172.17.0.1 is non-local host`), so the engine exited. Engines now bind and unbind their RMI services through the local registry on the loopback address and still advertise the configured hostname to callers. Host-mode engines behave as before, unless a host firewall drops loopback traffic to the registry port, where an engine now waits at start instead of binding.
- **`spt run` and `spt replay` `--network-mode` check** — `spt run` and `spt replay` refuse a `--network-mode` other than `host` or `bridge` with verify's message `network-mode must be 'bridge' or 'host', got: <value>` and exit status 1, before any port check, archive fetch, container or host connection. The values are matched case-insensitively, and surrounding spaces are ignored, so `Host`, `HOST` and ` host` still run in host mode and `Bridge` runs in bridge mode with its warning; the local route, the remote entry and the remote nodes all use the same normalised mode. A typo such as `hots` used to start the engines in bridge mode without a warning. `host`, `bridge` and the default behave as before. `spt verify` still accepts only exactly `host` or `bridge`. **Compatibility:** an explicit empty value and a bad value given with `--generate-only` are now refused; `Bridge`, `BRIDGE` or ` bridge` with `--interfaces` or `--host-interfaces` is now refused, as `bridge` already was, and those spellings now print the bridge warning on remote routes too.
- **Port checker engine detection** — The CLI's port checker now recognises a running engine by its own API responses, not by the Jetty error page (the Docker container lookup is unchanged): its `/metrics/json` probe accepts the current `metrics_schema` payload, and its `/run` probe accepts the engine's "Invalid run ID format" answer. It used to match a current engine only through the "Powered by Jetty" footer (and on Jetty 9.4 the servlet row) of the error page, so an engine on a newer Jetty, or one that hides its Jetty version there, would not have been recognised as SPT. A generic Jetty 400 page on `/run`, and an empty body (`[]`, `[ ]` or `null`) on `/metrics/json` or `/metrics`, no longer count as SPT: no engine sends them, and any other service that did was labelled an SPT service and, without an interactive prompt or with `--force`, sent `DELETE /run`. Every engine from v5.10.0 on is still detected.
- **Groovy and Python scenarios without their script engine** — A `.groovy` or `.py` scenario run with `--run-scenario` now fails, exit 1, with a message that the Groovy or Python script engine is not installed and that its JSR-223 engine jar goes in `ext/` next to `spt.jar`, pointing to the scenario docs. It used to run as JavaScript and stop on a JavaScript syntax error. The SPT image ships no Groovy or Python engine; JavaScript scenarios and files with any other extension or none still run as JavaScript. The reference Dockerfiles that add these engines now download from `repo1.maven.org`, and the shipped `groovy/types/weighted.groovy` and `py/types/weighted.py` examples use current configuration names (`load.op.weight`, `load.op.recycle.mode`, `load.op.type`, `storage.driver.limit.concurrency`). **Compatibility:** a `.py` or `.groovy` file that happened to be valid JavaScript, such as the shipped `py/default.py`, used to run as JavaScript and now fails without an engine in `ext/`. Without its engine, a missing `.groovy` or `.py` file now reports the missing engine instead of `Failed to read the scenario file`; both exit 1.
- **`spt run --api-port` on distributed runs** — `spt run --api-port` now works for distributed runs; the engines previously started on 9999 and the run timed out waiting for the requested port. The entry and every worker now serve the requested port, and so does a distributed `spt replay`.
- **Remote entry on a bridge network** — A distributed `spt run` or `spt replay` with `--network-mode bridge`, and a multi-host LIST run with a remote first host, now publish the remote entry node's API port, as a lone remote engine and a local entry already do. Since v5.11.0 the entry started without it, and the run failed at the entry readiness wait. Only the API port is published; remote workers stay on host networking. Host mode, the default, is unchanged.
- **`spt run` and `spt replay` `--api-port` range** — `spt run` and `spt replay` refuse an `--api-port` that is not a whole number from 1 to 65535 before starting any engine, with `--api-port must be between 1 and 65535, got <value>` and exit 1; such a value used to start the engine and fail after the 60 s API wait. The value must be plain decimal digits, so a signed value such as `+20041` is refused too; a leading zero is accepted, and `09999` runs on 9999. `--generate-only` now checks the value as well.
- **Concurrent runs on one remote host** — Two runs that started the same role (engine, worker or entry) on the same remote host in the same second got the same container name, and the second `docker run` failed. Remote container names now carry the time to the nanosecond.
- **Runs on one remote engine** — An `spt run` or `spt replay` that runs on a single remote engine (one `--test-hosts` entry, or several where only the first connects and `--min-hosts` allows it) now stores its driver statistics in `spt_run_params.json`; 5.17.0 recorded a `driverStatsError` there instead. A standalone DELETE there, seeded or from `--items-file`, now exits 0 after a clean delete; from 5.15.0 it exited 1 with "metric contributor identity is unavailable before execution starts". A real failure there no longer carries that reason as an extra cause.
- **`spt verify --api-port`** — `spt verify` now starts its test engine on the `--api-port` port, and publishes that port in bridge mode, so verifying on a port other than 9999 can pass. Verify used to check a port its engine never served, and fail after 30 seconds with `Ports not accessible`. An `--api-port` outside 1-65535 is now rejected.
- **Concurrent `spt verify` runs on one host** — `spt verify` no longer stops another invocation's running verify container on the same host. Before it starts its own container, and again after it removes it, verify now removes only running verify containers that are at least 15 minutes old and that it did not start; it used to remove every running container labelled `spt.verify=true`. Verify containers now carry an `spt.verify.run` label with the id of the `spt verify` invocation that started them; a container from an older CLI, without that label, is judged by its age alone. Each removal's log line now gives the container's age.
- **`spt verify` port wait** — When the port wait times out, verify now names only the ports it last saw closed and lists any port it got no result for; when every port was seen open but never all in the same round, it says so. It used to report every port closed, including an RMI registry that was open.
- **`spt replay` exit status after a terminal failure** — `spt replay` now exits 1 when the engine ends its scenario FAILED, whichever step failed, and names the failed step and the engine's cause, as `spt run` does. A replay whose only step failed this way still left results for that step, so it printed `Results fetch encountered errors`, an empty phase table and `Create metrics unavailable (status: partial)`, and exited 0. A replay whose steps all finished still exits 0 when the results fetch is incomplete.
- **`spt replay` launch-script flags** — `spt replay` now warns once in its preflight about the `--storage-*` and `--load-*` engine flags on the archived launch script that it does not keep, naming them without their values, for example `replay does not keep these launch-script flags: --storage-targetBucket-provision, --storage-targetBucket-count`. The warning is also recorded in the `diagnostics` of `replay-metadata.json`. It used to drop them with no warning.
- **`spt replay` refusal of a JavaScript `storage.targetBucket`** — When an archived JavaScript scenario mentions `storage.targetBucket`, `spt replay` now says that covers a bucket count, a bucket list or the provisioning setting, and that you can replay a JSON archive or remove the setting from the archived scenario. It used to say "a bucket count or list", which was wrong for the `"provision": false` setting that `spt run` writes into most of its own scenarios. Replay still refuses these archives, with the same failure class.
- **SSH commands and copies that outlived their deadline** — A command or file copy over SSH now returns within a second of its deadline when a jump-host or helper process keeps its output open. On a ProxyJump route to a host that stopped answering, `spt run` and `spt verify` could wait until the connection itself timed out, which after a network loss can take many minutes, and a stalled `scp` could likewise wait past its deadline. A command that succeeded but left such a process behind now returns at most 1 second after it exits, and a remote log stream that ends cleanly no longer warns that it dropped and reconnects.
- **Large item files on remote hosts** — An item file from `--items-file`, `--read-items-file` or `--delete-items-file` no longer fails its copy to a remote host after 30 seconds, which stopped the run before it started whenever the list took longer than that to copy: the copy now runs as long as it needs, and `spt run` prints one line per host with the files' size before it starts. A stalled or stopped copy ends with a message that names the copy and host and says why, instead of `signal: killed`, and when the host still answers, the remote staging directory is then removed without a second `context deadline exceeded` error.
- **Failed starts with item files** — A start that fails while it copies item files to a remote host now rolls back once. It used to roll back twice, each time with its own 30-second limit, so a host that no longer answered could delay the error by a second pass, and each cleanup error was reported twice. A start with item files whose `mkdir` of the remote staging directory is cut off by its timeout or a cancel no longer leaves an empty `/tmp/spt-items-*` directory on the host: the rollback now removes it.
- **Failed remote starts that left a container or directories behind** — A remote engine start that fails after it has created something on a host now has it removed, by the start's rollback, or at the end of the run when the run goes on without that host. A worker or entry whose container started but failed its API readiness check used to keep running after `spt run` exited with the start error, and a worker that failed it in a run that went on with the other workers kept running after the run. With `SPT_JAVA_OPTS` set, a failed start could leave its `/tmp/spt-items-*` staging directory and its `/tmp/spt-diagnostics/<run>/<host>/<role>` directory on the host; both are now removed, and the empty `<run>/<host>` directories above it stay, as after a successful run. Three cases still leave something behind: a `docker run` cut off after Docker created the container, whose ID the CLI never got; a directory whose `mkdir` ran on the host but whose SSH command failed for another reason before the start's time limit, which the CLI treats as never created; and a host that no longer answers, where the removal fails and is reported.
- **Count-limited runs on several engines** — A count-limited run no longer leaves an engine without a count, which that engine read as no limit. When the count is at least the number of engines but the split left one of them at 0, the count is now split evenly: `--object-count 4` on three engines runs 2, 1 and 1 operations, where the third engine used to run without a limit until stopped. Splits that already gave every engine a count are unchanged. These count-limited runs now fail before the step starts, with exit 1 and a reason that names the fix:
  - A count below the number of engines, such as `--object-count 1` or `--seed-objects 1` on two `--test-hosts`. One engine used to run without a limit, and an `spt run list` exited 0 having listed a different number of objects than it asked for.
  - An `spt run tables` on two or more engines that provisions its table, or that runs the `compaction` test vector, whose poll is a step of one operation. These runs already hung, because the second engine ran its one-operation step without a limit. A `tps` run with `--no-provision` runs only for a duration and is unaffected, and a `catalog` run with `--no-provision` fails only when `--namespace-count` times `--tables-per-ns` is below the number of engines.
  - A count-based read from an items file with fewer items than engines. It used to hang.
  - A scenario run directly with a count below the number of engines, including one that used to finish with a different number of operations than it asked for. A weighted or pipeline step checks each sub-step's count and any items file the sub-step reads, and a mixed step the count and items file it runs with; a count or items file that no operation uses is split as before.

  Duration runs are unchanged: a `--duration` read from an items file with fewer items than engines still exits 0. A count-based read whose item input path lists no objects still hangs, as it did before.

- **Failed DELETE error** — The final `Error:` of a failed DELETE run states the failed step and the DELETE verdict once each, on one line when auto-results are on (the default). It could repeat the step's reason and the verdict after `run also failed:`, over two lines, when the CLI's status check saw the failure first.
- **Traced DELETE** — `spt run delete` with op tracing on (`output.metrics.trace.persist=true`, from `--engine-override` or `SPT_ENGINE_OVERRIDES`) now fails before it starts, saying tracing isn't supported for standalone DELETE. It failed with only "failed to start metadata-mode step slice 0", after a seeded DELETE had written its seed objects.
- **`--help` on the engine** — `--help` and `-h` on the engine, the image and `run.sh` now print the engine's options, with their value types and aliases, to standard output and exit 0, without starting anything or writing files. They used to start the default scenario, on the mock driver or on the target the other arguments named, and run until stopped.
- **Invalid engine arguments** — An engine argument that cannot be applied now stops startup with exit status 2 before any load: an unknown option such as `--dry-run`, an argument without `--`, a value of the wrong type or not a number, and an option the engine no longer takes. The engine used to log the error and run anyway with the settings applied before it, which could send load to a configured target. `--storage-driver-remote` is refused the same way, with an explanation: SPT has no remote driver services, so start each `--storage-driver-addrs` host as a worker engine (`run.sh --run-node=true`); the engine you start also runs its share of the load. The getting-started, recycling, item naming and S3 versioning docs used invalid flags and are corrected. **Compatibility:** a command with an invalid flag used to run, wrongly, and now fails with exit 2. This includes Mongoose 3.x options that SPT has no name for, such as `--load-limit-count` (SPT's is `--load-op-limit-count`) and `--storage-net-http-namespace`; `--storage-driver-remote`; `--load-op-recycle=true` (use `--load-op-recycle-mode=true`); and the old aliases `--load-circular` and `--load-generator-recycle-enabled`, whose target is not a setting. A worker started with `--restart unless-stopped` restarts in a loop on such a flag.
- **Boolean values other than true or false** — A boolean engine setting now takes only `true` or `false`, in any case. Any other value, such as `yes`, `1` or an empty value, is refused: on the command line with exit 2, in a scenario's `Load.config(...)` or `.append(...)` as a scenario failure, and as a string in a defaults file or in the defaults of a run request, which the node answers with 400 and a message naming the setting. Such a value used to read as false without a word. A boolean option given with no value, such as `--run-node`, still means true. **Compatibility:** a command, scenario or defaults file that set a boolean to anything else now fails. This includes `spt run --engine-override load.op.shuffle=no`: the CLI sends `yes`, `no`, `on` and `off` as text, so `yes` read as false, and the run now fails to start with `status 400` and that message; give `true` or `false`. Unquoted `yes`, `no`, `on` and `off` written in YAML the engine reads, such as an extension's defaults file, still read as booleans.
- **Unlimited steps on several engines** — An engine running a step with neither a count nor a time limit, such as an `spt run list` without `--duration`, no longer reports `test_state` 2 (Completed) in `/metrics/json`, `/metrics/cluster/json` and `/metrics/fleet/json` during a momentary gap between operations. Such a step reports 1 (Running) while it is active and 2 only once it has ended. A multi-host unlimited step can therefore no longer be ended by the first engine that goes idle; with `--auto-results=false` that could stop the other engines mid-step. Time- and count-limited steps are unchanged. The Prometheus endpoint `/metrics` now follows the same rule for its active series (see the `spt_test_state_value` entry). **Compatibility:** a tool of your own that reads `test_state` from these JSON endpoints no longer sees 2 for an unlimited step while it runs; after the step ends, 2 comes from its retained terminal row for `api.linger.sec` (default 20 s), so with `--api-linger-sec=0` an unlimited step never reports 2.
- **Prometheus `test_state` gauge mid-step** — The Prometheus `/metrics` gauge `spt_test_state_value` now follows the rule of the JSON endpoints' `test_state`. An active step reads 2 (Completed) only once every limit it has (count, time) is reached, and a step with neither limit reads 1 (Running) while it runs; its end shows as the series ending. Before, it read 2 whenever no operation was in flight, which was most of the time on a rate-limited step and could happen on any step in a moment when nothing was in flight. A dashboard or alert of your own that keys on 2 no longer fires mid-step.
- **Exit status after a start or scenario failure** — The engine now exits 1 when its node fails to start (`Run node failure`, for example when the API port is taken), when the scenario file is missing or cannot be read, when the scenario has a syntax or configuration error, and when the defaults fail to load. It used to log the error and exit 0. A run that ends normally still exits 0. The engine's exit statuses are now 0 for success, 1 for a run, start or scenario failure and 2 for an argument error; `--help` lists them. **Compatibility:** a script or check that took exit 0 as success now sees these failures. A node logs its scenario's failure and keeps running. Its `/status` reports a typed terminal failure as `FAILED` and, as before, any other scenario failure as `COMPLETED`, including a boolean refused in the scenario.
- **Exit status after a start or scenario failure** — The engine now exits 1 when its node fails to start (`Run node failure`, for example when the API port is taken), when the scenario file is missing or cannot be read, when the scenario has a syntax or configuration error, and when the defaults fail to load. It used to log the error and exit 0. A run that ends normally still exits 0. The engine's exit statuses are now 0 for success, 1 for a run, start or scenario failure and 2 for an argument error; `--help` lists them. **Compatibility:** a script or check that took exit 0 as success now sees these failures. A node logs its scenario's failure and keeps running; its `/status` reports the failure as `FAILED` (see **A failed scenario on a node**).
- **A failed scenario on a node** — When a scenario posted to a node fails, the node's `/status` now reads `FAILED`, with the category `configuration` or `execution` and a message naming the cause, instead of `COMPLETED`. A syntax error in the posted scenario text is a `configuration` failure, and so is a setting that `Load.config(...)` or `.append(...)` refuses: an unknown or malformed option, or a bad boolean, list or number. Other failures are `execution` failures: a JavaScript `throw`, a failing Java call, and a call the step refuses before it reads the settings, such as `Load.config(null)` or `config(...)` after `append(...)`. For these failures the engine writes the message and never quotes the scenario, which may hold a credential: it gives the line and column of a syntax error, names a refused boolean setting without its value (`invalid boolean value for "load-op-shuffle"; give true or false`), and names an unknown or malformed option only by the part of its path that the engine defines (`invalid configuration option under "load-op"`, or `invalid configuration option` when no part is defined); otherwise it gives only the type of the failure. The details stay in the node's log. The node keeps running, as before. A typed terminal failure, such as a missing items file, keeps its own category and message, which may name a setting such as the items file's name; a valid scenario still reads `COMPLETED`, and a run stopped with `DELETE /run` still reads `STOPPED`. **Compatibility:** a script that posts scenarios to a node and takes `COMPLETED` as success now sees these failures, and `spt run`, the TUI and `spt replay` show them. `spt run list` can now fail, with exit 1, when its step's await or close fails; it used to exit 0. A refused setting in `Load.config(...)` or `.append(...)` now reaches the scenario as `com.dell.spt.base.config.ScenarioConfigurationException`, with the original exception, such as a `java.lang.NumberFormatException`, as its cause and the same message: a script or Java caller that catches the original type, for example with `e instanceof java.lang.NumberFormatException`, no longer catches it and now fails; test `e.getCause()` instead.
- **The `linux/arm64` image and arm64 JDKs** — The `linux/arm64` SPT image, and `run.sh` and `run.bat` with an arm64 JDK, now start: `-XX:UseAVX=2` is passed only to x86 JVMs. From 5.5.0 to 5.17.0 an arm64 JVM refused the option and exited.
- **Bundle launcher options** — `run.bat` now passes `-XX:+UseNUMA` and the RMI response timeout, as `run.sh` and the SPT image do. `run.sh` sets `GLIBC_TUNABLES=glibc.malloc.hugetlb=1` unless the caller has set `GLIBC_TUNABLES`, as the image does.
- **Signals sent to `run.sh`** — `run.sh` now replaces itself with the JVM, as the SPT image's entrypoint does, so a signal sent to `run.sh` stops the engine. **Compatibility:** the process now shows as `java ... spt.jar`; match `spt.jar`, not `run.sh`, to find it.
- **The bundle's Docker Compose example** — The `spt-weighted` service of the engine bundle's Docker Compose example no longer selects G1 on top of the image's ZGC, which stopped its JVM with `Multiple garbage collectors selected`.
- **`netty-mock` driver under load steps** — The netty-mock driver no longer overflows the stack under load steps: time-limited steps end on time, and count-limited steps no longer hang.
- **Driver close on an interrupted thread** — A storage driver closed on an interrupted thread now completes its close, instead of leaving its event loops or I/O workers running; from 5.15.0 such a close threw an `InterruptedException` partway through. The close takes no longer than a close on an uninterrupted thread, and the thread stays interrupted.
- **A `mixed` step of only writes and deletes** — A `mixed` step with GET and STAT weights of 0 no longer needs seed items to start. Without an items file it failed at start with `Seed items list must be non-null and non-empty`, from 5.8.0. A mix with GET or STAT still needs at least one seed item on each engine.
- **A count-limited `mixed` step** — A `mixed` step with `load-op-limit-count` now runs exactly that many operations on every shipped driver, and in a distributed step its slices run that many between them. It ran more, from 5.8.0: with a fast driver, every operation dispatched before the step saw the count, such as 4,049 for a limit of 4,000, or 19 for a limit of 1. The totals, the split by operation and the step's bytes and duration change for such a step; its steady-state rates and latencies don't. The step ends once each of its operations has published its final result, a multipart upload after its last part and its completion, also when that result is not counted, such as an interrupted operation. Some operations are still sent but not counted, as before, so such a step reports fewer operations than its count: on `dummy-mock`, a CREATE or READ of an object larger than `item-data-ranges-threshold`; and on every driver, an interrupted operation. A multipart upload whose part a cooperative driver cannot queue within 30 s publishes no final result, so a step holding one waits for its time limit, or without one until it is stopped. A multipart upload that the `fs` driver aborts after a part runs out of retries never ends either, when the upload had more parts than it sends at once, with the same effect. A `mixed` step without a count limit is unchanged; a count of 9223372036854775807 (`Long.MAX_VALUE`) is no limit, as 0 is. `spt run mixed` sets a count only through an engine override such as `--engine-override load.op.limit.count=N`. For driver authors: a step caps its operations at its count only on a driver whose new `StorageDriver.compositeResults()` returns `CompositeResults.IN_PARTS` (a multipart upload's initiation and parts come before its final result, as on every driver built on the cooperative base, which declares it) or `CompositeResults.ONE_RESULT` (one result for each operation, as on `dummy-mock`). The default, `UNDECLARED`, keeps the step as before, running past its count, and the step logs this once at its start; a driver decorator must return the value of the driver it wraps. A load generator ends such a step through the new `LoadGenerator.isCountLimitDrained(long)`, which is `false` by default.
- **Warnings in `errors.log`** — Warnings in `errors.log` are no longer dropped when debug lines reach the rate limit. Debug and info messages keep their own limit of 1,000 messages per 10 s, so `errors.log` can grow up to twice as fast when both limits are reached.
- **Paged path item input on the `s3` driver** — A path item input over more than one listing page no longer stops after the first page or repeats it, on the `s3` driver and on the drivers that inherit its listing, such as `s3-rdma`. Each next page started after the last item's whole name, `<bucket>/<key>`, instead of its key, so a copy-mode step could copy only the first page and exit 0, or list the first page again without end. Only an `item-input-path` engine override or a direct scenario reaches it.
- **`s3-aws` copy mode** — An `s3-aws` copy-mode step whose item input path is a bucket, such as `/src`, now copies each listed object, instead of failing every copy with not found. Each copy read one object named after the source bucket, in the driver's own bucket, instead of the listed object in the source bucket. Each copy lands under `<source bucket>/` in the target bucket, as on the `s3` driver; see [Copy Mode](engine/core/spt-base/doc/design/modes/copy_mode/README.md#231-s3-objects-copying). A source path that names an object, such as `/src/k0`, still copies that one object to every item. Only an `item-input-path` engine override or a direct scenario reaches it.
- **A false error line for every multipart write** — The HTTP-based S3 drivers no longer log "Request is finished (…) after the response is started (…)" in `errors.log` for each multipart upload and each retried part. Successful requests are timed as before; only failed ones change. In `op.trace.csv`, a multipart completion, abort or part retry that was never sent, for example because its connection failed, now has a blank start and latency and an epoch-sized duration, like any other request that never started, where it carried the earlier exchange's start and latency; it now also logs the DEBUG "Response is finished while not started" line in `errors.log` that other unsent requests log. In the multipart log (`parts.upload.csv`, fetched as `<step>.multipart.csv`), a completion or abort that had a connection but no response now has a latency of 0 instead of a stale value, usually negative. That log has no row for an unsent completion or abort, or for a failed part attempt, so those show only in `op.trace.csv`.
- **`s3-aws` listed keys with a slash** — Items that the `s3-aws` driver lists from a path item input now carry their bucket, as on the `s3` driver. A READ, STAT, UPDATE or DELETE of a listed key with a slash, such as `dir/sub/k`, used to take `dir` as the bucket: it failed, or, when a bucket `dir` existed, acted on that bucket, so a DELETE could remove objects from another bucket and count them a success. An `s3-aws` copy-mode step now lands each copy at `<target bucket>/<source bucket>/<key>`, as the `s3` driver does, and a listed key whose first segment is a bucket's name, such as `src/k0` in bucket `src`, is now copied from that key. In an items file written by such a step, a READ, STAT or DELETE of a key with a slash now writes `/<listed bucket>/<key>` where it wrote `/<key>`, and a copy writes `/<target bucket>/<source bucket>/<key>`. Only an `item-input-path` engine override or a direct scenario reaches it.
- **Copy sent again reads its source** — On the `s3`, `s3-rdma` and `swift` drivers, a copy that is sent again, by recycle mode (`load.op.recycle.mode`) or by `load.op.retry`, now reads the source object its first attempt read. Before, every attempt after the first asked for the source at the destination name under the source path, such as `/src/dst/src/k0` for `/src/k0`: it failed with not found, or, where such an object existed, copied it. A copy-mode step in recycle mode copied each object once and then failed every later copy; a copy retried after a retryable failure failed the same way. Each attempt reuses the source path the driver resolved for the first one, so a driver that overrides the path resolution gets its own source on every attempt. The `s3-aws` copy mode fixed above (**`s3-aws` copy mode**) keeps its source the same way. The first attempt, the destination, every other operation type and the `fs` driver are unchanged. Only an `item-input-path` engine override or a direct scenario reaches copy mode.
- **`s3-aws` multipart part retries** — A failed part of an `s3-aws` multipart upload was never really retried: no retry was ever sent. Before 5.15.0 the retry was dropped, with an ERROR "I/O worker failure". From 5.15.0 each of its 3 retries failed at once with `FAIL_UNKNOWN`, the step logged an ERROR "I/O operation invocation failure", and the upload was aborted. The retries are now sent. An upload whose part fails once now completes, and that part gives one failure row instead of four. A part that keeps failing now sends its 3 retries to the target, so an upload against a failing target takes longer to abort.
- **S3 drivers kept in memory after they close** — The `s3` and `s3-rdma` drivers and the `s3-tables` control plane no longer stay in memory after they close when they signed requests on a long-lived engine thread, such as the scenario thread that checks target buckets. With the image's default JVM settings, each such driver kept about 24 MB, and a step can keep more than one: one per distinct storage configuration, plus any driver that listed input items or discovered prefixes. Long multi-step scenarios and engines reused for many runs could fill the default 4 GB heap after about 170 kept drivers, which is fewer steps when each step keeps several.
- **A step id that an earlier step already used** — A CREATE or READ step whose `load.step.id` an earlier step already used in the same log directory now fails at its start with exit 1 and `step id "<id>" is already used in this log directory (<file> exists); give each step its own load.step.id`. From 5.15.0 it ran its whole load and then failed at close with `stale node source exists`. In a distributed step the Entry Node also tests every other node's files, through the file service it already uses, and counts the engine: `engine <n> of <m>: step id "<id>" is already used in that node's log directory; see the entry's log`; the Entry Node's log names the node's address and the file. A step with a configured id tests the Entry Node's files before it provisions any target bucket; every test runs before the step writes its `engine.build.json`, distributes any item or starts any slice. A file that a node cannot test, because it is denied or the node's file service fails, refuses the step the same way, with exit 1 and an `execution` failure: `engine <n> of <m>: step id "<id>" could not be checked in that node's log directory; see the entry's log`, or `step id "<id>" could not be checked in this log directory; see the engine log` for the Entry Node's own files; the node, the file and the cause are in the engine log. So a refused step runs no load on any node. The other nodes are reached only after the target-bucket checks, so a step refused for another node's file may already have created missing target buckets. Each node tests its own files again when its slice starts, before it writes any of them. The same refusal covers a partial-read step, a step with a NIC set, whatever its operation, and a metadata-mode step's integrity logs, and keeps its `configuration` category in metadata mode; a metadata-mode step whose item output file an earlier step already published now fails at its start too, naming the file, instead of at close with `stale completion record exists`. The earlier step's files, its `engine.build.json` and `event.loops.json` among them, are left as they were; only the refused step's own messages are appended to `messages.log` and `errors.log` in that folder. UPDATE, DELETE, LIST and NOOP steps without a NIC set or metadata mode still run when they reuse a step id. **Compatibility:** legacy scenarios and reruns that reuse a step id in the same log directory still fail, now at step start: give each step its own `load.step.id`. The shipped endurance examples (`js/endurance/infinite_loop_test.js` and `parallel_pipeline_and_infinite_loop_test.js`) now do. A step with a NIC set used to run and only warn when its NIC files could not be written; it now fails at start like the others. `spt run` gives each step its own id and is not affected.
- **SigV4 signing with more than one secret** — S3 requests signed with SigV4 now use the right key when one driver uses more than one secret, for example several entries in `storage.auth.file`. Each signing thread used the first secret's key that day for every secret, so a target that checks signatures rejected the other secrets' requests, and a target-bucket check with another credential reported the bucket as not accessible. - **Cleanup DELETE with `--part-size`** — A DELETE step on objects larger than `--part-size` (engine `item.data.ranges.threshold`), such as the step that `--cleanup` adds, now sends one DELETE per object, counts it, and ends. Since 5.6.0 the step counted none of them and never ended, so the run needed an external kill. On `s3` the DELETEs were sent and the objects deleted; the `fs` driver's DELETE step hung the same way; with `--s3-driver aws` (since 5.9.0) the step sent a whole-object PUT for each object instead of a DELETE, so the objects were left in place. Only CREATE and READ are now split into parts above the threshold; every other operation type runs as it does with no threshold:
  - On `s3`, UPDATE, STAT and NOOP steps above the threshold hung the same way and now complete.
  - On `s3`, an UPDATE with `item.data.ranges.random` or `item.data.ranges.fixed` and a threshold logged `IllegalArgumentException: Not supported - both byte ranges configured and size threshold` over and over and sent no request; it now runs as a ranged UPDATE. A READ or CREATE with byte ranges and a threshold is still refused.
  - On `fs`, an UPDATE above the threshold now writes each object once, as one plain UPDATE, and reports the object's size; it used to write the parts and then the whole object, and reported twice the size.
  - With `--s3-driver aws`, an UPDATE above the threshold sent whole-object PUTs and counted none of them as succeeded; it now takes the driver's ordinary UPDATE route, which writes the object again (see the `s3-aws` UPDATE entry).
  - A `mixed` step with a threshold now counts its DELETE and STAT results above the threshold, which it sent and then dropped.
  - The warning "Multipart upload threshold is set … but batch size is …" now appears only for CREATE and READ steps, the ones split into parts; a DELETE, UPDATE, STAT or NOOP step with a threshold and a batch size above 1 no longer logs it.

  **Compatibility:** the output of these completed workloads changes: `fs` UPDATE byte counts, the DELETE and STAT counts of `mixed` steps with a threshold, and `s3` UPDATE with byte ranges and a threshold, which now runs. Only an engine override of `item.data.ranges.threshold` or a custom scenario reaches them; the CLI never passes a threshold to those steps.

A failed upload now counts as one failure, whether its initiation, a part or its completion failed. An upload whose initiation failed used to count nothing, so a count-limited step ran to its time limit. - **A step's end after an aborted multipart upload** — A multipart upload aborted after a part ran out of retries no longer holds its step's end for `load.op.wait.limit` (30 s by default) or leaves it unresolved in `operation.lifecycle.csv`. At concurrency 2 or more, a part of the upload that failed after the abort was still retried, and its retry restarted the ended upload's lifecycle, so a count-limited step reached its count and then waited out the limit. Once an upload is aborted, its other parts are no longer retried, and a part that a successful sibling fetched just before the abort is dropped instead of restarting the upload when it is queued after the abort. Counts were already right and are unchanged, and a step without part failures is unchanged.
- **Parts of an aborted multipart upload left unsettled** — A part of a multipart upload that was still waiting to be sent when the upload's abort ended, or was ending, the upload is now dropped unsent and counted as unattempted in `operation.lifecycle.csv`. Its dispatch was refused, but nothing settled it. At the head of the driver's dispatch queue, such a part kept the dispatcher busy on one CPU offering it again, and the operations queued behind it did not run, at least while the abort's result was being published and, once the abort had ended, until something else let the part through. On `s3` and `s3-rdma` with a NIC set, a part whose connection arrived while the abort's result was being published, or after the abort had ended, gave back its connection and permit but stayed queued in the step's operation lifecycle until the step stopped. It needs a part still queued when the abort ended, which a full input queue (`driver-limit-queue-input`) makes more likely, with any number of parts against the part window. It was reproduced in unit, stress and loopback tests, not in a step: among them a part that a successful sibling queued just before the abort, and a two-part upload on two NICs.
- **Multipart writes with `load.op.retry=true`** — A multipart write with `load.op.retry=true` no longer stalls after a part fails. A failed upload is now retried as a whole, from a new initiation with all its parts, as documented. The part used to be retried as an extra part of its upload, which then never completed and held the step until its stop. An upload aborted after a part ran out of retries now ends with the status of the first part that did, including in the operation trace, whether the abort is answered, refused or cannot connect, so it is retried only when the part's failure is transient: a part the target refuses for good, for example with 403, fails its upload once. It used to end with `FAIL_UNKNOWN` after an abort the target answered (on `s3`, also one it refused), and otherwise with the abort's own failure, such as `FAIL_IO`. On `s3`, a failed initiation now keeps its own status, so a throttled one (503) is retried too; on a connection's first initiation it used to be reported as `RESP_FAIL_NOT_FOUND`, which is never retried.
- **Stale upload ID on a reused `s3` connection** — On the `s3` driver, a multipart initiation answered without an upload ID no longer takes the previous upload's ID on a reused connection. A successful answer without an ID is now `RESP_FAIL_NOT_FOUND` on every connection, as it already was on a connection's first initiation, instead of sending its parts to the previous upload. A failed initiation keeps its own status and no longer stores the previous upload's ID or writes an `INIT` row with it to the multipart log (`parts.upload.csv`, fetched as `<stepID>.multipart.csv`). Real S3 targets answer each successful initiation with its own ID, so only a target that leaves it out, or a failed initiation on a reused connection, was affected.

The file used to hold every argument as given. A node also serves that file at `GET /logs/<step_id>/Cli`. Argument names, their order and every other value are unchanged, an empty value or an argument without `=` is logged as given, and the run still uses the real values. Values in `storage.net.http.uri.args` are not masked. Only arguments on the engine's own command line reach this file (the jar, `run.sh`, `docker run <image> ...`); `spt run` passes no credentials there. The step `config.yaml` now also masks those five header values under `storage.net.http.headers`, wherever they were set (command line, scenario `config` block, posted defaults or a defaults file) and for every run, `spt run` included; it already masked the credentials.
- **Credentials in a node's `GET /config`** — A node's `GET /config` now shows the storage credentials (`storage.auth.uid`, `.secret` and `.token`) and the values of the `Authorization`, `Proxy-Authorization`, `Cookie`, `x-amz-security-token` and `X-Auth-Token` headers under `storage.net.http.headers` as `***`, in YAML and JSON, as the step `config.yaml` does. It used to return them in clear. An unset or empty value and every other value are unchanged, the node keeps the real values, and `GET /config/schema` is unchanged. SPT itself does not read `GET /config`. A client that posts a `GET /config` response back to `POST /run` as `defaults` now sends `***` as those credentials and headers, so it must set them itself.
- **Completion of multi-host steps with several operation types or differing limits** — On more than one host, the CLI now shows a step with several operation types as completed, and prints "Test COMPLETED", only once every operation type has completed on at least one engine. It used to do so once any one operation type had. Every `spt run` mixed workload on several hosts is such a step. Separately, when the engines of one step report different limit types (for example one engine an operation count and another no limit), the CLI now treats the step as having no limit and waits until every engine has completed it. Each UPDATE of an item named `/<bucket>/<key>`, as an `s3-aws` write's items file records it, or of an object listed from an item input path, was sent as a copy from an object named after the bucket in the driver's own bucket, and failed with not found. No `spt run` workload runs an UPDATE; an archived `UpdateLoad` in `spt replay`, an engine `--load-op-type=update` or a direct scenario reaches it.

- **Multipart completion answered 200 with an error** — The `s3` and `s3-rdma` drivers now treat a multipart completion answered `200 OK` with an S3 `<Error>` body as failed, abort the upload, and count it as a failure. Only transient error codes (`InternalError`, `ServiceUnavailable`, `SlowDown`, `RequestTimeout`, or a missing, empty or truncated code) are retried under `load.op.retry=true`, as a whole upload. Before, it counted as a written object and the upload was left open, so a later read of it failed. Each step's `errors.log` names each such error code once, for at most 16 codes (once per sub-load in a weighted, mixed or pipeline step); a missing code is logged as `(missing)`, and a code that is not a plain S3 code name of at most 64 characters as `(unreadable)`. - **Multipart aborts at the end of a step** — On the `s3` drivers, the abort that follows a failed multipart completion near the end of a step is now read to its answer, within its own time bound (5 s from when the abort was sent, so that a worker's stop, with every abort sent before it, stays inside the entry node's 10 s RMI response timeout), before the driver's connections close. Before, an abort answered late was logged as "Response timeout", recorded as failed, and held the step's close for `storage.net.timeoutMilliSec` (30 s by default), or hung the scenario with `storage.net.timeoutMilliSec=0`. A step that ended by its count right after such a completion could also stop its connections before the abort was sent: the upload stayed open on the target and, in an integrity run, was recorded `failed_orphaned`. The wait now falls inside the step: when such an abort is pending, whole-step `StepDuration`, `TPAvg` and `ConcurrencyMean` include it. Steady-state figures do not change. The driver's close no longer waits without bound for such an abort: it waits at most twice `storage.net.timeoutMilliSec` plus 1 s (60 s when the timeout is 0), then records the upload `failed_orphaned` in `multipart.lifecycle.csv` and logs one warning with the count. On the HTTP drivers (`s3`, `s3-tables`, `swift`, `atmos`), a synchronous control request (the bucket check, versioning check and bucket creation, listings, delete verification, and the aborts above) whose connection closes without a response now ends at once and logs "Connection closed before the response"; before, it waited `storage.net.timeoutMilliSec` and logged "Response timeout".

An upload or read whose next part, next range, completion or abort the stop refused used to wait out `load.op.wait.limit` (30 s by default) before it was reported unresolved, which lowered the step's whole-run rate, bandwidth and concurrency in `metrics.total.csv`. Steady-state figures do not change. Known issue: a stopped step can leave the multipart uploads it had in flight open on the target. Each chunk of a multipart response no longer allocates a buffer it throws away. Responses up to 64 KiB, which every normal initiation, completion and abort is, are read as before; LIST responses are unchanged.
- **Numeric URI arguments, headers and tags** — A number or boolean given for a URI argument (`storage.net.http.uri.args`), HTTP header (`storage.net.http.headers`) or S3 object tag (`storage.object.tagging.tags`) through `spt run --engine-override` or a `POST /run` defaults document no longer fails the step with `ClassCastException … cannot be cast to class java.lang.String`. URI arguments and headers are sent as typed (`--engine-override storage.net.http.uri.args.tid=0012` sends `tid=0012`), and tags as the text `s3-aws` already sent (`7`, `true`, `1000.0`). With the Netty HTTP drivers (`s3`, `s3-tables`, `s3-rdma`, Atmos, Swift), a list or map URI argument or header, or a header with no value, now fails the step with a message that names it instead of a cast or a `NullPointerException`, and so does a list or map tag with `s3`, `s3-tables` and `s3-rdma`; `s3-aws` and `fs` take these values as before. A number or boolean given either way for `load.step.id`, `run.comment`, `storage.integrity.mode`, `storage.integrity.algorithm`, `storage.integrity.input.provenance` or `storage.integrity.input.expectedProducerId`, which failed every run, is refused with a message that names the setting and says to quote the value; other text settings behave as before. Values that worked before send the same bytes, though a step's `config.yaml` now records a number or boolean given for these three maps as quoted text (`X-Id: "007"`), with every driver; a whole-map override such as `storage.net.http.uri.args={tid: 0012}` keeps its YAML meaning, so quote the values in a map literal.
- **A stopped step ends sooner after its limit** — When a step stops, the engine settles every operation still queued before dispatch as unattempted, and it now does so in fewer passes over the queues: each queued operation is visited once by the storage driver and is not settled again by the step. At the shipped `driver-limit-queue-input` of 1,000,000, a stopped step can hold one to two million queued operations (two million for a multipart write), which took several seconds after the last request. That settling now takes much less time: in a 20 s time-limited write against a loopback S3 target, a stopped multipart step (about two million queued operations) ended about 2.7 s after its limit instead of about 7.2 s, and a single-part step (about one million) about 0.8 s after it instead of about 2.9 s. So the step ends sooner and its whole-step duration and averages include less of this bookkeeping; a stopped multipart write at the default queue limit still spends a second or more on it. Steady-state results and the `operation.lifecycle.csv` counts are unchanged. Since 5.15.0.
- **File system listing** — Reading a listed `fs` path with data verification no longer reports every SPT-written file as corrupt, and an items file written from such a listing now holds each SPT-written file's real offset instead of 0. The offset is now taken from the file name, not the full path; a file SPT did not write still gets offset 0, unless its name after the prefix happens to be a non-negative number in the naming radix (such as `readme` in radix 36). Affected all releases.
- **`--auto-terminate-seconds` stops the run** — With auto-results on (the default), `spt run` and `spt replay` `--auto-terminate-seconds` stop the run again at the deadline, a regression since 5.14.0: the CLI let the step run to its natural end and then exited 1. At the deadline the CLI now stops the run through the engine API (`DELETE /run` with the run's ID), fetches its artifacts, then shuts the engines down if `--shutdown-on-complete` is set; with `--auto-results=false` it ends the run through shutdown and container stop, as before. It exits 0 when the run was healthy up to the deadline and the stop is confirmed, and prints `Auto-terminate: the run was stopped at the N s deadline`. It exits 1, with an error that names auto-terminate, when the stop request fails or the run reports no terminal state after it, since the results may then be partial; with `--shutdown-on-complete` the CLI then tries the shutdown, which can still confirm the stop. A run that had already ended at the deadline, or that ended on its own while the stop was in flight, says so instead of saying it was stopped; one that had already ended takes the normal exit rules. A step that failed before the deadline still exits 1. For `spt run`, a run whose every request failed before the deadline also exits 1, and a DELETE or verification workload stopped at the deadline exits 1, because it did not complete. Ctrl-C keeps its exit code and messages. The TUI waits for the stop attempt, for a bounded time, before it closes. The deadline starts after the CLI has connected to the hosts and covers engine start-up, launch and the run; in headless mode a deadline reached before the workload is submitted now ends the start with an error that names auto-terminate, instead of the start step's own timeout text.
- **Verified split read of an updated item** — With `item.data.verify` on, a read split into ranges by engine `item.data.ranges.threshold` (from the CLI, `--engine-override item.data.ranges.threshold=N`) on the `s3` and `s3-rdma` drivers no longer reports the ranges of an item whose ranges were updated as corrupt (`RESP_FAIL_CORRUPT`) when the target holds the updated data. Each range is now verified as the same bytes of a whole read are, against the updated data where the item's update mask says so; before, it was checked against the item's data before the update, so a range that held stale data for an updated part of the item passed; such a range is now reported corrupt, as a whole read of it always was. Reads of items with no updated ranges, whole reads and unverified reads are unchanged. The defect dates from 5.6.0.
- **DELETE verification of large objects** — On the Netty S3 drivers, `--validate-inventory` pre-validation no longer fails for objects of 2 GiB or more, and post-verification no longer reports a surviving object of that size as unresolved instead of still present. A `HEAD` response's size no longer counts against the control-response limit. Affected since 5.15.0.
- **RDMA pool sizing under the image-pull skip** — With `--skip-image-pull` or `SPT_SKIP_IMAGE_PULL`, RDMA pool sizing now pulls a missing non-dev engine image, as the engine launch does, instead of leaving that host unsized at the default direct-memory limit. A dev image is still never pulled, and `spt.log` notes that the pool-sizing probe may pull the image despite the skip. Since 5.17.0.

## [5.16.2] - 2026-10-22

### Added

- **Concurrent local runs** — Added `spt run --rmi-registry-port` (default 1099) to set the local engine's RMI registry port, so several `spt run` instances can run on one host at once, each with its own `--api-port` and registry port. Before, a second instance failed to start with `Port already in use: 1099`. Remote and distributed runs keep port 1099 and reject any other value.

### Changed

- **Target-bucket provisioning** — Before each phase of an `s3`, `s3-rdma` or `s3-aws` workload starts, the engine on the entry node now checks the phase's target buckets: the bucket it writes to, the bucket it reads or lists, and every bucket its items file names. It creates a missing bucket only for the phase that writes the run's objects (the write or seed phase), and only after the target answers 404. `spt run --provision-target-bucket=false` (engine `storage.targetBucket.provision`, default `true`) still checks every bucket but never creates one. A bucket that is missing or not accessible ends the run before any object operation, with the phase and the cause in the console and exit code 1. Before, each worker checked and created the bucket on the first object it wrote, distributed workers could race to create it, and a failure only failed operations. Existing buckets are used as they are; SPT never clears, deletes or reconfigures a bucket. See [Target Buckets](cli/docs/TARGET_BUCKETS.md).
- **S3 region** — The `s3-aws` driver now picks its region in the same order as the other S3 drivers: `--region` or `storage.region`, then the region of a standard AWS endpoint (`s3.<region>.amazonaws.com`), then `us-east-1`. Before, it used `eu-west-2` when no region was set. `spt run` now also reads `S3_REGION` when `--region` is not given. A CreateBucket request to a standard AWS endpoint outside `us-east-1` carries the region's location constraint.
- **Bucket names in custom scenarios** — A per-operation expression (`${...}`, `#{...}`) in the bucket segment of `item.output.path` now fails the step at start with a configuration error, because the bucket must be known before the phase starts; keep such expressions after the bucket, as in `/bucket/${...}`. An initialization expression (`%{...}`) in the bucket segment, including the engine's default timestamped output path, is now evaluated once by the entry node, so every node of a distributed run writes to the same bucket instead of one per node.
- **`--create-prefix` deprecated** — The flag never had an effect. It is now hidden, prints a deprecation warning, and will be removed in the next minor release.
- **S3-AWS workers** — With `storage.driver.threads` unset, the `s3-aws` driver now runs one I/O worker per concurrency permit instead of at most one per hardware thread. Every request blocks its worker, so a run with `--threads` above the node's CPU count previously kept only as many requests in flight as the node had CPUs and queued the rest behind busy workers; it now keeps the configured number in flight. A worker blocked in a request no longer takes queued permits with it: new operations go to idle workers first.

### Fixed

- **Bucket checks taken for a missing bucket** — The `s3` and `s3-rdma` drivers treated any failed bucket check, an authorization failure (401, 403) or a server error included, as a missing bucket and tried to create it. Only a 404 now counts as missing; any other answer is reported as the bucket being inaccessible, and no create request is sent. Worker logs no longer print the response body of a failed bucket check.
- **Runs that fail during setup** — A run that fails before any phase slice starts now ends with an engine `FAILED` status that carries the step, the category and the message, and `spt run` exits 1 for every workload. The console shows that cause rather than a missing-metrics error, and a distributed run ends instead of waiting for metrics that never come.
- **S3-AWS lost requests** — A request the AWS client lost with no connection (so that `storage.crt.socketTimeoutMs` could not see it) stayed in flight for the rest of the run and, through the worker it blocked, stalled every permit queued behind it. The driver now puts a deadline on each request with `storage.crt.requestTimeoutMs` (default 300000, `0` for no bound), from the moment it makes it until the response has been read in full, a GET's body included: a request that outlives it is cancelled and fails as a timeout, counted and logged like any other.
- **S3-AWS stop with a lost request** — A step that stopped with such a request in flight waited for the whole of `load.op.wait.limit`, could not be stopped within the engine's budget, and ended with the operation still active. Once the step has closed admission, the driver now gives the requests in flight `storage.crt.stopTimeoutMs` (default 5000, half of the engine's budget for stopping a run; `0` to turn off) and then cancels them, a GET still reading its body and a request made after the grace included, so they end as `INTERRUPTED` and the stop completes within the budget. A driver stopped and started again gets a fresh grace for each stop.

## [5.16.1] - 2026-10-19

### Fixed

- **S3-AWS stalled requests** — The `s3-aws` driver now applies `storage.crt.connectionTimeoutMs` (default 5000) and `storage.crt.socketTimeoutMs` (default 30000) to all of its S3 clients. ### Changed

- **S3-RDMA buffer reuse** — The `s3-rdma` driver now keeps registered buffers and reuses them across operations instead of allocating, zero-filling, and registering a new buffer for every PUT and GET, which limited RDMA throughput. A buffer is reused only after the server's final response to its request, and a buffer used by an integrity-verified GET only after that GET verified; buffers of requests that time out, lose their connection, or fail are deregistered. Pooled buffers stay within half of the JVM's direct-memory limit and are released when a per-operation buffer would otherwise not fit; transfers above 1 GiB are not pooled. `spt run --rdma-buffer-pool=false` (env `RDMA_BUFFER_POOL`, engine `storage.rdma.bufferPool`) restores per-operation buffers. The RDMA data-path summary in `messages.log` adds pool counters.
- **Remote entry-node log relay** — Entry-node output now arrives over one `docker logs --follow` SSH session instead of a new SSH session twice a second, reducing CPU load on the entry host. The console still shows only the engine's stdout; its stderr (such as JVM and logging warnings) is kept only in the CLI log, and only with `--log-level debug`.
- **Dependency updates** — The CLI is now built with Go 1.25.14 (previously 1.25.10). Updated Netty to 4.1.139 (netty-tcnative 2.0.84), AWS SDK/CRT to 2.55.14/0.48.5, Log4j to 2.26.1, Jackson to 2.22.3, Jetty to 9.4.58, Commons Codec to 1.23.0, Commons Lang to 3.21.0, Guava to 33.7.2, Avro to 1.11.5, Disruptor to 3.4.4, SLF4J to 1.7.36, Bouncy Castle TLS to 1.86.2, and Docker Go connections to 0.8.2.

### Fixed

- **S3-RDMA reply validation** — RDMA PUT and GET now honor the server's `x-amz-rdma-reply` and `x-amz-rdma-bytes-transferred` headers. A server that declines RDMA (HTTP 200 with reply 501, or no reply) previously produced "successful" writes counted at full object size although nothing was stored; declined PUTs now fail. Declined GETs are counted once over HTTP when `--rdma-fallback` is enabled and fail otherwise. GET bytes come from the server's reported transfer size, and a success without that header, a byte-count mismatch, or any HTTP body (including chunked bodies) on an RDMA success fails as corrupt.
- **S3-RDMA multipart uploads** — The multipart initiate request no longer allocates, copies, and registers the entire object; only upload parts use RDMA, each with a part-sized buffer. Parts that fail RDMA preparation or time out now settle their upload's part accounting exactly once, so retries and abort proceed.
- **S3-RDMA ranged reads** — Reads with fixed or random byte ranges now use HTTP instead of an RDMA buffer sized for the whole object, which previously miscounted or failed valid range responses.
- **S3-RDMA memory exhaustion** — An RDMA buffer allocation that runs out of JVM direct memory, or a PUT payload copy that runs out of memory, now fails the operation, or sends it over HTTP with `--rdma-fallback`, instead of escaping the driver and stopping its dispatch of further operations.
- **S3-RDMA fallback setting** — With `--rdma-fallback` disabled, RDMA buffer-registration or token failures now fail the operation instead of silently sending it over HTTP.
- **S3-RDMA fallback payload** — With `--rdma-fallback`, a PUT whose RDMA preparation failed after its payload was copied (for example, when no RDMA token could be generated) was sent over HTTP without its body and failed. The fallback request now carries the whole payload, and the same failure with `--rdma-fallback` disabled no longer reports the object's bytes as written.
- **Partial-read retries at stop** — A partial read whose retry had not yet sent its request when a run stopped now delivers its earlier failure exactly once. Previously, the failure was counted but its result was never delivered, and the run ended with “Range result delivery failed.”
- **DELETE failure-budget reporting** — Duration-based DELETE runs now propagate a failure-budget exception consistently when the budget is exceeded during worker startup, matching failures detected during active waiting.
- **Composite expression evaluation** — Give each expression segment its own evaluation context to prevent intermittent method-resolution failures when synchronous and asynchronous segments run together.

- **Write prefixes and saved manifests** — `spt run write` now honors `--prefix` before any shard directories, preserving complete object keys in saved manifests for subsequent reads and cleanup. Combining `--save-items` with `--cleanup` retains the manifest after object deletion. Workloads that do not support `--prefix` now reject it explicitly instead of silently ignoring it.
- **Run labels on result artifacts** — `spt run --label` now applies the same sanitized label to generated step IDs and their result filenames as to the results directory. Runs without a label retain the `mt` prefix.
- **Distributed launch messages** — Ordinary distributed workloads now report “distributed run” instead of the misleading “distributed replay.”
- **Verification service startup** — `spt verify` now polls the required service ports for up to 30 seconds instead of checking once after a fixed ten-second sleep. Healthy engines that start more slowly can pass, already-ready engines proceed immediately, and unavailable ports still cause a bounded failure followed by container cleanup.
- **False metrics-schema warning at run start** — The TUI no longer reports “Incompatible metrics JSON … requires metrics_schema >= 2” while engines are reachable but have not yet published metrics for the current run, such as during the pre-step stabilization pause. Genuinely incompatible metrics payloads still produce the warning, including when they first appear after startup.
- **Credentials in step config logs** — The engine now masks storage credentials in each step's logged `config.yaml`, which single-host runs keep under `.node-home` in the results folder.
